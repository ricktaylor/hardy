# Storage Consistency Updates (DRAFT / RFC)

> **Status: draft for review.** Captures the node-state-ledger and policy-epoch design settled in the design dialogues of 2026-09-04 — the epoch as a filter-declared chain fingerprint, salted by an operator break-glass flag — and harvests the storage shutdown & recovery items from the project backlog (clean-shutdown markers, clock tamper detection). It amends the restart re-admission story in [`filter_subsystem_design.md`](filter_subsystem_design.md) — the "every restart conservatively re-admits everything" rule is superseded by operator-declared reevaluation — and completes the freshness story that [`policy_subsystem_redesign.md`](policy_subsystem_redesign.md) and [`routing_table_redesign.md`](routing_table_redesign.md) lean on. Of the mechanisms described here, only the per-bundle `PolicyEpoch` stamp and `clear_classification` exist in code today; everything else is design.

## Motivation

Three otherwise-separate needs converge on the same missing object — a durable record of facts about the store *as a whole*, rather than about any one bundle:

- **The policy epoch needs one durable ingredient.** The filter redesign settled lazy re-classification: every persisted classification value (annotation slots, later `class`, `route_table` and `route_key`) is a cache of a pure derivation, stamped with the policy epoch that produced it and re-derived when the stamp goes stale. The epoch itself is content-addressed — a digest of the chain's declared behaviour, recomputed at every startup and needing no storage (see below) — but its *operator override* is durable state: a forced reevaluation must survive restarts and crashes mid-sweep, or the sweep is silently half-applied, and the salt that expresses the override is the ingredient that needs a home.
- **Clean-shutdown detection.** The backlog's "clean shutdown markers" item: a storage implementation should keep a private record of whether it was shut down in an orderly fashion, so that restart can distinguish "resume" from "recover". Today the restart walk unconditionally re-parses and re-validates every stored bundle; a clean-shutdown marker is the precondition for ever lightening that.
- **Clock tamper detection.** The backlog's sibling item: detecting that the clock has moved backwards across a restart (which corrupts bundle-age and lifetime arithmetic) requires a persisted last-known-time baseline to compare against.

None of these facts is per-bundle, and the metadata schema has no home for any of them. This document gives them one.

## The node-state ledger

**A small singleton record inside the metadata store.** Each metadata-storage backend persists a tiny set of node-scoped facts alongside the bundle records it already holds — a row in SQLite/PostgreSQL, a process-scoped value in the memory backend.

**Placement inside the metadata store is fate-sharing, not convenience.** The salt is half of the epoch the stamps were issued under; the two must travel together. When an operator restores a metadata-store backup, the salt arrives with the stamps it governs and the comparison stays coherent: a forced sweep in progress at backup time resumes correctly, and no restore can silently cancel or spuriously repeat one. A sidecar file in a configuration directory can desync from a restored store, splitting the epoch from its stamps.

**Tenants and ownership split.** The ledger has three foreseen tenants with two distinct owners:

| Fact | Owner | Crosses the storage trait? |
| --- | --- | --- |
| reevaluation salt (the policy epoch's operator override) | BPA (semantic state) | yes — typed accessors |
| clean-shutdown marker | the storage implementation | no — private to the backend |
| clock baseline | BPA (future) | yes, when it lands |

The BPA-owned facts cross `MetadataStorage` as narrow typed accessors, not a generic key-value bag: the ledger holds a handful of known facts, and a stringly surface on a public extension trait invites exactly the out-of-contract coupling the metadata visibility rules exist to prevent. The shutdown marker never crosses the trait at all — each backend (bundle-data stores included) is free to keep its own, in whatever representation suits its consistency mechanism.

**Trait additions are non-breaking, and degradation is graceful *and correct*.** The accessors get default implementations that signal "unsupported". A backend without a durable ledger loses nothing on the automatic path — the chain fingerprint needs no storage at all — and degrades only the operator override: a forced reevaluation holds only while the flag stays set (each flagged start mints a fresh in-memory salt), rather than persisting on its own until the sweep drains. Durability is an upgrade a backend opts into, never a correctness precondition, and out-of-tree backends keep compiling.

## The policy epoch — a fingerprint of the chain, salted by the operator

The per-bundle side is already settled and partly built ([`filter_subsystem_design.md`](filter_subsystem_design.md), "Restart re-admission"): each bundle's classification group carries the `PolicyEpoch` it was last derived under, a mismatch against the current epoch triggers lazy re-derivation at the Dispatch block, and zero is reserved so that records from before the mechanism (or with the field elided) are always stale. This document settles the other side: what the current epoch *is*, and when it changes.

**The epoch is a fingerprint of the running chain, declared by the filters themselves.** The question "has this filter's behaviour changed in any way that matters?" is answerable only by the filter's author — no other party can see inside a closed classifier — so the declaration rides the code that changes: every registered input filter supplies a behaviour version, and the engine folds those versions, the chain order (last-writer-wins makes order behaviour-relevant), the hook structure and slot registrations, and the config-gated built-ins' settings into one stable 64-bit digest, using a fixed platform-stable hash (never the standard library's per-process randomly-keyed one). The digest is a pure function of the running chain: recomputed identically at every startup, it needs no storage, no bump protocol, and no ordering discipline. This is the honest key for what the classification group already is — a cache of a pure derivation, keyed by a digest of the deriving function, the build-system action-key shape — and it makes policy changes self-announcing: the stock `[classes]` provider declares the hash of its compiled rule set, so editing classification configuration reevaluates stored bundles with no operator action at all. It also makes reverts free: a bundle classified under chain *F* that sat parked through a chain-*G* era reads as fresh again when the deployment reverts to *F*, correctly, because its cached classification really is *F*'s output. The author guidance is one sentence, recorded in the registration rustdoc: version the *behaviour*, not the build — a filter that declares its crate version reevaluates the world on every release; the rule-hash is the model.

**An unversioned filter means "assume changed".** The declaration defaults to unversioned, and an unversioned filter poisons the composite with a per-boot value: a chain containing one drops that deployment to conservative reevaluate-every-restart — the filter doc's original rule, safe by default — and precision becomes an upgrade each filter earns by declaring itself. The opposite default (some stable constant) would silently convert every forgotten version bump into stale classification, which is the failure this mechanism exists to prevent.

**The operator keeps a break-glass lever, and it is the one durable thing: the salt.** The lookup epoch is a digest of (chain fingerprint, salt). The salt lives in the node-state ledger and changes only when the operator passes the `reevaluate_policy` flag — the database-upgrade idiom — which rotates and persists it, making every stored bundle stale at once regardless of what the filters declared. This covers the two honest residuals of self-declaration: an author who shipped a behaviour change without bumping their version, and reevaluation forced for its own sake (suspected corruption, belt-and-braces after an incident). The salt must be durable because the override's promise must survive restarts: a salt mixed in for one boot only would revert on the next start, and bundles the forced sweep had not yet reached would silently read fresh again — a half-applied sweep with no record that one was in flight.

The filter doc's original rule — bump on *every* restart, because behaviour-change detection is impossible — is thereby resolved rather than merely replaced: detection was being asked of the wrong party. It is impossible for the platform and trivial for the author. Self-declaration keeps the old conservatism as the *default* (unversioned filters retain it) instead of the only mode, and shrinks the operator's obligation from "know when to reevaluate" to "hold the break-glass flag". The accepted residual is stated plainly: a behaviour change shipped without a version bump leaves stored bundles stale until the operator notices and pulls the flag — the same failure the release-notes obligation carried, relocated to a code-review-visible constant beside the code that changed.

**Crash safety is four small properties, not a protocol.**

- **Recomputation, not recovery.** The fingerprint half of the epoch is derived from the running chain at every start. A crash cannot desync it from the policy it describes, because they are not separate facts.
- **Rotate-before-use.** The salt is the only durable write and carries the only ordering rule: a flagged start persists the rotated salt *before any bundle is processed*, so no stamp is ever issued under a salt that did not survive.
- **Single-record atomicity.** A stamp and the classification it guards live in one metadata record, mutated in memory and persisted in one write — a crash leaves either the old coherent record or the new one, never a fresh stamp over stale values.
- **Interrupted sweeps resume by construction.** A crash mid-reevaluation leaves some records re-stamped with the new epoch and the rest still carrying the old one. Every subsequent start recomputes (or re-reads) the same new epoch, so the stragglers still mismatch and the sweep simply continues, lazily, across any number of restarts until it drains. Nothing records "a sweep is in progress" because nothing needs to: the stamps themselves are the progress ledger.

**Restart already is the sweep.** No walk machinery is added. Every recovered population re-enters `process_bundle` on its own existing trigger — the restart walk re-dispatches checkpointed bundles directly, transfer and delivery checkpoints reset to Waiting and follow through the waiting poll, `WaitingForService` transits when its service re-registers, fragments via the reassembly poll. The staleness check sits at the top of `process_bundle`, upstream of every consumer of classification (the route lookup, the class read), so laziness is sound: no decision is ever taken on a stale cache. Fresh arrivals are stamped with the current generation when their input chain runs, so they never pay a spurious re-derivation at their first re-dispatch.

**Rejected alternatives**, and why:

- **A per-lookup re-derivation hook** (a "Forward Classifier" re-running key selection at every dispatch entry) was litigated in the routing dialogue and dropped: it cannot actually escape the epoch — its inputs are annotation slots, which are themselves epoch-stamped caches, so it re-derives stale values deterministically — and it forks the one-classification-pass model while paying chain cost on the waiting-sweep hot path. See [`routing_table_redesign.md`](routing_table_redesign.md).
- **A standing generation number in configuration.** Durability for free (the config file), but it makes the epoch a value the operator must manage and never reuse; a one-shot imperative flag has no reuse hazard and matches the existing upgrade idiom. Its content-hash variant returns in the settled design at the correct locus — declared by each filter over its own rules, rather than computed by the operator over configuration files.
- **An operator-declared counter as the *only* trigger** (this dialogue's interim ruling). Workable, but it relocates the unanswerable question to the party least equipped to answer it: the operator must learn from release notes what the filter author already knew. It survives demoted, as the salt behind the break-glass flag.
- **Deriving the generation by scanning stamps** (`max + 1`). Unsound: when the newest-stamped bundles all depart, the scan rolls the generation back, and stragglers classified under genuinely old policy read as fresh.
- **A node-local counter outside the store** (state file beside the config). Breaks fate-sharing with restored backups, as above.

**What this settles for routing.** With the epoch durable and operator-declared, the routing lookup's inputs are persisted classification like everything else in the group — honest caches under the stamp, re-derived by the same lazy pass. The dispatcher resolves `{table, key}` per lookup entirely from the record — `route_table.unwrap_or(default)`, `route_key.unwrap_or(destination)`, both freshened by the Dispatch-block check before any consumer reads them — and hands them to the RIB as arguments. No separate lookup-time classification seat exists, no `ClassPolicy` property feeds the lookup, and the RIB reads neither policy nor metadata itself ([`routing_table_redesign.md`](routing_table_redesign.md)).

## Clean-shutdown detection — towards automated restart

**The marker is the classic dirty flag, kept privately by each store.** A backend marks its ledger dirty when it opens for writing and clean on orderly close; finding the dirty mark at open means the previous process died with work possibly in flight. This is deliberately storage-internal: each backend's consistency mechanism differs (the write-side half already exists in the localdisk store's atomic tmp-write/rename/fsync discipline; SQLite and PostgreSQL bring their own journalling), so what "dirty" implies and how to recover from it is the backend's business.

**What it enables, later: proportionate restart.** Today the restart walk assumes the worst unconditionally — every stored bundle is re-parsed and re-validated, with junk deleted, duplicates reconciled, and orphans re-admitted. That behaviour is exactly right after a crash and mostly wasted after an orderly shutdown. A clean marker is the precondition for a future fast-path restart that lightens the walk; the full walk remains the response to a dirty marker. Whether a `was_clean` signal ever crosses the trait to let the BPA modulate its own recovery is left open below — nothing in this document depends on it.

**The fast path cannot break the epoch.** The staleness check lives at `process_bundle`, not inside the restart walk, so a lightened walk changes nothing about re-derivation: whatever moves, transits; whatever transits, gets checked. The two mechanisms compose without either knowing the other exists.

## Clock tamper detection — the third tenant

Bundle lifetime arithmetic trusts the local clock; a clock that moves backwards across a restart can resurrect expired bundles or extend lifetimes, and one that leaps forward can mass-expire traffic in custody. Detection requires only a persisted baseline — the ledger records a recent wall-clock high-water mark, and a start that finds `now` before the baseline knows the clock has been tampered with or lost. The *response* (refuse to start, quarantine expiry decisions, log loudly) is deliberately not designed here; this document only gives the baseline its seat in the ledger, alongside the other two tenants, so the trait surface is shaped with all three in view.

## Integration

- **The filter registration surface** gains the behaviour-version declaration for input filters (the kinds whose outputs persist — Classifiers and Verifiers; egress Rewriters persist nothing and declare nothing), defaulting to unversioned. The stock `[classes]` provider declares its rule-set hash.
- **`MetadataStorage`** gains the typed ledger accessors for the BPA-owned facts (the salt now; the clock baseline later), with default-unsupported implementations (the graceful-degradation contract above). SQLite, PostgreSQL, and the in-memory backend implement them; bundle-data stores are untouched.
- **The Builder/config** gains the `reevaluate_policy` flag. Startup ordering is the one rule: store online → compute the chain fingerprint, read the salt (rotate-and-persist if flagged; per-boot if unsupported) → the resolved epoch reaches the engine before recovery and bundle processing begin.
- **The filter engine** computes the composite digest at build, holds the epoch for the run, and performs the Dispatch-block check and stamp-at-classification; the re-derivation pass itself (provenance-selected input chain, bounded head read from storage per [`streaming_pipeline_design.md`](streaming_pipeline_design.md)) is the already-settled Phase 3 machinery, unchanged.
- **Document amendments carried by this design**: the filter doc's re-admission section (restart no longer auto-bumps; the stamp is an opaque digest compared by equality, not a monotonic counter; the version-the-behaviour guidance), and the routing/policy docs' key-selection paragraphs (the persisted `route_key` cache under the epoch, in place of both the original derive-once wording and the interim lookup-time framing).

## Open questions

1. **`was_clean` visibility.** Does the clean-shutdown marker ever cross the trait so the BPA can lighten its restart walk, or does each backend only consume its own marker internally? (The fast-path restart design owns this.)
2. **Runtime policy pushes.** When the centralized policy manager lands, a push that swaps the agent classifier's rule snapshot changes that classifier's declared version, and the engine recomputes the composite with no ledger write — lazy convergence follows automatically. Whether the engine re-reads declarations dynamically or the push drives an explicit recompute, and the push protocol's version encoding, are the policy tranche's questions.
3. **Accessor and declaration shape.** Per-fact ledger methods versus one small node-state struct; whether the salt is opaque bytes or a bare integer at the trait surface; per-filter version method versus a registration parameter; and the fixed digest algorithm.
4. **Ledger writes on the data stores.** Whether the bundle-data backends (localdisk, S3) want a shutdown marker of their own from day one, or only when the fast-path restart design needs it.
