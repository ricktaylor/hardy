# Refactor plan — the streaming sequence and the tranches after it

The single working plan for the in-flight refactor effort: the streaming sequence, the filter redesign's remaining Phase 3, and the tranches that follow. Design rationale lives in the design documents ([`filter_subsystem_design.md`](filter_subsystem_design.md), [`streaming_pipeline_design.md`](streaming_pipeline_design.md), [`queue_architecture.md`](queue_architecture.md), [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md)) and the two redesign drafts ([`routing_table_redesign.md`](routing_table_redesign.md), [`policy_subsystem_redesign.md`](policy_subsystem_redesign.md)); this is the work list, in dependency order.

## Current state

**Landed:** main carries the v0.3.0 stack — #673 (CLA streaming), #674 (bpv7 parse), #675 (parse), #676 (cbor perf), #677 (metadata) — with #680 (service streaming) and #710 (delivery mirrors forwarding). The #712–#719 train is merged, on bpv7's #753 (the editors refuse what the parser rejects; flags compare by encoding) and #757 (editing and signing keep BPSec operations verifiable): the filter redesign's Phase 2 (#712, which also seats Phase 3's Egress and Deliver hooks), streamed ingress (#717, #718) and streamed origination (#719). The streaming sequence below is under way: egress, delivery, storage and streaming BPSec follow, each its own PR. What else remains: Phase 3's open rows, the ADU reassembly tranche, the cleanup that follows the acceptance-at-ingress change (#760, which also settles bpv7's checks API: the parser classifies, one `Parsed::check` by role reports, the `bpsec` feature gates the processing, and bpa's `bundle::arrival` holds the header pass with its fate, report and payload modules) and the delivery leg, and the queue, policy and routing tranches.

**Streaming seams.** The pull-shaped `Receiver`/`Segment` stream (`bpa::stream`) is the decision of record for all six seams — CLA ingress, service and application originate, both deliveries, and CLA egress — and all six traits take it. A caller holding a whole buffer passes `Bytes`, itself a one-segment `Receiver`; truncation is an error with ack gating; liveness, the size cap and backpressure are composable receiver decorators. A write/commit handle was rejected: parse-at-commit cannot express the pre-drain gate's parse-during-arrival, and push inverts control toward the trivial party. The BPA's own egress and delivery doors hand over the whole bundle as one segment until their legs land.

## Sequencing

1. The streaming sequence (below), one PR per leg so that each review covers one concern: ingress (#717, #718) → origination (#719) → egress → delivery → storage → streaming BPSec. Egress precedes delivery because its payload is plaintext pass-through and needs no streaming cryptography; delivery must decrypt as it streams once the BPSec leg lands, and streams plaintext payloads until then. The storage leg gives `BundleStorage` its streamed write and load and retires `concat_stream`. It precedes streaming BPSec, whose in-flight cryptography reads through it, and it completes the CLA, service and storage surfaces that other work builds on, so the gRPC API (#741) can land while streaming BPSec is under way. Streaming BPSec comes last because it touches both directions.
2. Filter Phase 3's open rows land with the leg or tranche each names.
3. The ADU reassembly tranche is independent of the streaming legs: its `Store` seams carry interim bodies, and its true streaming arrives with the storage leg's streamed load and write.
4. Per-hop BPSec, acceptance at ingress and the security roles a Classifier names (#760, below) land ahead of the egress and delivery legs; the output doors' cleanup that those legs make possible (their key-source scopings, egress's `PerHopRefusal::Covered`, delivery's decryption and its `NoKey` park) follows them, listed in the per-hop section below.
5. Delta fields ride with their consuming tranches: `MetadataDelta` carries the annotation slots (Phase 2), the `route_table`/`route_key` routing inputs (#718) and the egress Bundle Age decision `add_bundle_age` (#760); `class` arrives with the policy tranche.
6. The queue, policy and routing tranches follow the streaming sequence.

Every step ends green: `cargo fmt --check`, `clippy --locked --all-targets --all-features -- -D warnings`, workspace tests, bpv7 `no_std` check.

## The streaming sequence

One PR per leg, in this order, so that each review sees one coherent scope. A leg's PR stays a draft until its planned work is in.

**Lengths without a buffer.** The streamed doors declare lengths from the persisted block index, never from a loaded buffer's `data.len()`. `Bundle::encoded_len()` (`bpv7/src/bundle.rs`) derives the whole-bundle length with its RFC anchors — the payload block MUST be last and a bundle SHALL be an indefinite-length CBOR array (both RFC 9171 §4.1), so the payload's bundle-absolute `extent.end` plus the one break byte is the encoded length. Because canonical CBOR gives the payload a definite-length head, the value is known at header-parse time, before the payload arrives: the declared-size admission gates use it today (ingress `parse_headers` and both originate doors), and it serves egress framing (`streaming_pipeline_design.md` §6.2's "original bundle size") and any announce-style wire's `bundle_size`. The ADU length needs no accessor: the payload block's `data` range is an interior range with no break-byte dependency.

### Ingress — landed (#717, #718)

Bundle reception is one streamed pipeline with one metadata write: the header pass parses and verifies off the CLA stream, the Ingress chain and the route lookup decide at the pre-drain gate, and the payload drains through the validating `ValidatingReceiver`. Bundles are stored as received; the scheduled §5.1.1 removals apply at each output door.

**Gate-then-drain + routing (§5.7 routing-at-commit, #718).** The RIB lookup runs at the pre-drain gate as the decision of record — an explicit Drop rejects without awaiting the payload, and the commit executes the carried decision, deciding again if the table changed during the drain (fresh arrivals skip `DispatchPending`, except the admin-endpoint and fragment arms, which queue for the processing pool). The drain follows the gate decisions, the ordering a Classifier-set storage QoS (a policy-tranche target) will need: the door decorates the arrival with a `ValidatingReceiver` and drains it through one `Store::save_stream` call only once the chain and the route lookup have settled — a rejected bundle spools nothing and is never persisted, with the door settling the decorator's verdict after the drain and discarding any save the verdict rejects.

**The ingress drain still accumulates in memory before `save`.** `Store::save_stream` (`store.rs`) is the streaming seam at its target signature, but its interim body spools through `concat_stream`, because `BundleStorage` exposes only `save(Bytes)` / `load -> Option<Bytes>`, so there is nowhere to spool a payload without materialising it. The storage leg (below) swaps the backends' streamed write into that body; its callers change only in the error type they map.

### Origination — landed (#719)

Both application doors stream: `ApplicationSink::send_streamed` builds around a segmented payload (`Builder::build_stream`), and the raw door runs the same strict header pass as CLA ingress, in the source role. Both settle their gate decisions before a payload byte spools, write the record once, and execute the route decision directly. A store-side LRU settles recent duplicates at the input gates.

**Revisit `max_bundle_size` after this leg.** The cap is admission policy carried as `Option<NonZeroU64>` end to end, but an unset builder cap takes the private 64 MiB default at dispatcher construction, because ingress accumulates whole bundles in memory and "no policy" would mean unbounded RAM growth per hostile stream. Once the bound is enforced in the u64 domain against spooled storage, the default becomes `None` (non-breaking, the default being private), and the dispatcher's `max_bundle_size_mem` seam and its addressable-bound clamp go. The knob's meaning shifts to custody-admission policy (a half-arrived transfer has no metadata entry, so the reaper and eviction cannot touch it; the spool chokepoint still needs the bound). The lift also needs dynamic storage-headroom admission, and streaming BPSec for encrypted payloads, which delivery decrypts with the whole bundle resident until then.

## Per-hop BPSec and acceptance at ingress (#760)

A per-hop block's security operations end at the next node that changes it, which is their acceptor, so no valid operation puts a per-hop block inside an encrypted BIB.

**Built: the next node accepts the per-hop blocks' operations at ingress.** Under the block lifecycle model, a node that must change or remove a block is the acceptor of every security operation on it, and the security source of any protection on the block that replaces it. The header pass decrypts and verifies the operations on a Previous Node or Bundle Age block, which every forwarder must replace (RFC 9171 §5.4), and on a Hop Count it can read and check, and CLA ingress writes each block in plaintext without them before the bundle is first stored (`dispatcher::rewrite_received_headers`): the forwarder's per-hop writes in `update_extension_blocks` meet no protection, and a local Service reads the Previous Node (§4.4.1). A missing key is a failed acceptance (the keyless Bundle Age entry below). The source half, re-encrypting an updated block under a BCB this node sources where security policy requires the block to stay confidential, waits for an egress security policy, which the BPA does not yet have.

**Built: a Classifier names this node's security roles by service.** `MetadataDelta::roles`, a union across the Ingress chain that serves the arrival only, the acceptor's role outranking the verifier's on one operation, names for each block whether this node is the verifier or the acceptor of its BCB operation and of its BIB operation. As an acceptor, the gate processes the operations after the chain and the route, through bpv7's `Parsed::check`, and the ingress rewrite removes them: the BCB operation on a block accepted for confidentiality, with those on an encrypted BIB that covers it and on that BIB's other targets, all or none (RFC 9172 §3.9), each of which must be announced for confidentiality too, and the BIB operation on a block accepted for integrity; the BIB over a block accepted for confidentiality alone stays, in plaintext, checked where this node holds its key, and a block encrypted here cannot be accepted for integrity alone, its BIB being encrypted with it. As a verifier, a role a node that is not the acceptor "MAY attempt" (RFC 9172 §5.1.2) and one announced is expected to fill, the gate requires a block verified for integrity to carry an integrity operation this arrival checked and found good, the header pass's or the drain's for a streaming payload, and authenticates the ciphertext of a block verified for confidentiality by decrypting it, the plaintext going nowhere, at the gate for an extension block (`Parsed::check`) and in the drain for the payload; a verification that passes changes nothing. A failure (15), a block this node cannot accept or verify (11: no key, integrity on a block encrypted here, or an encrypted BIB over the block that also covers a block not announced for confidentiality, whose BCB operation goes with its own), or a service announced that the block does not carry (12, the target discarded as RFC 9172 §5.1.1 and §5.1.2 recommend of one the policy expected protected) meets the fate the flags decide, as the per-hop blocks do, a coupled block that fails included. The per-hop blocks are outside the announcements, accepted by the header pass before the chain runs, and so is the destination's acceptance of every operation, which outranks any verification announced. A BIB on the primary block is verified and removed, and the primary stored as received (RFC 9171 §4.3.1); one left with no CRC is refused at the egress door when the node requires primary integrity, never given one. **Built: the destination accepts every operation it can at ingress.** Where the gate delivers the bundle here, now or once its service registers, every block an operation targets joins the acceptors (RFC 9172 §1.4), the primary block's BIB included; a fragment's wait for reassembly. An operation in a security context this node does not support is its acceptor's alone: where this node accepts it, the target is a failed acceptance and the security block one it cannot process (13, its flags decide), and elsewhere it travels untouched and unreported. **Built: the destination accepts the payload's own operations at ingress.** The gate resolves the keys and begins the decrypt and verify stages, a missing key deleting the bundle there (Block unsupported) rather than parking it, since nothing waits for a key; the drain decrypts the payload and checks its BIBs against the plaintext as it streams into the save, and the payload is stored in plaintext without them, its CRC restored; a plaintext payload's BIB goes the same way. A Classifier's announcement of the payload is accepted the same way, a node that is not the destination processing a BCB where its policy directs it (RFC 9172 §5.1.1); a fragment's is passed over, for acceptance after reassembly. A block whose encrypted BIB also covers the payload is accepted with it, its BIB operation checked over its plaintext.

**Built: neither a Previous Node nor a Bundle Age block reads `Maybe`.** A signed-then-encrypted Previous Node is non-compliant at its source: the block lives one hop, so its signer and its encryptor are the same node, and the final paragraph of RFC 9172 §3.9 forbids a source adding both a BIB and then a BCB for one target. No BCB context yields a plaintext integrity result (RFC 9172 §3.2 counts the AEAD tag as part of the confidentiality service), so neither a MAC nor an asymmetric assertion such as draft-ietf-dtn-bpsec-cose's `COSE_Sign1` combines compliantly with confidentiality. An integrity operation on a Previous Node or Bundle Age block inside an encrypted BIB is therefore invalid, whether or not the receiving node holds the keys: only the forwarder that inserted the block can source an operation on it, and either it signed and then encrypted the block, which §3.9 forbids, or the signature is an earlier node's that the changing node, as its acceptor, had to remove. So bpv7's parser never marks either block `BibCoverage::Maybe`: beside an encrypted BIB a node cannot read, such as the bundle source's end-to-end protection of the payload, the block is accepted, or discarded as a failed acceptance, and replaced, where it previously parked at every egress attempt until it expired. Such an operation is one this node, the block's acceptor, cannot accept, so the block meets a failure's fate: a keyed pass that decrypts the BIB proves it, a conflicting security operation (RFC 9172 §7), and the block's flags decide, reporting or deleting the bundle as Conflicting security operation (§7.1, reason code 16); without the key, the structure shows the BIB may cover the block when every BCB-covered block other than a BIB is one of those two (`Parsed::check`, where its decryption of encrypted BIBs by necessity finds them), and the block is one this node cannot accept. Either way the BIB goes with the block, whole, since this node encrypts nothing again. Hardy can still receive bundles that hide one from a node without the key; the hidden signature fails closed at the downstream key-holder.

**The Hop Count is the partial exception.** Its increment is a SHOULD (RFC 9171 §4.4.3), so a signature on a count no node has incremented can legitimately survive inside an encrypted BIB, and the parser still marks it `Maybe`. A Hop Count whose operations this node cannot accept travels unchanged and unincremented, and is logged at info level where this node forwards the bundle: one it holds no key for, one with an operation in a security context it does not support, and one whose BCB operation is coupled to others it does not accept (RFC 9172 §3.9), on an encrypted BIB it cannot read that may cover the block, or on one that also covers another block, unless this node accepts every block that BIB covers. One under a BIB it holds no key for is not accepted either, since this node is the acceptor of a Hop Count's operations only where it holds the keys to check them: it is stored with that BIB, and egress leaves it unincremented. A Bundle Age this node cannot accept on a bundle with a creation time is no failure: this node writes the one it owes from the clock, so the received block is discarded whatever its flags, and nothing is reported. **Target:** egress's refusal of a protected Previous Node or Bundle Age block (`PerHopRefusal::Covered`), which parked the bundle, is unreachable now that neither reads `Maybe` and ingress accepts or discards their operations, and goes.

**A scheduled removal never encrypts a BIB again.** CLA ingress applies the scheduled removals (RFC 9172 §5.1.1 failure-drops, failed acceptances and honoured `delete_block_on_failure` unknowns) through bpv7's `remove_blocks` before the bundle is first stored. The cascade never encrypts anything again, so it refuses a block whose removal would shrink an encrypted BIB that also covers a block that stays. Where the RFCs require the block gone, its ciphertext having failed to authenticate (§5.1.1) or its flags asking for it to be discarded (RFC 9171 §5.6 Step 4), ingress removes that BIB with it, whole, as §5.1.1 discards such a target with every security block associated with it, the BIB's other targets keeping their ciphertext without its operations; otherwise, as for a failed acceptance tied to a block that stays, it keeps the block as received, an exception to the fate's discard. Each is logged at info level. The cascade also refuses a block an encrypted BIB this node cannot decrypt may cover (`Maybe`, which a per-hop block other than the Hop Count never reads), and the primary block's BIB while another operation's scope includes the primary: ingress stores those as received, logged, the rest removed, rather than leave a BIB naming a block that no longer exists or break that operation.

**Built: a keyless forwarder's Bundle Age.** Under the block lifecycle model a node that must update a Bundle Age is the acceptor of every security operation on it, so one it holds no key for is a failed acceptance, and RFC 9172 §5.1.1 requires the block to be discarded with its operations (ruled 2026-10-01, reading "cannot be decrypted" as including holding no key; revisit if the IETF DTN WG settles the reading). The header pass treats a missing key for any operation on a Previous Node or Bundle Age block, a BCB's or a BIB's, as a failed acceptance: the block is an RFC 9171 §5.6 Step 4 block, whose flags demand a "Block unsupported" report and delete the bundle, and which is otherwise discarded with its operations, its value unread; a bundle without a creation time loses its only expiry signal, and the fate the header pass decides deletes it. A bundle with a creation time whose Bundle Age ingress discards, for a failed operation or a failed acceptance, is marked (`add_bundle_age`, ahead of the Ingress chain, which may clear it) so egress writes a fresh one from the clock: a node upstream wanted the bundle to carry one, and a downstream node without an accurate clock must use it (§5.5).

**What the change leaves.** The output doors keep paths no received bundle reaches once ingress accepts: a received payload is stored in plaintext, and an acceptor without a key is refused at the door. They go in one cleanup once #760 and the delivery leg have both landed, since the delivery leg reshapes the same doors; two switches and one ruling go with it.

## ADU reassembly tranche (`fragment_reassembly_redesign.md`)

Settled, not yet built. Fragments are never bundle records: each pending ADU is one wire-form partial under the reassembled id, with its coverage in `BundleMetadata`, merged door-side under a per-ADU permit, and an Ingress Classifier decides the divert, so the filter chain runs once per ADU. Built ahead of it, within today's machinery: security on a fragment is processed after reassembly (RFC 9172 §5.2), the ingress door checking nothing of a fragment's own, the stitcher restoring the payload under fragment 0's security blocks (`Editor::restore_block`) and the whole re-entering the door; and `MetadataDelta::reassemble`, persisted with the chain's output until the door merges fragments itself. 
All fragmentation-shaped work — the defects below, streaming-shaped reassembly — is gathered in [`fixing_fragmentation.md`](fixing_fragmentation.md), and the redesign settles the decision it deferred. The entries record defects in the current code until the redesign closes them; where a fix direction differs from the redesign, the redesign governs.

**Concurrent final fragments both park NotReady.** `poll_fragments` only sees siblings already parked in `AduFragment` status, so when the last two fragments of an ADU are processed concurrently each polls while the other is still `Dispatching`, both conclude the set is incomplete, both park, and nothing ever re-triggers reassembly (reproduced with a delegating metadata store holding the two polls open across each other). Deliberately not patched in place: the fix would land in `poll_fragments`/`reassemble`, which the settled redesign in [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) deletes wholesale — its ledger-driven completion has no park-vs-poll window. Another motivating instance of the shape problem that redesign exists to fix.

**RFC 9171 §5.9 material-extents reassembly (overlapping fragments).** `Store::reassemble()` (`src/storage/adu_reassembly.rs`) requires the received fragments to tile `[0, total_adu_length)` exactly: contiguous, non-overlapping and complete. Overlapping fragment sets are rejected and the fragments dropped as `ReassemblyResult::Failed`. RFC 9171 §5.9 is more permissive: overlapping fragments are legal on the wire (e.g. the same bundle refragmented differently on divergent paths), and a conformant reassembler computes each arriving fragment's "material extents" — the byte ranges not already covered by previously received fragments — completing when the material extents concatenate to the full ADU. First-received bytes win; overlap is trimmed, not rejected. Hardy has never accepted overlap: the pre-tiling-check code also failed overlapping sets (payload-length sum ≠ total), except for the length-sum coincidence that silently delivered a corrupt ADU (2026-07-08 review findings #1/#4). The tiling check makes rejection deterministic and safe, but Hardy remains non-conformant for legitimately overlapping fragment sets. Settled in [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) (not yet implemented): the per-ADU `Coverage` ledger merges overlapping ranges and replaces `FragmentSet`/`poll_fragments`, so overlap stops being a failure mode.

**Deletion status reports on reassembly failure.** When reassembly fails (`ReassemblyResult::Failed`), `Store::adu_reassemble` deletes the held fragments directly against storage (`delete_data` + `tombstone_metadata`) and the dispatcher's `Failed` arm returns without action — no deletion status reports are generated. RFC 9171 §5.10 says a deletion status report SHOULD be generated per deleted bundle (each fragment is its own bundle, reported to its own report-to EID with its fragment offset/length) when the report flag is set and reporting is enabled. Not patched in place: [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) dissolves the case — fragments are never held as bundle records, failures shrink to door-side drops of single arrivals, and an expired partial reports its own deletion through the reaper.

**Offset-keyed fragment set drops the trigger's cleanup on a hostile collision.** `FragmentSet.adus` is keyed by fragment offset, so a hostile sibling sharing the trigger fragment's source/timestamp/offset but a different `total_adu_length` (a distinct bundle id, so nothing deduplicates it) overwrites the trigger's seeded entry. The trigger then never reaches the cleanup loop — its metadata is never tombstoned and its `Dispatching` gauge never decremented — while the reassembly fails the length check and drops without cleanup. Not patched in place: closed structurally by [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) — fragments are never bundle records, and a sibling with a mismatched total drops at the door's consistency check under the ADU's merge permit.

**ADU reassembly materialises the whole ADU with no size bound (silent too-large death).** `Store::reassemble` (`src/storage/adu_reassembly.rs`) allocates the entire ADU in RAM (`vec![0; adu_len]`) sized from the wire-declared `total_adu_length`, which is checked only for `usize` addressability, never against `max_bundle_size`. A large declared total can exhaust memory, and a non-addressable one fails reassembly with only a `debug!` — no report either way. Not patched in place: [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) bounds memory by `max_bundle_size` behind the streaming merge seams.

**A restart can strand a complete fragment set (restart orphan).** Restart recovery only re-counts `AduFragment` rows (`src/dispatcher/restart.rs`); completion is checked when a new sibling arrives, so a set whose last fragment was parked just before a crash, with reassembly not yet run, is never completed and sits until its lifetime expires. Not patched in place: [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) gives restart a reassembly-aware arm that completes a finished ledger at recovery.

**Shapes the rows keep.** `Bundle` is never deserialized: backends decode a `StoredBundle` that becomes a `Bundle` only through `into_bundle(status)`. The `MetadataStorage` mutation vocabulary is create / status-CAS / terminal (`insert`, `swap_status`, `tombstone_if`/`tombstone`, beside the bulk resets and the recovery protocol), so no write can match a tombstone. Independent of this tranche, and cheapest after its record reshape: seal the (bpv7, per-hop) pair into one type only the parse layer can mint. Today the per-hop cache is set by hand in three `metadata.per_hop =` assignments (`ingress.rs`, two in `originate.rs`) and the status-report path's `with_per_hop`, and at Egress it holds the values as received while the Rewriters' edits live only in the bytes (`filter/mod.rs`, `forward.rs`).

### Open items the queue tranche owns

**Backend conformance tests.** The shared `tests/storage` harness (`metadata_suite.rs`, run against memory, sqlite, and postgres) pins only a winning `swap_status` and an unconditional `tombstone`; the conditional semantics are still hand-rolled per backend (`metadata_mem.rs`, sqlite's `test_swap_status_is_conditional`/`test_tombstone_if_is_conditional`) and postgres has none. Add META cases pinning a lost `swap_status` from a stale snapshot, `tombstone_if` win and loss, and `swap_status` against a tombstone (quietly `false`, never resurrecting), then retire the per-backend copies.

**sqlite status codec: port postgres's `StatusFields` shape.** sqlite's status codec is a positional tuple — `from_status -> (i64, Option<i64>, Option<i64>, Option<String>)` / `to_status(code, param1, param2, param3)` — where peer and queue ids both travel as anonymous `param1`/`param2`; postgres solved the identical problem with a named `StatusFields` struct. Port that shape to sqlite when the conformance suite lands. The suite should also pin the two real cross-backend divergences the codec hides: postgres narrows peer ids to `i32` (a typed error above 2^31) while sqlite stores them losslessly as `i64`, and sqlite's `from_status` stores the ADU-fragment `sequence_number()` via `as i64` (a value above `i64::MAX` is silently reinterpreted negative and round-trips bit-exact through the mirror cast on read, where postgres refuses it with a typed error).

**sqlite temporal columns → INTEGER epoch milliseconds.** `expiry` and `received_at` are TEXT columns holding rusqlite's `OffsetDateTime` encoding, and both are ordering keys: `poll_expiry` keysets on `(expiry, rowid)` and `poll_pending` pages in `received_at` order — so chronological correctness rides on the lexicographic order of an encoding rusqlite owns. Write-site UTC normalization (see `insert`) holds the invariant today, but a rusqlite encoding change (their parser already carries a "legacy format" branch from the last one) would interleave two string formats in one table and silently corrupt the order. Fix: store both columns as INTEGER Unix-epoch **milliseconds**. Milliseconds are exact for wire-derived values (DTN creation time and lifetime are both ms) and safe at the saturated top end — a `Duration::MAX` lifetime caps expiry at year 9999, which fits `i64` at ms (~2.5×10¹⁴) and µs, but overflows at ns; never nanoseconds. Sub-ms components from the monotonic `CreationTimestamp` nudge truncate to ties, broken by `rowid` exactly as today (the reaper needs approximately-ascending only). The keyset queries keep their shape with integer binds; the index shrinks from ~32-byte strings to 8-byte ints; sqlite reaches parity with postgres's native `TIMESTAMPTZ` semantics; and the UTC-normalization crutch and its comments retire. Backfill is pure SQL — `CAST(ROUND((julianday(expiry) - 2440587.5) * 86400000) AS INTEGER)` (sqlite's date functions parse the rusqlite format; f64 julianday precision ≈ 50 µs at modern dates, fine at ms) — or moot if the upgrade wipes/purges rows under the established metadata-store upgrade precedent. Ride with the `StatusFields`/conformance codec pass above: same file, one coordinated schema migration.

**Redundant tombstone on the Completed path.** After a successful `tombstone_if`, `delete_bundle` issues a second, unconditional `tombstone` — a wasted UPDATE per completed transfer on the SQL backends. Needs a data-only delete variant (or flag) so the resolution's own tombstone stands.

**A CLA that cancels every attempt loops the bundle through dispatch until it expires.** A cancelled transfer re-enters dispatch at once, with no routing event, so a CLA that cancels deterministically is offered the bundle again at the pace of the dispatch and egress queues. A route lookup that excludes the cancelling CLA was set aside: at a bundle's only CLA it turns a transient failure into a park with nothing to wake it. Pacing the retry belongs with the rest of retry policy (`design.md`, deferred CLA transfer outcomes).

**A BPA-side egress abort needs its own reason.** The load never fails, but the BPA may abort an egress stream before its end for a reason of its own. A CLA whose pull then returns `RecvError` answers `StreamCancelled`, and the forward door, which re-dispatches a cancelled transfer at once, cannot tell that from the CLA's own cancel. `RecvError` stays a stop signal: the egress stream's adapter records why it aborted, as the input doors' `ValidatingReceiver` and `BuiltReceiver` record theirs, and the door reads that reason before it resolves a `StreamCancelled`.

**The re-dispatch pre-swap is subsumed by `requeue()`.** `resolve_offer`'s Redispatch arm, which a deferred `Failed` outcome and a cancelled transfer share, pre-swaps `ForwardAckPending` → `Dispatching`, and the dispatch channel's send then CASes `Dispatching` → `DispatchPending`; letting the send CAS directly from the `ForwardAckPending` snapshot saves one write per failed transfer with identical race semantics. Deliberately parked: the `requeue()` primitive in `queue_architecture.md` makes this fall out for free — do not implement separately.

**`PeerId` newtype.** bpa has ~26 bare `peer: u32` sites, roughly half from the transfer-outcome branch (`ForwardAckPending { peer }`, `owns_peer`, `reset_peer_ack_pending`, the outcome plumbing). The hazard is concrete: `ForwardPending { peer, queue }` carries two u32-domain identifiers and the sqlite codec flattens both into adjacent positional `i64`s. A `PeerId(u32)` newtype (with `QueueId` as its natural sibling) makes cross-assignment unrepresentable end-to-end and gives the postgres `i32` narrowing a single home.

**`next_hop` payload inside the queue-key type (same premise as the `PeerId` newtype above).** The `Eid::Null` placeholder, `BundleStatus::same_queue`, the `send_to` debug_assert, and three independently implemented backend queue disciplines all exist because `BundleStatus` doubles as queue identity and per-bundle payload. The poll half is one typed row selector shared by `MetadataStorage::poll(&StatusSelector, stream, limit)` and `MetadataStorage::sweep(&StatusSelector, to) -> u64`, superseding `poll_pending`, `poll_waiting`, `poll_service_waiting`, `poll_expiry` and the three `reset_*` sweeps. `StatusSelector` is exhaustive, so a new arm is a compile error in every backend until it handles it; each arm is a WHERE clause that never matches a tombstone, and `sweep` refuses the scan-only arms (`UnsweepableSelector`). Arms: `Exact(BundleStatus)`, in ascending `received_at`; `ForwardQueue { peer }`, that peer's `ForwardPending` across every queue (the route-change preemption reset, leaving `ForwardAckPending` transfers alone); `PeerQueues { peer }`, its `ForwardPending` plus `ForwardAckPending` (swept when the adjacency goes); `ServiceQueues { service }`, `DeliverPending` plus `DeliveryAckPending`; `All`, the soft-recovery scan; `Expired { now, exclude_handoff }`, the reaper's expiry-ordered refill on the caller's clock, optionally excluding the hand-off statuses. The egress lane poll needs a per-lane arm. The typed-send half is a named edge `enqueue_forward(store, bundle, peer, lane)` growing `next_hop` as an edge parameter. Do not mint a `QueueKey` enum or a `ForwardSender` type: they would be second names for `StatusSelector` and the named edges. Until then, the postgres `poll_pending` queue-identity comment is the interim guard.

**The `bpa.bundle.status` gauge wants one owning module.** The gauge is hand-balanced at sixteen raw metric sites across seven files, eight of them outside `Store`'s transitions, and drift accumulates silently when a status write loses a race (the gauge-drift note in [`TODO.md`](TODO.md)). One owning module in `otel_metrics.rs` with `admit`/`transition`/`remove` verbs — the metric name and label vocabulary private to it — turns the balance into a local property. Deferred from the dispatch review as cross-cutting churn outside that branch's correctness story.

**Claim-on-dequeue ritual duplicated across four consumers.** The `channel.rs` module doc's claim discipline is hand-copied in `forward_bundle`, `deliver_bundle`, the dispatch consumer, and `poll_service_waiting`. The owner is a `lifecycle::transitions` module, the crate's only status writer. A `StatusWriter` holds its own `Arc<dyn MetadataStorage>` privately and its raw CAS wrappers are private to the module, so holding a `&StatusWriter` grants exactly the named edges: an illegal transition is a function that does not exist. Each edge is a CAS from the caller's snapshot (`false` = lost the race, and the caller drops its stale copy); the only unconditional writes are the pre-circulation ingress checkpoint, the terminal delete, and restoring one's own won claim. The `bpa.bundle.status` gauge moves only inside the edges, where a CAS wins, and `record_sweep(from, to, count)` replaces the per-reset gauge pairs and the `Eid::Null` dummy-status hack in `store.rs`. The edges are methods on `StatusWriter` (`store.status_writer().claim_dispatch(&mut bundle)`), in verb families: `claim_dispatch` ({`Waiting`, `WaitingForService`} → `Dispatching`), `requeue_dispatch` (a failed `ForwardAckPending` → `Dispatching`), `claim_forward` (`ForwardPending` → `ForwardAckPending`), `enqueue_deliver` and `claim_delivery` (`Dispatching` → `DeliverPending` → `DeliveryAckPending`), `park_waiting`, `park_for_service`, and `resolve_delete` (`drop_expired` for the reaper) followed by `finalize_delete`. A channel's move into its fixed target status gets a domain name per target, and an edge with no consumer is not added. Never a caller-supplied target status: a generic claim or enqueue taking an arbitrary `BundleStatus` is unimplementable outside the module by design. On the two hand-off legs the Dispatcher composes one thin method per leg — `claim_for_forward(bundle, peer)` / `claim_for_delivery(bundle, service)` (Dispatcher methods, because the pre-claim expiry arm resolves via `drop_bundle`) — each running expiry-check, then named-edge CAS, then `Option<Claimed>` where `Claimed` is a `#[must_use]` token with no `Drop` behaviour, and becomes the only bundle input `offer_to_*` accept. Rejected: a single generic `claim_handoff` (it must take the target status, exactly the caller-supplied-edge shape the named edges exist to rule out).

**metadata_mem clones the whole matching set under the Mutex in all five `poll_*` fns.** Two-pass key-then-clone polls fix it without contract changes.

**Legacy `New` rows are stranded.** Ingress writes one record, directly at `Dispatching`, so `New` is never persisted any more — but a store written by an earlier build can hold `New` rows (a crash between that build's insert and its checkpoint). Restart's recovery leaves `New` in its no-op arm and every backend's `poll_expiry` excludes `New` (memory, sqlite, postgres), so such a row is never recovered and never expires, holding its id and its bundle data. Fix: a per-backend purge at migration, or drop the `New` exclusion from `poll_expiry` so the reaper expires the rows. Only stores written by unreleased builds are affected — 0.2.0 records do not load at all.

**Hot-path structural re-parses.** One hot path re-runs `hardy_bpv7::parse::parse` on stored bytes the BPA has already parsed: `adu_reassembly.rs` per fragment merge. The per-hop rewrite's editor takes the record's block index, as delivery and the administrative door hand over the payload through it, and the Egress and Deliver chains decode only the BCB OperationSets they locate through it. Candidates: a cached parse beside the loaded data. Natural home: this tranche's record reshape, or a dedicated perf tranche; benchmark before and after. Sibling inside the bpv7 BPSec cascade: `canonical_primary` re-decodes and CRC-re-verifies the primary block on every include-primary BIB/BCB operation, pure confirmation of an invariant the parser already enforced — pass an "already canonical" flag or cache the canonical primary bytes once per bundle so the IPPT/AAD path borrows raw.
