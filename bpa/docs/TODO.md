### Concurrent final fragments both park NotReady (2026 dispatch review, finding 6)

`poll_fragments` only sees siblings already parked in `AduFragment` status, so when the last two fragments of an ADU are processed concurrently each polls while the other is still `Dispatching`, both conclude the set is incomplete, both park, and nothing ever re-triggers reassembly (reproduced with a delegating metadata store holding the two polls open across each other). Deliberately not patched in place: the fix would land in `poll_fragments`/`reassemble`, which the settled redesign in [`fixing_fragmentation.md`](fixing_fragmentation.md) deletes wholesale — its ledger-driven completion has no park-vs-poll window. Another motivating instance of the shape problem that redesign exists to fix.

### RFC 9171 §5.9 material-extents reassembly (overlapping fragments)

#### Background

`Store::reassemble()` (`src/storage/adu_reassembly.rs`) requires the received fragments to tile `[0, total_adu_length)` exactly: contiguous, non-overlapping and complete. Overlapping fragment sets are rejected and the fragments dropped as `ReassemblyResult::Failed`.

RFC 9171 §5.9 is more permissive: overlapping fragments are legal on the wire (e.g. the same bundle refragmented differently on divergent paths), and a conformant reassembler computes each arriving fragment's "material extents" — the byte ranges not already covered by previously received fragments — completing when the material extents concatenate to the full ADU. First-received bytes win; overlap is trimmed, not rejected.

Hardy has never accepted overlap: the pre-tiling-check code also failed overlapping sets (payload-length sum ≠ total), except for the length-sum coincidence that silently delivered a corrupt ADU (2026-07-08 review findings #1/#4). The tiling check makes rejection deterministic and safe, but Hardy remains non-conformant for legitimately overlapping fragment sets.

#### What full §5.9 support needs

- `FragmentSet` must hold *trimmed* ranges decided at insert time by arrival order: on insert, clip the new fragment's payload range against the extents already covered (possibly splitting it), rather than keying whole fragments by raw offset.
- The completeness gate in `poll_fragments()` (`adu_totals >= total_adu_len`) must sum material extents, not raw payload lengths, or completion fires early on overlapping sets.
- The copy loop in `reassemble()` then slices each stored payload sub-range; the tiling invariant holds by construction.
- §5.9 requires the reassembled ADU to replace the payload of the fragment whose material extents include offset zero — the current "fragment 0" special-casing needs re-deriving from material extents, not from a raw offset-0 key.

### Deletion status reports on reassembly failure

When reassembly fails (`ReassemblyResult::Failed`), `Store::adu_reassemble` deletes the held fragments directly against storage (`delete_data` + `tombstone_metadata`) and the dispatcher's `Failed` arm returns without action — no deletion status reports are generated. RFC 9171 §5.10 says a deletion status report SHOULD be generated per deleted bundle (each fragment is its own bundle, reported to its own report-to EID with its fragment offset/length) when the report flag is set and reporting is enabled.

The fix is plumbing, not policy: `adu_reassemble` should hand the fragment `Bundle`s back on failure instead of consuming them, so `Dispatcher::reassemble` can route each through `drop_bundle(bundle, reason)` (which already does the flag-gated `report_bundle_deletion` + delete). Reason-code selection per failure mode needs deciding: `DepletedStorage` fits the length-not-addressable case; coverage gaps/overlaps have no exact RFC 9171 reason code (`NoAdditionalInformation` or `BlockUnintelligible` are the candidates).

### Offset-keyed fragment set drops the trigger's cleanup on a hostile collision (review round 3)

`FragmentSet.adus` is keyed by fragment offset, so a hostile sibling sharing the trigger fragment's source/timestamp/offset but a different `total_adu_length` (a distinct bundle id, so nothing deduplicates it) overwrites the trigger's seeded entry. The trigger then never reaches the cleanup loop — its metadata is never tombstoned and its `Dispatching` gauge never decremented — while the reassembly fails the length check and drops without cleanup. Key the map by bundle id (or fail the set on an offset collision); natural to fold into the §5.9 material-extents rework above, which re-keys this structure anyway.

## Ingress status-report conformance (invalid bundles, duplicates, expired arrivals)

RFC 9171 pins the reception report's reason code: §5.6 Step 2 prescribes "No additional information" (Step 4's "Block unsupported" is the only other reception-report reason), and a parse/CRC failure routes through the §5.10 Bundle Deletion procedure, whose deletion report is what cites "Block unintelligible". Every ingress reject with a recoverable bundle id — the keyed header pass, the payload drain (a `TailFailure` carries its reason via `reason_code()`), and the pre-drain gates (lifetime/hop, RFC 9171 validity, Ingress chain drop) — emits the conforming §5.6/§5.10 reports as a **single** status report bundle: one §6.1.1 record asserts both reception and deletion (the coalescing ION also performs), each assertion gated on its own request flag, the record's reason citing the deletion. The two reportless cases are deliberate and lawful: a refused transfer (truncation, size cap) is never reported, and a bundle whose primary block never parsed has no id to report — the §4.1 MAY-discard, outside the reception state machine. The pair is the §5.6-Step-3 → §5.10 normative shape; of the major implementations (ION, HDTN, µD3TN, DTNME, ESA-BP, cFS BPNode), only DTNME reports these failures at all (the same pair) — the rest drop them silently.

§5.6 Step 4's block-flag-alone trigger is honoured: an unprocessable block flagged `report_on_failure` forces the reception report (`ReceptionReport::Demanded`) even when the bundle requests no reception reporting — the trigger ION, µD3TN, and DTNME also implement, with ION and DTNME sharing our "Block unsupported" reason (µD3TN says "Block unintelligible"; the RFC leaves "cannot process" undefined, so that split is implementation choice). The §4.2.4 admin-record/anonymous carve-outs are rejected at parse, a report whose report-to is the null endpoint is suppressed at the dispatch seam, and the §5.1.1 failure-drop facts stay bundle-flag-gated (RFC 9172 keeps that reporting at requested-MAY level).

Duplicates: RFC 9171 specifies no duplicate-bundle processing at all (the word does not appear), so §5.6 read literally reports reception on every arrival, including replays. Decision: duplicates SHOULD get a reception report — a sender may be intentionally repeating a bundle probing for status-report ACKs. Adopted: ingress reports reception before the duplicate check (matching refactor/parse).

Expired arrivals are the deliberate exception, and a named SHOULD-level deviation: §5.5 makes deletion of an expired bundle a MUST (via §5.10, whose deletion report is SHOULD when flagged), and we instead treat a bundle that arrives already expired as if it never arrived — no reception report, no deletion report, no metadata entry — rather than amplifying already-dead traffic into report bundles. The silence rides §5.1's blanket discretion ("the decision on whether or not to generate a requested status report is left to the discretion of the BPA"); it is also the field-minority position — ION, µD3TN, DTNME, and ESA-BP all accept-then-report expired arrivals, only HDTN doesn't check. The pre-drain early gate implements this silence for the lifetime case (hop-exhaustion still emits the combined reception + deletion report). Bundles that expire *in custody* are unaffected: the validity filter, reaper, and `drop_bundle` paths still generate §5.10 deletion reports citing "Lifetime expired".

## Storage backend metrics (common + bespoke)

An audit (2026-07-10, while defaulting bpa-server to sqlite/localdisk) found the persistent storage backends emit no metrics at all — none of sqlite-storage, localdisk-storage, postgres-storage, or s3-storage even depends on the `metrics` crate. Their only observability is the `instrument`-feature tracing spans. Production nodes on the new persistent defaults therefore have no storage operation counts, error counters, or latencies; only the in-memory backends carry store-level metrics today (`bpa.mem_store.*`, `bpa.mem_metadata.*`, documented in `docs/user-docs/operations/observability.md`).

Two layers of work:

**Common metrics in the `Store` wrapper** (`src/storage/store.rs`) — every operation flows through it, so instrumenting there covers all backends uniformly and keeps the backend crates metrics-free for the common cases. Proposed: `bpa.storage.ops` (counter), `bpa.storage.errors` (counter), and `bpa.storage.op.duration` (histogram), labelled `store = metadata|bundle` and `op = load|save|replace|delete|insert|tombstone|get|poll` (the `poll_*` variants folded into one label value to bound cardinality).

**Bespoke per-backend metrics** where only the backend knows the truth: sqlite database/WAL file size, localdisk store-directory bytes and file count, postgres connection-pool stats, s3 request retries. These need either per-crate `metrics` emission or a `stats()`-style trait extension sampled periodically — a trait-surface decision to make when the work is picked up.

Documentation: a new backend-agnostic "Storage Operations" table in `docs/user-docs/operations/observability.md`, plus per-backend tables as bespoke metrics land.

## Bufferless bundle and ADU lengths (streaming prerequisite)

The streaming end-state removes the loaded whole buffer that `total_len = data.len()` measures at the delivery and forward doors, but both lengths are derivable from the persisted block index alone. `Bundle::encoded_len()` (`refactor/bpv7-parse`, arriving with the train cascade) names the whole-bundle derivation with its RFC anchors — the payload block MUST be last and a bundle SHALL be an indefinite-length CBOR array (both RFC 9171 §4.1), so the payload's bundle-absolute `extent.end` plus the one break byte is the encoded length. Because canonical CBOR gives the payload a definite-length head, the value is known at header-parse time, before the payload arrives — available to the early-filter gate, egress framing ([`streaming_pipeline_design.md`](streaming_pipeline_design.md) §6.2's "original bundle size"), the forward-before-store tee (§5.7), and any announce-style wire's `bundle_size`, none of which a commit-measured metadata field could serve. The ADU length needs no accessor at all: the payload block's `data` range is an interior range with no break-byte dependency.

Remaining work when the consumers land:

**Spool-commit cross-check.** The spool counts the bytes it writes; a commit-time `debug_assert!(counted == encoded_len())` catches index-vs-bytes drift without minting a second source of truth in metadata.

**Pin the ADU-length definition at the Application door.** The announced size is the *stored* payload block data length, pre-BPSec-decryption — AES-GCM preserves plaintext length so the two coincide today, but a length-changing confidentiality suite would make the distinction real. Post-reassembly bundles re-derive both lengths from the reassembled bundle's index.

## Remove `total_len` from the streamed ADU originate (ruled 2026-09-04)

`ApplicationSink::send_streamed` / `Dispatcher::originate_streamed` carry a declared `total_len` only because the payload block's definite-length byte-string head sits in the wire prefix `Builder::build_stream` emits before the first payload byte — the caller must know the length before the stream starts, which excludes producers that genuinely don't (a compressor, a live capture). We probably want to remove the parameter: spool the payload unframed and record a marker in `BundleMetadata` — the `to_remove` deferred-edit family — that the stored form's payload length is unresolved, fixed up at egress where the per-attempt resident rewrite already runs. Consequences to design through before starting: the stored bytes are not a canonical bundle until fixed, so every consumer of stored bytes (delivery's raw-`Service` path, restart's reconcile parse, the async payload verifier) must honour the marker or the fix-up must happen once at first read; the declared-size admission gate loses its pre-drain seat for these sends (the bound falls back to the spool's byte count); and the `BuiltReceiver` length-violation contract (`PayloadTooLarge`/`PayloadUnderrun`) dissolves — the stream defines the length. The parameter stays until then; callers that cannot declare use `send` or the trait's buffering default.

## Registration/routing concurrency races (whole-codebase review 2026-07-08, #14/#15)

Two non-atomic await sequences in the CLA/routing registries can race and leave stranded or wrongly-deleted state. Neither is data-loss or wire-corruption, and both need specific concurrent timing, so they were deferred past v0.2.0.

**`add_peer` vs concurrent removal (`src/cla/registry.rs`, review #14) — fixed 2026-09-03, one sliver remains.** `add_peer` now claims the address first, constructs the peer complete (no half-built published state: `PeerTable::reserve`/`publish` split id-minting from publication), and re-checks its claim after the construction awaits — a removal that won the claim finds the peer withdrawn instead of stranded RIB entries. Residual sliver: a removal interleaving the `rib.add_forward` loop itself (after the re-check) can still strand the entries added so far; closing it needs either a compensation sweep (complicated by the known gauge-drift accounting) or the generation/epoch guard, and rides with #15's identity-token work below. A second sliver (2026 dispatch review round 2): the `Reservation` guard RAII-covers the peer *id* only — the `cla.peers` address entry claimed before `publish` is not guarded, so cancellation of `add_peer` mid-construction leaks the address entry until the CLA unregisters; fold into the same epoch/identity work.

**`unregister_agent` name-reuse race (`src/routing/rib.rs`, review #15).** `unregister_agent` removes the agent from the name map, `await`s `agent.on_unregister()` (arbitrary duration — e.g. a gRPC proxy drain), then calls `remove_by_source(name)`. A new agent that registers under the same name during that await (the map slot is already free) has its freshly-installed routes deleted by the stale `remove_by_source`, which matches purely on the source string. Fix needs an identity/generation token so `remove_by_source` only removes routes owned by the unregistering agent instance, not a same-named successor.

**sqlite status codec: port postgres's `StatusFields` shape (review round 3, R3-3).** sqlite's status codec is a positional tuple — `from_status -> (i64, Option<i64>, Option<i64>, Option<String>)` / `to_status(code, param1, param2, param3)` — where peer and queue ids both travel as anonymous `param1`/`param2`; postgres solved the identical problem with a named `StatusFields` struct. Port that shape to sqlite when the D3 conformance suite lands. The suite should also pin the two real cross-backend divergences the codec hides: postgres narrows peer ids to `i32` (a typed error above 2^31) while sqlite stores them losslessly as `i64`, and sqlite's `from_status` stores the ADU-fragment `sequence_number()` via `as i64` (a value above `i64::MAX` is silently reinterpreted negative and round-trips bit-exact through the mirror cast on read, where postgres refuses it with a typed error).

**sqlite temporal columns → INTEGER epoch milliseconds (2026-09-09, from the dispatch review round-2 expiry-ordering question).** `expiry` and `received_at` are TEXT columns holding rusqlite's `OffsetDateTime` encoding, and both are ordering keys: `poll_expiry` keysets on `(expiry, rowid)`, `poll_pending` on `(received_at, id)` — so chronological correctness rides on the lexicographic order of an encoding rusqlite owns. Write-site UTC normalization (see `insert`) holds the invariant today, but a rusqlite encoding change (their parser already carries a "legacy format" branch from the last one) would interleave two string formats in one table and silently corrupt the order. Fix: store both columns as INTEGER Unix-epoch **milliseconds**. Milliseconds are exact for wire-derived values (DTN creation time and lifetime are both ms) and safe at the saturated top end — a `Duration::MAX` lifetime caps expiry at year 9999, which fits `i64` at ms (~2.5×10¹⁴) and µs, but overflows at ns; never nanoseconds. Sub-ms components from the monotonic `CreationTimestamp` nudge truncate to ties, broken by `rowid` exactly as today (the reaper needs approximately-ascending only). The keyset queries keep their shape with integer binds; the index shrinks from ~32-byte strings to 8-byte ints; sqlite reaches parity with postgres's native `TIMESTAMPTZ` semantics; and the UTC-normalization crutch and its comments retire. Backfill is pure SQL — `CAST(ROUND((julianday(expiry) - 2440587.5) * 86400000) AS INTEGER)` (sqlite's date functions parse the rusqlite format; f64 julianday precision ≈ 50 µs at modern dates, fine at ms) — or moot if the upgrade wipes/purges rows under the established metadata-store upgrade precedent. Ride with the StatusFields/D3 codec pass above: same file, one coordinated schema migration.

## Sink drop-cleanup via reconciler queue (replace spawn-from-Drop)

All three Sink `Drop` impls (`src/cla/registry.rs`, `src/services/registry.rs`, `src/routing/agent/sink.rs`) enqueue their async unregistration by spawning a task from sync `Drop`. This is already non-blocking, but spawn-from-Drop allocates a task per drop, gets exactly-once semantics only from ad-hoc guards, and can silently not run when the pool is already cancelled during shutdown — only the routing sink checks `is_cancelled`.

The tidy-up: `Drop` pushes a component identity onto an unbounded channel drained by one long-lived reconciler per registry — `Drop` stays plain sync code, delivery is exactly-once (an explicit `unregister()` leaves a stale id the reconciler no-ops on), and shutdown ordering becomes explicit (drain the reconciler before cancelling the pool). `refactor/sink-lifecycle` (`4d24e3f8`) already prototypes this shape for the CLA registry (`drop_tx` + `signal_dropped`); the work is applying the pattern uniformly across `cla::Sink`, `ServiceSink`, and `RoutingSink`. Design rationale in [`streaming_pipeline_design.md`](streaming_pipeline_design.md) §5.1.2; the channel-context alternative (`refactor/sink-to-context`) was considered and rejected — the Sink trait shape stays.

Out of scope here: §5.1.2 also proposes replacing the per-method `Weak::upgrade()` call gating with an `alive: AtomicBool` load. That is an orthogonal hot-path change (call gating, not drop delivery) and should be weighed separately.

## refactor/filters review triage (2026-09-09)

Open items from the `refactor/filters` deep review (`references/reviews/review-refactor-filter.md`, full work orders and per-finding dispositions inline there) routed to this ledger rather than the branch: the dispatcher items predate the branch or belong to the accepted hardening design, and the prior-art items are mined from the 2026-08-28 hardening patch (`references/reviews/bpa-hardening-changes-2026-08-28.patch`), which several entries name as reference implementation. The OF-03 queue-key entry lives beside its R3-4 sibling in the transfer-outcome section above.

**Dispatcher hardening group (F-01, F-02, F-15, F-16).** Four faces of the same missing discipline — pipeline consumers running before recovery, and resolutions acting on unclaimed bundles. F-01: the channel storage poller and `run_dispatch_queue` consumer start at `build()`, before `Bpa::start`'s awaited recovery, so with persistent metadata `DispatchPending` rows are claimed and routed against a not-yet-populated RIB while `recover()` walks the store; the work order stands as written in the review — the dispatcher owns its deferred start mirroring the registries' park-pending-drain-in-`start()` pattern (`Dispatcher::new` parks the consumer receiver, a new `Dispatcher::start` takes it once and spawns the consumer, called from `Bpa::start` after the awaited store start). F-02: status-report resolution in `admin.rs` fires up to four `on_status_notify` calls and an unconditional delete without claiming — `tombstone_if` before notifying, skip on a lost race. F-15: `poll_waiting`'s consumer processes unclaimed `Waiting` bundles (its sibling `poll_service_waiting` claims first) — CAS `Waiting → Dispatching` before `process_bundle`. F-16: the three `Drop(None)` resolutions delete unconditionally where `drop_bundle`'s own doc says every drop is claimed — one private `silent_drop_bundle` helper beside `drop_bundle` (`tombstone_if` then `delete_bundle`), all three sites routed through it. F-15/F-16 are interim mechanical patches: the claim ritual's structural owner is the hardening design's `lifecycle::transitions` (the claim-on-dequeue entry below).

**Claim-on-dequeue ritual duplicated across four consumers (OF-04).** The `channel.rs` module doc's claim discipline is hand-copied in `forward_bundle`, `deliver_bundle`, the dispatch consumer, and `poll_service_waiting`. The owner is the accepted hardening design's `lifecycle::transitions` module and its named edges (`claim_dispatch`, `claim_forward`, `claim_delivery`, `requeue_dispatch` per §3.2) — never a caller-supplied target status: once the StatusWriter confines raw `swap_status` to that module, a generic claim taking an arbitrary `BundleStatus` is unimplementable outside it by design. On the two hand-off legs the Dispatcher composes one thin method per leg — `claim_for_forward(bundle, peer)` / `claim_for_delivery(bundle, service)` (Dispatcher methods, because the pre-claim expiry arm resolves via `drop_bundle`) — each running expiry-check, then named-edge CAS, then `Option<Claimed>` where `Claimed` is a `#[must_use]` token with no `Drop` behaviour, and becomes the only bundle input `offer_to_*` accept. Rejected: a single generic `claim_handoff` (it must take the target status, exactly the caller-supplied-edge shape §3.2 kills). Prior art: the hardening patch implements the StatusWriter confinement end to end with most named edges wired; its delivery leg is dead code and its generic `enqueue_channel(writer, bundle, &BundleStatus)` is the rejected shape, so start from the patch's module but land the per-leg compositions. Taste-pass refinements to take with it: edges as methods on `StatusWriter` (`store.status_writer().claim_dispatch(&mut bundle)`), keep the patch's verb families (`claim_*`, `park_*`, `resolve_delete`/`finalize_delete`), rename `enqueue_channel` to a domain name, drop dead reserved edges until their consumers exist, and `record_sweep(from, to, count)` in place of the per-reset gauge pairs and the `Eid::Null` dummy-status hack in `store.rs`.

**Ingress commit points ignore the terminating `Segment::Final` (OF-01; amended post-cascade).** `parse_headers`' Ready arm and the ingress drain both commit on structural completeness, so a whole bundle sent in `Segment::Next` then cancelled is Accepted — the CLA acks a transfer the peer abandoned, violating the `Segment` doc's own contract. The review's anchors are rewritten by the spool leg, so re-verify at the train tip and re-draft the `confirm_final(stream)` helper against the landed drain shape (loop: empty `Next` is contract-legal padding; empty `Final` commits; bytes are trailing garbage → reject; `Err` → `Cancelled`; called only when completion arrives on a non-final segment, so the happy path never pulls again). The sequencing constraint stands: the grpc-api-v1 Receive door has a declared behavioural dependency on this, so it lands before or with that branch. Acceptance: whole-bundle-in-`Next`-then-drop pipeline tests asserting `Refused`/`Cancelled`.

**Every `Cla::forward` error parks undifferentiated in `Waiting` (OF-02).** `offer_to_cla`'s Err arm parks a transient `cla::Error::StreamCancelled` waiting for a routing event an interruption does not cause — stalled until expiry on a stable topology. Latent in-tree (whole-buffer `Bytes` cannot truncate). Fix shape: `Err(StreamCancelled) => OfferOutcome::Redispatch(bundle)`, with the claim + mandatory `get_metadata` reload moved into `resolve_offer`'s single Redispatch arm (the in-hand bundle carries in-memory rewrites that must not re-enter dispatch), which also lets `transfer_outcome::Failed` delete its inline swap.

**Pre-store ingress filtering with a typed per-transfer rejection (OF-16).** The hardening patch ran the Ingress chain before anything was persisted for live CLA transfers, with `cla::Error::FilterFailed` partitioned from systemic faults: a filter error or silent drop leaves nothing durable, the transfer stays unacked, and the peer's retransmission is the fail-closed retry loop. Structurally dissolves F-16 at the ingress site (deletion by never storing) and is the shape the grpc-api-v1 Receive door wants; rides the hardening legs. F-16's `silent_drop_bundle` remains the interim fix for the durable-path sites.

**Slot writes are trusted from the handle, not validated against the frozen table (OF-14; Phase 3).** `BundleMetadata::apply` honours whatever `SlotWrite` carries: a handle minted from a `FilterPack` never passed to `add_filters` writes an unregistered name into at-rest metadata, and oversized writes are silently dropped with a warn. The hardening patch hard-errored (`UnknownSlot`, `SlotValueTooLarge`) against the frozen `SlotTable` the engine already holds — restore the unknown-slot refusal when the Phase 3 slots wiring lands; the patch carries the tests.

**deliver.rs/admin.rs duplicate the payload-extraction block verbatim (OF-05).** The ~25-line parse + key_source + `bpsec::block_data(1)` block including the !Send-Rc scoping comment. Extract a sync `Dispatcher::payload_bytes(&self, data: Bytes) -> Result<Bytes, hardy_bpv7::Error>`; a sync fn cannot hold the OperationSets across an await, so both safety comments become compiler-proved and deletable. Pairs naturally with OF-04's delivery leg.

**Configured CLA/service activation failure degrades silently (F-17).** A pre-start duplicate `register_cla` makes a configured CLA silently never activate while every health signal says up (`error!` then continue, where baseline `build()` propagated with `?`). Replace both log-and-continue arms with `trace_expect`, the crate's fail-stop convention — the dispatch review round 2 recorded the downgrade as "acceptable", so this is a deliberate revisit, and the CHANGELOG must note that activation failure aborts.

**CLA activation order is hash order, not configuration order (F-18).** `ClaRegistry::start`'s doc promises configuration order but the pending map is a `HashMap`; `ServiceRegistryBuilder` already uses an order-preserving `Vec`.
