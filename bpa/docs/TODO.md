## Storage backend metrics (common + bespoke)

An audit (2026-07-10, while defaulting bpa-server to sqlite/localdisk) found the persistent storage backends emit no metrics at all — none of sqlite-storage, localdisk-storage, postgres-storage, or s3-storage even depends on the `metrics` crate. Their only observability is the `instrument`-feature tracing spans. Production nodes on the new persistent defaults therefore have no storage operation counts, error counters, or latencies; only the in-memory backends carry store-level metrics today (`bpa.mem_store.*`, `bpa.mem_metadata.*`, documented in `docs/user-docs/operations/observability.md`).

Two layers of work:

**Common metrics in the `Store` wrapper** (`src/storage/store.rs`) — every operation flows through it, so instrumenting there covers all backends uniformly and keeps the backend crates metrics-free for the common cases. Proposed: `bpa.storage.ops` (counter), `bpa.storage.errors` (counter), and `bpa.storage.op.duration` (histogram), labelled `store = metadata|bundle` and `op = load|save|swap|delete|insert|tombstone|get|poll` (`swap` for the status-conditioned `swap_status` writes) (the `poll_*` variants folded into one label value to bound cardinality).

**Bespoke per-backend metrics** where only the backend knows the truth: sqlite database/WAL file size, localdisk store-directory bytes and file count, postgres connection-pool stats, s3 request retries. These need either per-crate `metrics` emission or a `stats()`-style trait extension sampled periodically — a trait-surface decision to make when the work is picked up.

Documentation: a new backend-agnostic "Storage Operations" table in `docs/user-docs/operations/observability.md`, plus per-backend tables as bespoke metrics land.

## Negotiated size-cap deferrals (negotiated-max-bundle-size review, 2026-09-10)

**Central egress enforcement of the declared CLA limit.** The registration declaration only shrinks the effective cap echoed back to the CLA; egress does not consult it, so a CLA with a genuine transport limit below the BPA cap is still offered larger bundles and must refuse each per-bundle (`proto/cla.proto` documents this contract). Enforcing it centrally first requires splitting the two semantics the field conflates: a receive MRU folded into advertising (tcpclv4's declaration — RFC 9174 sends are bounded by the peer's session MRU, unknowable at registration) versus a transport limit the BPA must respect when offering.

**No terminal disposition for a deterministic per-bundle forward error.** A bundle whose encapsulated outer exceeds bibe's negotiated cap parks retriable in `Waiting` after its deterministic `PayloadTooLarge`, so every routing event re-runs the full egress pipeline into the same rejection for the bundle's whole lifetime. The dispatcher needs a terminal outcome (or back-off) for forward errors that cannot resolve differently on retry.

## Registration/routing concurrency races (whole-codebase review 2026-07-08, #14/#15)

Two non-atomic await sequences in the CLA/routing registries can race and leave stranded or wrongly-deleted state. Neither is data-loss or wire-corruption, and both need specific concurrent timing, so they were deferred past v0.2.0.

**`add_peer` vs concurrent removal (`src/cla/registry.rs`, review #14) — residual slivers.** `add_peer` claims the address first, builds the peer complete before publishing (`PeerTable::reserve`/`Reservation::publish`), and re-checks its claim after the construction awaits, so a removal that wins the claim withdraws the peer. Two slivers remain. A removal interleaving the `rib.add_forward` loop (after the re-check) can still strand the entries added so far; closing it needs a compensation sweep (complicated by the known gauge-drift accounting) or the generation/epoch guard, and rides with #15's identity-token work below. And (2026 dispatch review round 2) the `Reservation` guard covers the peer *id* only — the `cla.peers` address entry claimed before `publish` is unguarded, so cancelling `add_peer` mid-construction leaks it until the CLA unregisters; fold into the same epoch/identity work.

**`unregister_agent` name-reuse race (`src/routing/rib.rs`, review #15).** `unregister_agent` removes the agent from the name map, `await`s `agent.on_unregister()` (arbitrary duration — e.g. a gRPC proxy drain), then calls `remove_by_source(name)`. A new agent that registers under the same name during that await (the map slot is already free) has its freshly-installed routes deleted by the stale `remove_by_source`, which matches purely on the source string. Fix needs an identity/generation token so `remove_by_source` only removes routes owned by the unregistering agent instance, not a same-named successor.

## Bundle cancellation (dropped 2026-08-21, re-owned by grpc-api-v1)

`ServiceSink::cancel`/`ApplicationSink::cancel`, the wire `CancelRequest`/`CancelResponse` pair, and `Dispatcher::cancel_local_dispatch` were removed: the wire was the only consumer, and the implementation was status-blind (it would "cancel" a bundle mid-CLA-transfer, returning true while the peer might still receive it). If cancellation returns, it must be conditional on a still-cancellable status (CAS tombstone), and per-flow replacement/deletion-in-custody belongs to the FlowController seam (`policy_subsystem_redesign.md`). The oneof slot 7 / name "cancel" is reserved in service.proto.

## CLA transfer-outcome follow-ups (feat/cla-transfer-outcome review, 2026-08-07)

Items dispositioned as follow-up work during the branch review; the merge-gating fixes landed on the branch itself.

**Guard timer for transfers a CLA never resolves (ruled 2026-09-29).** The reaper defers `ForwardAckPending`, because an accepted transfer cannot be recalled, so a CLA that accepts a transfer and never reports its outcome holds the bundle until its peer is removed or it unregisters, not until the bundle's lifetime ends. Add a BPA-side guard timer: once a `ForwardAckPending` bundle's lifetime plus a grace period has passed with no outcome, time the transfer out as outcome-unknown and return it to `Waiting`, where the dispatch expiry checkpoint drops it as an attributable expiry. The swap must be status-conditioned like every other resolution, so a late outcome or the peer sweep racing the timer loses cleanly; `bpa/docs/design.md` "Deferred CLA Transfer Outcomes" describes the intended bound.

**LegacyIpn-form status-report sources need a black-box regression test (2026 dispatch review, finding 21 test debt).** The dispatch branch fixed the admin status-report park to key `WaitingForService` by the canonical registration EID (normalised through `NodeIds::local_service_eid`), so a report whose subject source arrived in `LegacyIpn` form no longer strands until expiry — but nothing pins the fix. Write it **black-box** in `bpa/tests/` — a status report for a bundle whose source EID is 2-element-ipn-form reaches the service registered under the canonical EID — so it pins the behaviour, not the normalisation seat. The scenario is permanent: egress deliberately re-encodes sources as `LegacyIpn` for 2-element-ipn peers, so downstream legacy nodes generate exactly these reports.

**Stored-but-uncommitted data cleanup wants a guard (2026 dispatch review, finding 30).** Every ingress failure path repeats the delete-the-saved-blob cleanup by hand. A `DataGuard` owning the saved name — sync `Drop` signalling a janitor task, defused when the name lands in the inserted record — deletes the five caller-side cleanup sites and makes a missed cleanup unrepresentable. Deferred with the `bpa.bundle.status` gauge's owning module ([`refactor_plan.md`](refactor_plan.md), queue tranche).

**Smaller notes, take-or-leave.** `TransferOutcome::Failed` carries no reason in the Rust trait while the wire deliberately does (`google.rpc.Status`), so Rust CLAs always send a constant placeholder — plumb a reason through when a CLA has one worth sending. `tcpclv4` has a small spawn-after-shutdown window (`forward` racing `on_unregister` can spawn a transmit task after `tasks.shutdown()` returned; tokio-util's `TaskTracker` allows spawning on a closed tracker) — the orphan resolves harmlessly, noted for the next time session-task lifetime guarantees matter. The two peer-removal sweeps run as two sequential statements and could be one `status IN (...)` UPDATE if removal rate ever matters. Gauge drift accumulates silently when a status write loses to a tombstone — a periodic recount fixes it if it ever shows; the structural fix (gauge moves fused into every `Store` transition behind a privatized `status`) is the queue tranche's status writer ([`refactor_plan.md`](refactor_plan.md)).

**Pipeline test de-flake pass.** Four `Known test-guide deviation` markers in `bpa/tests/pipeline.rs` — two ~100 ms quiesce sleeps, one quiet-window absence assert, and the `expect_no_offer` quiet-window helper (four call sites) — carry timing the test style guide forbids (synchronize on the event, not the clock). Replace each with an event-driven wait: a `#[cfg(test)]` parked-state hook for the ~100 ms quiesce sleeps, and a `shutdown().await` barrier (then assert-empty) for the quiet windows. These predate the parse refactor; batched here so the annotations reference a real item. `pipeline::throughput` belongs here too: it asserts more than 1000 bundles a second, a wall-clock gate the guide forbids, and fails under build load; mark it `#[ignore]` or move it to the criterion bench.

**The coverage report's inventory and a pipeline label are stale.** `test_coverage_report.md`'s unit-test inventory and fuzz table name moved files (`rib/`, `bundle/core.rs`, `dispatcher/local.rs`) and four tests that no longer exist, and `bpa/tests/pipeline.rs` labels its local-delivery test INT-BPA-03, which the component test plan assigns to fragment reassembly. A small follow-up off `main` fixes both.

**Tombstone-on-reject suppression (duplicate invalid bundles may re-report).** A duplicate *invalid* bundle (rejected before the metadata insert) isn't deduplicated — a replay re-parses and may re-report. Accepted for now: RFC 9171 status reports are off-by-default debugging aids, not acks, so a duplicate report is harmless. Suppressing via a tombstone-on-reject is deliberately deferred because the future compressed-status-report / custody work inverts the requirement (a resend then means "report lost, please re-report"), so that design must own the semantics. Referenced from the duplicate-check comment in `dispatcher/ingress.rs`.

## Sink drop-cleanup via reconciler queue (replace spawn-from-Drop)

All three Sink `Drop` impls (`src/cla/registry.rs`, `src/services/registry.rs`, `src/routing/agent/sink.rs`) enqueue their async unregistration by spawning a task from sync `Drop`. This is already non-blocking, but spawn-from-Drop allocates a task per drop, gets exactly-once semantics only from ad-hoc guards, and can silently not run when the pool is already cancelled during shutdown — only the routing sink checks `is_cancelled`.

The tidy-up: `Drop` pushes a component identity onto an unbounded channel drained by one long-lived reconciler per registry — `Drop` stays plain sync code, delivery is exactly-once (an explicit `unregister()` leaves a stale id the reconciler no-ops on), and shutdown ordering becomes explicit (drain the reconciler before cancelling the pool). The work is applying the pattern uniformly across `cla::Sink`, `ServiceSink`, and `RoutingSink`. The CLA-only prototype on `refactor/sink-lifecycle` (`4d24e3f8`, `drop_tx` + `signal_dropped`) is prior art for this shape only; nothing else on that branch is carried forward. Design rationale in [`streaming_pipeline_design.md`](streaming_pipeline_design.md) §5.1.2; the channel-context alternative (`refactor/sink-to-context`) was considered and rejected — the Sink trait shape stays.

Ownership does not change: the component keeps owning its Sink, and the per-call `Weak::upgrade()` stays the liveness gate. Inverting it (a component-held `Arc<dyn Sink>`, a registry-held `Weak`, an `alive` flag for call gating) was considered and rejected.

## feat/cla-acceptance review ledger (2026-09-11)

**file-cla startup sweep bulk-fills the unbounded path channel (F-14, pre-existing amplified).** The sweep enumerates the whole outbox into the pre-existing `flume::unbounded` path channel far faster than the serial forwarder drains it, so restart memory grows O(N) with outbox size on the constrained/32-bit targets Hardy supports. The sweep loop is already await-shaped, so a bounded channel paces at no throughput cost; note that a bounded channel makes the watcher event loop's send block into the debouncer's channel — acceptable, but a deliberate coupling. Fixed means: starting against N pre-existing files holds O(1) queued paths, paced by dispatch completion.

**Poison rows are re-polled forever (round-2 N-06, pre-existing policy).** A stored row whose status or bundle blob no longer decodes is `warn!`-ed and skipped by every `poll_pending` pass — sqlite's garbage-adjacency and garbage-bundle arms, and postgres's `decode_bundle → None` — but never disposed, so it re-warns each poll and consumes a slot in the `LIMIT`; a run of poison rows at the front of the `received_at` order starves the drain. Reachable only through corruption or a future encoding change (the migrations clear the rows current code could create). A disposal/quarantine policy for undecodable rows is a cross-backend design decision; take it once, for all backends and both decode failure classes.

## refactor/filters review triage (2026-09-09)

Open items from the `refactor/filters` deep review routed to this ledger rather than the branch; the dispatcher items predate the branch. Its queue-tranche and streaming-leg items are in [`refactor_plan.md`](refactor_plan.md).

**Dispatcher hardening group (F-01, F-02, F-15, F-16).** Four faces of the same missing discipline — pipeline consumers running before recovery, and resolutions acting on unclaimed bundles. F-01: the channel storage poller and `run_dispatch_queue` consumer start at `build()`, before `Bpa::start`'s awaited recovery, so with persistent metadata `DispatchPending` rows are claimed and routed against a not-yet-populated RIB while `recover()` walks the store. The dispatcher owns its deferred start mirroring the registries' park-pending-drain-in-`start()` pattern (`Dispatcher::new` parks the consumer receiver, a new `Dispatcher::start` takes it once and spawns the consumer, called from `Bpa::start` after the awaited store start). F-02: status-report resolution in `admin.rs` fires up to four `on_status_notify` calls and an unconditional delete without claiming — `tombstone_if` before notifying, skip on a lost race. F-15: `poll_waiting`'s consumer processes unclaimed `Waiting` bundles (its sibling `poll_service_waiting` claims first) — CAS `Waiting → Dispatching` before `process_bundle`. F-16: the two `Drop(None)` resolutions (`process_bundle`'s route-drop arm and `resolve_offer`'s `Dropped(bundle, None)`) delete unconditionally where `drop_bundle`'s own doc says every drop is claimed — one private `silent_drop_bundle` helper beside `drop_bundle` (`tombstone_if` then `delete_bundle`), both sites routed through it. F-15/F-16 are interim mechanical patches: the claim ritual's structural owner is the queue tranche's `lifecycle::transitions` status writer ([`refactor_plan.md`](refactor_plan.md)).

**Configured CLA/service activation failure degrades silently (F-17).** A pre-start duplicate `register_cla` makes a configured CLA silently never activate while every health signal says up (`error!` then continue, where baseline `build()` propagated with `?`). Replace both log-and-continue arms with `trace_expect`, the crate's fail-stop convention — the dispatch review round 2 recorded the downgrade as "acceptable", so this is a deliberate revisit, and the CHANGELOG must note that activation failure aborts.

**CLA activation order is hash order, not configuration order (F-18).** `ClaRegistry::start`'s doc promises configuration order but the builder keeps `clas` in a `HashMap` and collects it into the pending list in hash order; `ServiceRegistryBuilder` already uses an order-preserving `Vec`. Switch to `clas: Vec<(String, PendingCla)>` with a linear-scan duplicate check in `insert`.

**Queues-close-before-RIB-withdrawal ordering hand-duplicated (F-32).** `unregister_cla` and `remove_peer` carry byte-identical close-then-withdraw blocks (the "(mirrors remove_peer)" comment is the tell); a divergent future edit reintroduces the sweep-before-close bug on one path only. Extract `retire_peer(&self, cla, node_ids, peer_id)` called from both.

**delivery_queue.rs synchronizes on a sleep-poll loop (F-08).** `await_status` polls on a 50 ms sleep, violating the deterministic-test rule (the two pipeline.rs sleep deviations are acknowledged debt, not licence for a third). Fix shape per the sibling suites' delegating-wrapper pattern (`dispatch_queue.rs`'s `InjectingStorage`): a `SignallingStorage` whose `swap_status` and `reset_service_queue` send `()` after delegating — the bulk `reset_service_queue` matters, it writes the awaited `WaitingForService` transition without ever calling `swap_status` — and an event-driven read-then-`recv_async` loop under a regression-bounding timeout. Belongs with the pipeline de-flake pass above.

**htb_policy.rs/tbf_policy.rs are never-compiled orphans (OF-07).** Their premise (runtime-registered policy modules) is gone; delete both files and the four commented-out `mod` lines — [`policy_subsystem_redesign.md`](policy_subsystem_redesign.md) is the live home for scheduler designs.

**`BpaBuilder::{cla, service}` panic on duplicate names via `.expect` although `build()` returns `Result` (OF-08).** Reachable from bpa-server YAML; the branch's own freeze-in-build pattern is the template for returning the error instead.

**`Bpa::start(bool)` is an opaque flag (OF-09).** Delete the parameter: `start()` always soft-recovers, and hard repair becomes a separate `repair()` entry point. ~65 call sites, so it rides a release boundary. Target shape: `async fn start(&self) -> Result<()>` is phase-ordered — soft recovery to completion, then subsystem start (reaper, RIB), then the registration doors open — and a CLA, service, or routing-agent registration before that returns a typed `NotStarted` error, so a recycled peer id can never observe a dead peer's rows. `async fn repair(&self) -> Result<RepairReport>` is the only recovery path allowed to delete data, runnable instead of or before `start()`; `RepairReport` counts `confirmed`, `junk`, `duplicates`, `orphans` and `data_lost`, with a one-line `Display` summary. `start` and `repair` are mutually exclusive one-shot passes (`AlreadyStarted`), and `shutdown` closes the registration doors first, so a racing registration gets a typed error rather than an emptied registry. Hold the lifecycle state as an enum, and name the methods symmetrically.

**Storage recovery runs only with `--recover-store`, and the user docs say otherwise.** `docs/user-docs/recovery/index.md` says recovery runs on every startup, but `bpa-server` passes `-r`/`--recover-store` to `Bpa::start`, and without it the metadata/data reconciliation is skipped. One consequence is unledgered elsewhere: a bundle in `ForwardAckPending` or `DeliveryAckPending` when the node stopped is never reset, and the reaper defers ack-pending records, so without `-r` nothing ever reaps it. Correct the docs, and reap or reset ack-pending records at every start (OF-09's always-soft-recover `start()` would).

**`Dispatcher::key_provider()` method shadows the `key_provider` field while returning a different thing (OF-10).** Rename to `key_source_fn`; three private call sites.

**`Cla::peers` map value is an anonymous `(Vec<NodeId>, u32)` tuple across five destructure sites (OF-11).** Private `struct PeerEntry { node_ids, peer_id }`.

## Ingress diagnostics name no peer

Refusals and disposals at the CLA ingress door log at `debug!` without the bundle id, the CLA or the peer, and the ingress spans carry no fields, so an operator cannot tell which peer sends oversized, truncated or integrity-failing bundles. An operational logging pass across the doors: the CLA and peer as fields on the receive span, and `TooLarge`, `Truncated` and `IntegrityFailed` at `warn!` with the bundle id when it is known.

## `no_std` support is blocked by `metrics`

The bpa library is written for `no_std` with a heap allocator, but it depends unconditionally on the `metrics` crate (`bpa/Cargo.toml`), which requires `std`, so the crate does not build `no_std` today (`bpa/docs/design.md`, Dependencies). Put the metric call sites behind a feature, or route them through a `no_std`-capable facade, so the core builds for the embedded targets the workspace's `no_std` crates (cbor, bpv7, bpa) are meant to reach.

## AdminRecord registry: designed, not built

The filter design's two-tier extension model lists an AdminRecord registry beside the CLA, service, and routing-agent registries: a registry and sink keyed by administrative record type, with record-type-claim authorisation at the gRPC layer, as the admin path's extension surface. It is designed in the separate DTN NOC repository's `acme_design.md` §4 and not built; admin records addressed to this node terminate in the Admin block's fixed handling. Build it, or retire the references in `filter_subsystem_design.md`, when the admin-path work is picked up.

## Storage encryption at rest is the backend's, and undocumented

Bundles are stored as received — plaintext where they arrived or were originated in plaintext, including those this node will secure as a BPSec source — and the metadata carries decoded per-hop values in plaintext even where the block is BCB-protected (`streaming_pipeline_design.md` §5.5). That is within BPSec's model, which leaves the nodes' own storage out of scope (RFC 9172 §1), but a backend outside the node's trust boundary (S3, a database on another host, removable media) needs encryption at rest from the backend itself. [`docs/user-docs/configuration/storage.md`](../../docs/user-docs/configuration/storage.md) does not say so; it should.

## External #712 review ledger (2026-09-30)

Items the external reviews of the filter subsystem (2026-09-30, and its 2026-10-01 second pass), or their verification, found that no branch fixes.

**No test observes the filter counters.** `bpa.filter.filtered` and `bpa.filter.modified` are incremented as documented, but the bpa tests install no metrics recorder, so nothing pins them. A `metrics_util::debugging::DebuggingRecorder` (a dev-dependency) around the engine's inline tests would assert each, by hook.

**No block-count cap.** The in-memory `Block` map costs ~774 B per wire block, so 262,146 tiny extension blocks in a 3.8 MB bundle take ~53× the wire size in heap before any filter runs, and the work, though linear, is synchronous (2.5 s measured, inside an async task with no yield point). Each editing Rewriter adds a full wire-form copy per attempt — a factor streamed egress shrinks to the header region (`streaming_pipeline_design.md` Phase B). A configurable maximum block count at the pre-drain gate, beside `max_bundle_size` and the RFC 9171 gates, would cap both; whether a cap conflicts with any conformance requirement is unchecked.

**The post-registration poll can re-attempt a fresh park.** `register_service` spawns `poll_service_waiting` asynchronously; landing after a bundle parks `WaitingForService`, it re-dispatches the bundle at once — one redundant attempt (failing the same way if the failure is deterministic), and a non-determinism tests must synchronise around (`bpa/tests/filter_dispositions.rs` waits on the park swap itself). The RIB's Waiting poller skips stale wakes since `Rib::request_poll`; the service poll has no equivalent.
