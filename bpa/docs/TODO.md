## Fragmentation and ADU reassembly

All fragmentation-shaped work — the four sections below, fragment-carried payload BIB deferral, streaming-shaped reassembly — is gathered in [`fixing_fragmentation.md`](fixing_fragmentation.md), and the decision it deferred is settled in [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) (2026-09-07, not yet implemented). The sections here record defects in the current code until that redesign closes them; where a fix direction below differs from the redesign, the redesign governs.

### Concurrent final fragments both park NotReady (2026 dispatch review, finding 6)

`poll_fragments` only sees siblings already parked in `AduFragment` status, so when the last two fragments of an ADU are processed concurrently each polls while the other is still `Dispatching`, both conclude the set is incomplete, both park, and nothing ever re-triggers reassembly (reproduced with a delegating metadata store holding the two polls open across each other). Deliberately not patched in place: the fix would land in `poll_fragments`/`reassemble`, which the settled redesign in [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) deletes wholesale — its ledger-driven completion has no park-vs-poll window. Another motivating instance of the shape problem that redesign exists to fix.

### RFC 9171 §5.9 material-extents reassembly (overlapping fragments)

#### Background

`Store::reassemble()` (`src/storage/adu_reassembly.rs`) requires the received fragments to tile `[0, total_adu_length)` exactly: contiguous, non-overlapping and complete. Overlapping fragment sets are rejected and the fragments dropped as `ReassemblyResult::Failed`.

RFC 9171 §5.9 is more permissive: overlapping fragments are legal on the wire (e.g. the same bundle refragmented differently on divergent paths), and a conformant reassembler computes each arriving fragment's "material extents" — the byte ranges not already covered by previously received fragments — completing when the material extents concatenate to the full ADU. First-received bytes win; overlap is trimmed, not rejected.

Hardy has never accepted overlap: the pre-tiling-check code also failed overlapping sets (payload-length sum ≠ total), except for the length-sum coincidence that silently delivered a corrupt ADU (2026-07-08 review findings #1/#4). The tiling check makes rejection deterministic and safe, but Hardy remains non-conformant for legitimately overlapping fragment sets.

#### Fix

Settled in [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) (not yet implemented): the per-ADU `Coverage` ledger merges overlapping ranges and replaces `FragmentSet`/`poll_fragments`, so overlap stops being a failure mode.

### Deletion status reports on reassembly failure

When reassembly fails (`ReassemblyResult::Failed`), `Store::adu_reassemble` deletes the held fragments directly against storage (`delete_data` + `tombstone_metadata`) and the dispatcher's `Failed` arm returns without action — no deletion status reports are generated. RFC 9171 §5.10 says a deletion status report SHOULD be generated per deleted bundle (each fragment is its own bundle, reported to its own report-to EID with its fragment offset/length) when the report flag is set and reporting is enabled.

Not patched in place: [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) dissolves the case — fragments are never held as bundle records, failures shrink to door-side drops of single arrivals, and an expired partial reports its own deletion through the reaper.

### Offset-keyed fragment set drops the trigger's cleanup on a hostile collision (review round 3)

`FragmentSet.adus` is keyed by fragment offset, so a hostile sibling sharing the trigger fragment's source/timestamp/offset but a different `total_adu_length` (a distinct bundle id, so nothing deduplicates it) overwrites the trigger's seeded entry. The trigger then never reaches the cleanup loop — its metadata is never tombstoned and its `Dispatching` gauge never decremented — while the reassembly fails the length check and drops without cleanup. Not patched in place: closed structurally by [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) — fragments are never bundle records, and a sibling with a mismatched total drops at the door's consistency check under the ADU's merge permit.

### ADU reassembly materialises the whole ADU with no size bound (silent too-large death)

`Store::reassemble` (`src/storage/adu_reassembly.rs`) allocates the entire ADU in RAM (`vec![0; adu_len]`) sized from the wire-declared `total_adu_length`, which is checked only for `usize` addressability, never against `max_bundle_size`. A large declared total can exhaust memory, and a non-addressable one fails reassembly with only a `debug!` — no report either way. Not patched in place: [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) bounds memory by `max_bundle_size` behind the streaming merge seams.

### A restart can strand a complete fragment set (restart orphan)

Restart recovery only re-counts `AduFragment` rows (`src/dispatcher/restart.rs`); completion is checked when a new sibling arrives, so a set whose last fragment was parked just before a crash, with reassembly not yet run, is never completed and sits until its lifetime expires. Not patched in place: [`fragment_reassembly_redesign.md`](fragment_reassembly_redesign.md) gives restart a reassembly-aware arm that completes a finished ledger at recovery.

## Ingress status-report conformance (invalid bundles, duplicates, expired arrivals)

RFC 9171 pins the reception report's reason code: §5.6 Step 2 prescribes "No additional information" (Step 4's "Block unsupported" is the only other reception-report reason), and a parse/CRC failure routes through the §5.10 Bundle Deletion procedure, whose deletion report is what cites "Block unintelligible". Every ingress reject with a recoverable bundle id — the keyed header pass, the payload drain (a `ValidationFailure` (`src/dispatcher/validate.rs`) carries its reason via `reason_code()`), and the pre-drain gates (lifetime/hop, RFC 9171 validity, Ingress chain drop) — emits the conforming §5.6/§5.10 reports as a **single** status report bundle: one §6.1.1 record asserts both reception and deletion (the coalescing ION also performs), each assertion gated on its own request flag, the record's reason citing the deletion. The two reportless cases are deliberate and lawful: a refused transfer (truncation, size cap) is never reported, and a bundle whose primary block never parsed has no id to report — the §4.1 MAY-discard, outside the reception state machine. The pair is the §5.6-Step-3 → §5.10 normative shape; of the major implementations (ION, HDTN, µD3TN, DTNME, ESA-BP, cFS BPNode), only DTNME reports these failures at all (the same pair) — the rest drop them silently.

§5.6 Step 4's block-flag-alone trigger is honoured: an unprocessable block flagged `report_on_failure` forces the reception report (`ReceptionReport::Demanded`) even when the bundle requests no reception reporting — the trigger ION, µD3TN, and DTNME also implement, with ION and DTNME sharing our "Block unsupported" reason (µD3TN says "Block unintelligible"; the RFC leaves "cannot process" undefined, so that split is implementation choice). The §4.2.4 admin-record/anonymous carve-outs are rejected at parse, a report whose report-to is the null endpoint is suppressed at the dispatch seam, and the §5.1.1 failure-drop facts stay bundle-flag-gated (RFC 9172 keeps that reporting at requested-MAY level).

Duplicates: RFC 9171 specifies no duplicate-bundle processing at all (the word does not appear), so §5.6 read literally reports reception on every arrival, including replays. Decision: duplicates SHOULD get a reception report — a sender may be intentionally repeating a bundle probing for status-report ACKs. Adopted: ingress reports reception before the duplicate check, both at the gate's early duplicate probe and after the spool.

Expired arrivals are the deliberate exception, and a named SHOULD-level deviation: §5.5 makes deletion of an expired bundle a MUST (via §5.10, whose deletion report is SHOULD when flagged), and we instead treat a bundle that arrives already expired as if it never arrived — no reception report, no deletion report, no metadata entry — rather than amplifying already-dead traffic into report bundles. The silence rides §5.1's blanket discretion ("the decision on whether or not to generate a requested status report is left to the discretion of the BPA"); it is also the field-minority position — ION, µD3TN, DTNME, and ESA-BP all accept-then-report expired arrivals, only HDTN doesn't check. The pre-drain early gate implements this silence for the lifetime case (hop-exhaustion still emits the combined reception + deletion report). Bundles that expire *in custody* are unaffected: the dispatch, forward, and deliver expiry checkpoints and the reaper resolve them through `drop_bundle`, which generates §5.10 deletion reports citing "Lifetime expired".

## Storage backend metrics (common + bespoke)

An audit (2026-07-10, while defaulting bpa-server to sqlite/localdisk) found the persistent storage backends emit no metrics at all — none of sqlite-storage, localdisk-storage, postgres-storage, or s3-storage even depends on the `metrics` crate. Their only observability is the `instrument`-feature tracing spans. Production nodes on the new persistent defaults therefore have no storage operation counts, error counters, or latencies; only the in-memory backends carry store-level metrics today (`bpa.mem_store.*`, `bpa.mem_metadata.*`, documented in `docs/user-docs/operations/observability.md`).

Two layers of work:

**Common metrics in the `Store` wrapper** (`src/storage/store.rs`) — every operation flows through it, so instrumenting there covers all backends uniformly and keeps the backend crates metrics-free for the common cases. Proposed: `bpa.storage.ops` (counter), `bpa.storage.errors` (counter), and `bpa.storage.op.duration` (histogram), labelled `store = metadata|bundle` and `op = load|save|swap|delete|insert|tombstone|get|poll` (`swap` for the status-conditioned `swap_status` writes) (the `poll_*` variants folded into one label value to bound cardinality).

**Bespoke per-backend metrics** where only the backend knows the truth: sqlite database/WAL file size, localdisk store-directory bytes and file count, postgres connection-pool stats, s3 request retries. These need either per-crate `metrics` emission or a `stats()`-style trait extension sampled periodically — a trait-surface decision to make when the work is picked up.

Documentation: a new backend-agnostic "Storage Operations" table in `docs/user-docs/operations/observability.md`, plus per-backend tables as bespoke metrics land.

## Bufferless bundle and ADU lengths (streaming prerequisite)

The streaming end-state removes the loaded whole buffer that `total_len = data.len()` measures at the delivery and forward doors, but both lengths are derivable from the persisted block index alone. `Bundle::encoded_len()` (`bpv7/src/bundle.rs`) names the whole-bundle derivation with its RFC anchors — the payload block MUST be last and a bundle SHALL be an indefinite-length CBOR array (both RFC 9171 §4.1), so the payload's bundle-absolute `extent.end` plus the one break byte is the encoded length. Because canonical CBOR gives the payload a definite-length head, the value is known at header-parse time, before the payload arrives — the declared-size admission gates use it today (ingress `parse_headers`, the raw originate door), and it serves egress framing ([`streaming_pipeline_design.md`](streaming_pipeline_design.md) §6.2's "original bundle size") and any announce-style wire's `bundle_size`, none of which a commit-measured metadata field could serve. The ADU length needs no accessor at all: the payload block's `data` range is an interior range with no break-byte dependency.

Remaining work when the consumers land:

**Spool-commit cross-check.** The spool counts the bytes it writes; a commit-time `debug_assert!(counted == encoded_len())` catches index-vs-bytes drift without minting a second source of truth in metadata.

**Pin the ADU-length definition at the Application door.** The announced size is the *stored* payload block data length, pre-BPSec-decryption — AES-GCM preserves plaintext length so the two coincide today, but a length-changing confidentiality suite would make the distinction real. Post-reassembly bundles re-derive both lengths from the reassembled bundle's index.

## Negotiated size-cap deferrals (negotiated-max-bundle-size review, 2026-09-10)

**Default flips to no-policy when streaming lands.** `max_bundle_size` is admission policy carried as `Option<NonZeroU64>` end-to-end, but an unset builder cap still takes the private 64 MiB default at dispatcher construction, because ingress accumulates whole bundles in memory and "no policy" would mean unbounded RAM growth per hostile stream. The streaming pipeline enforces the bound in the u64 domain against spooled storage, at which point the default becomes `None` — a non-breaking change, the default being private. The dispatcher's `max_bundle_size_mem` seam (and its addressable-bound clamp) is deleted by the same work.

**Central egress enforcement of the declared CLA limit.** The registration declaration only shrinks the effective cap echoed back to the CLA; egress does not consult it, so a CLA with a genuine transport limit below the BPA cap is still offered larger bundles and must refuse each per-bundle (`proto/cla.proto` documents this contract). Enforcing it centrally first requires splitting the two semantics the field conflates: a receive MRU folded into advertising (tcpclv4's declaration — RFC 9174 sends are bounded by the peer's session MRU, unknowable at registration) versus a transport limit the BPA must respect when offering.

**No terminal disposition for a deterministic per-bundle forward error.** A bundle whose encapsulated outer exceeds bibe's negotiated cap parks retriable in `Waiting` after its deterministic `PayloadTooLarge`, so every routing event re-runs the full egress pipeline into the same rejection for the bundle's whole lifetime. The dispatcher needs a terminal outcome (or back-off) for forward errors that cannot resolve differently on retry. Filter chain failures have the same shape (external #712 review L-11, 2026-09-30): stored bytes that fail the engine's decode park the bundle `WaitingForService` at Deliver, re-attempted into the same failure on every re-registration until expiry. At Egress the engine's own decode arm is unreachable from storage — `update_extension_blocks` decodes the stored bytes first and parks `Waiting` itself, with the same retry shape — so the engine's Egress error arm is defensive only.

## Remove `total_len` from the streamed ADU originate (ruled 2026-09-04)

`ApplicationSink::send_streamed` / `Dispatcher::originate_streamed` carry a declared `total_len` only because the payload block's definite-length byte-string head sits in the wire prefix `Builder::build_stream` emits before the first payload byte — the caller must know the length before the stream starts, which excludes producers that genuinely don't (a compressor, a live capture). We probably want to remove the parameter: spool the payload unframed and record a marker in `BundleMetadata` — the `to_remove` deferred-edit family — that the stored form's payload length is unresolved, fixed up at egress where the per-attempt resident rewrite already runs. Consequences to design through before starting: the stored bytes are not a canonical bundle until fixed, so every consumer of stored bytes (delivery's Application and raw-`Service` paths, restart's reconcile parse) must honour the marker or the fix-up must happen once at first read; the declared-size admission gate loses its pre-drain seat for these sends (the bound falls back to the spool's byte count); and the `BuiltReceiver` length-violation contract (`PayloadTooLarge`/`PayloadUnderrun`) dissolves — the stream defines the length. The parameter stays until then; callers that cannot declare buffer the payload and use `send`.

## Registration/routing concurrency races (whole-codebase review 2026-07-08, #14/#15)

Two non-atomic await sequences in the CLA/routing registries can race and leave stranded or wrongly-deleted state. Neither is data-loss or wire-corruption, and both need specific concurrent timing, so they were deferred past v0.2.0.

**`add_peer` vs concurrent removal (`src/cla/registry.rs`, review #14) — residual slivers.** `add_peer` claims the address first, builds the peer complete before publishing (`PeerTable::reserve`/`Reservation::publish`), and re-checks its claim after the construction awaits, so a removal that wins the claim withdraws the peer. Two slivers remain. A removal interleaving the `rib.add_forward` loop (after the re-check) can still strand the entries added so far; closing it needs a compensation sweep (complicated by the known gauge-drift accounting) or the generation/epoch guard, and rides with #15's identity-token work below. And (2026 dispatch review round 2) the `Reservation` guard covers the peer *id* only — the `cla.peers` address entry claimed before `publish` is unguarded, so cancelling `add_peer` mid-construction leaks it until the CLA unregisters; fold into the same epoch/identity work.

**`unregister_agent` name-reuse race (`src/routing/rib.rs`, review #15).** `unregister_agent` removes the agent from the name map, `await`s `agent.on_unregister()` (arbitrary duration — e.g. a gRPC proxy drain), then calls `remove_by_source(name)`. A new agent that registers under the same name during that await (the map slot is already free) has its freshly-installed routes deleted by the stale `remove_by_source`, which matches purely on the source string. Fix needs an identity/generation token so `remove_by_source` only removes routes owned by the unregistering agent instance, not a same-named successor.

`ServiceSink::cancel`/`ApplicationSink::cancel`, the wire `CancelRequest`/`CancelResponse` pair, and `Dispatcher::cancel_local_dispatch` were removed: the wire was the only consumer, and the implementation was status-blind (it would "cancel" a bundle mid-CLA-transfer, returning true while the peer might still receive it). If cancellation returns, it must be conditional on a still-cancellable status (CAS tombstone), and per-flow replacement/deletion-in-custody belongs to the FlowController seam (`policy_subsystem_redesign.md`). The oneof slot 7 / name "cancel" is reserved in service.proto.

## CLA transfer-outcome follow-ups (feat/cla-transfer-outcome review, 2026-08-07)

Items dispositioned as follow-up work during the branch review; the merge-gating fixes landed on the branch itself.

**Guard timer for transfers a CLA never resolves (ruled 2026-09-29).** The reaper defers `ForwardAckPending`, because an accepted transfer cannot be recalled, so a CLA that accepts a transfer and never reports its outcome holds the bundle until its peer is removed or it unregisters, not until the bundle's lifetime ends. Add a BPA-side guard timer: once a `ForwardAckPending` bundle's lifetime plus a grace period has passed with no outcome, time the transfer out as outcome-unknown and return it to `Waiting`, where the dispatch expiry checkpoint drops it as an attributable expiry. The swap must be status-conditioned like every other resolution, so a late outcome or the peer sweep racing the timer loses cleanly; `bpa/docs/design.md` "Deferred CLA Transfer Outcomes" describes the intended bound.

**Backend conformance tests (D3).** The shared `tests/storage` harness (`metadata_suite.rs`, run against memory, sqlite, and postgres) pins only a winning `swap_status` and an unconditional `tombstone`; the conditional semantics are still hand-rolled per backend (`metadata_mem.rs`, sqlite's `test_swap_status_is_conditional`/`test_tombstone_if_is_conditional`) and postgres has none. Add META cases pinning a lost `swap_status` from a stale snapshot, `tombstone_if` win and loss, and `swap_status` against a tombstone (quietly `false`, never resurrecting), then retire the per-backend copies.

**Redundant tombstone on the Completed path (P3).** After a successful `tombstone_if`, `delete_bundle` issues a second, unconditional `tombstone` — a wasted UPDATE per completed transfer on the SQL backends. Needs a data-only delete variant (or flag) so the resolution's own tombstone stands.

**Subsumed by the `requeue()` redesign (P2).** `transfer_outcome`'s `Failed` arm pre-swaps `ForwardAckPending` → `Dispatching` and the dispatch channel's send then CASes `Dispatching` → `DispatchPending`; letting the send CAS directly from the `ForwardAckPending` snapshot saves one write per failed transfer with identical race semantics. Deliberately parked: the `requeue()` primitive in `queue_architecture.md` makes this fall out for free — do not implement separately.

**sqlite status codec: port postgres's `StatusFields` shape (review round 3, R3-3).** sqlite's status codec is a positional tuple — `from_status -> (i64, Option<i64>, Option<i64>, Option<String>)` / `to_status(code, param1, param2, param3)` — where peer and queue ids both travel as anonymous `param1`/`param2`; postgres solved the identical problem with a named `StatusFields` struct. Port that shape to sqlite when the D3 conformance suite lands. The suite should also pin the two real cross-backend divergences the codec hides: postgres narrows peer ids to `i32` (a typed error above 2^31) while sqlite stores them losslessly as `i64`, and sqlite's `from_status` stores the ADU-fragment `sequence_number()` via `as i64` (a value above `i64::MAX` is silently reinterpreted negative and round-trips bit-exact through the mirror cast on read, where postgres refuses it with a typed error).

**sqlite temporal columns → INTEGER epoch milliseconds (2026-09-09, from the dispatch review round-2 expiry-ordering question).** `expiry` and `received_at` are TEXT columns holding rusqlite's `OffsetDateTime` encoding, and both are ordering keys: `poll_expiry` keysets on `(expiry, rowid)` and `poll_pending` pages in `received_at` order — so chronological correctness rides on the lexicographic order of an encoding rusqlite owns. Write-site UTC normalization (see `insert`) holds the invariant today, but a rusqlite encoding change (their parser already carries a "legacy format" branch from the last one) would interleave two string formats in one table and silently corrupt the order. Fix: store both columns as INTEGER Unix-epoch **milliseconds**. Milliseconds are exact for wire-derived values (DTN creation time and lifetime are both ms) and safe at the saturated top end — a `Duration::MAX` lifetime caps expiry at year 9999, which fits `i64` at ms (~2.5×10¹⁴) and µs, but overflows at ns; never nanoseconds. Sub-ms components from the monotonic `CreationTimestamp` nudge truncate to ties, broken by `rowid` exactly as today (the reaper needs approximately-ascending only). The keyset queries keep their shape with integer binds; the index shrinks from ~32-byte strings to 8-byte ints; sqlite reaches parity with postgres's native `TIMESTAMPTZ` semantics; and the UTC-normalization crutch and its comments retire. Backfill is pure SQL — `CAST(ROUND((julianday(expiry) - 2440587.5) * 86400000) AS INTEGER)` (sqlite's date functions parse the rusqlite format; f64 julianday precision ≈ 50 µs at modern dates, fine at ms) — or moot if the upgrade wipes/purges rows under the established metadata-store upgrade precedent. Ride with the StatusFields/D3 codec pass above: same file, one coordinated schema migration.

**`PeerId` newtype (review round 3, R3-4).** bpa has ~26 bare `peer: u32` sites, roughly half from the transfer-outcome branch (`ForwardAckPending { peer }`, `owns_peer`, `reset_peer_ack_pending`, the outcome plumbing). The hazard is concrete: `ForwardPending { peer, queue }` carries two u32-domain identifiers and the sqlite codec flattens both into adjacent positional `i64`s. A `PeerId(u32)` newtype (with `QueueId` as its natural sibling) makes cross-assignment unrepresentable end-to-end and gives the postgres `i32` narrowing a single home.

**`next_hop` payload inside the queue-key type (filters review OF-03; same premise as R3-4 above).** The `Eid::Null` placeholder, `BundleStatus::same_queue`, the `send_to` debug_assert, and three independently implemented backend queue disciplines all exist because `BundleStatus` doubles as queue identity and per-bundle payload. Owned by the queue tranche ([`queue_architecture.md`](queue_architecture.md)). The poll half is one typed row selector shared by `MetadataStorage::poll(&StatusSelector, stream, limit)` and `MetadataStorage::sweep(&StatusSelector, to) -> u64`, superseding `poll_pending`, `poll_waiting`, `poll_service_waiting`, `poll_expiry` and the three `reset_*` sweeps. `StatusSelector` is exhaustive, so a new arm is a compile error in every backend until it handles it; each arm is a WHERE clause that never matches a tombstone, and `sweep` refuses the scan-only arms (`UnsweepableSelector`). Arms: `Exact(BundleStatus)`, in ascending `received_at`; `ForwardQueue { peer }`, that peer's `ForwardPending` across every queue (the route-change preemption reset, leaving `ForwardAckPending` transfers alone); `PeerQueues { peer }`, its `ForwardPending` plus `ForwardAckPending` (swept when the adjacency goes); `ServiceQueues { service }`, `DeliverPending` plus `DeliveryAckPending`; `All`, the soft-recovery scan; `Expired { now, exclude_handoff }`, the reaper's expiry-ordered refill on the caller's clock, optionally excluding the hand-off statuses. The egress lane poll needs a per-lane arm. The typed-send half is a named edge `enqueue_forward(store, bundle, peer, lane)` growing `next_hop` as an edge parameter. Do not mint a `QueueKey` enum or a `ForwardSender` type: they would be second names for `StatusSelector` and the named edges. Until then, the postgres `poll_pending` queue-identity comment is the interim guard.

**The `bpa.bundle.status` gauge wants one owning module (2026 dispatch review, finding 29).** The gauge is hand-balanced at ~20 raw metric sites across seven files, and drift accumulates silently when a status write loses a race (see the note below). One owning module in `otel_metrics.rs` with `admit`/`transition`/`remove` verbs — the metric name and label vocabulary private to it — turns the balance into a local property. Deferred from the dispatch review as cross-cutting churn outside that branch's correctness story.

**LegacyIpn-form status-report sources need a black-box regression test (2026 dispatch review, finding 21 test debt).** The dispatch branch fixed the admin status-report park to key `WaitingForService` by the canonical registration EID (normalised through `NodeIds::local_service_eid`), so a report whose subject source arrived in `LegacyIpn` form no longer strands until expiry — but nothing pins the fix. Write it **black-box** in `bpa/tests/` — a status report for a bundle whose source EID is 2-element-ipn-form reaches the service registered under the canonical EID — so it pins the behaviour, not the normalisation seat. The scenario is permanent: egress deliberately re-encodes sources as `LegacyIpn` for 2-element-ipn peers, so downstream legacy nodes generate exactly these reports.

**Stored-but-uncommitted data cleanup wants a guard (2026 dispatch review, finding 30).** Every ingress failure path repeats the delete-the-saved-blob cleanup by hand. A `DataGuard` owning the saved name — sync `Drop` signalling a janitor task, defused when the name lands in the inserted record — deletes the five caller-side cleanup sites and makes a missed cleanup unrepresentable. ## Sink drop-cleanup via reconciler queue (replace spawn-from-Drop)

All three Sink `Drop` impls (`src/cla/registry.rs`, `src/services/registry.rs`, `src/routing/agent/sink.rs`) enqueue their async unregistration by spawning a task from sync `Drop`. This is already non-blocking, but spawn-from-Drop allocates a task per drop, gets exactly-once semantics only from ad-hoc guards, and can silently not run when the pool is already cancelled during shutdown — only the routing sink checks `is_cancelled`.

The tidy-up: `Drop` pushes a component identity onto an unbounded channel drained by one long-lived reconciler per registry — `Drop` stays plain sync code, delivery is exactly-once (an explicit `unregister()` leaves a stale id the reconciler no-ops on), and shutdown ordering becomes explicit (drain the reconciler before cancelling the pool). The work is applying the pattern uniformly across `cla::Sink`, `ServiceSink`, and `RoutingSink`. The CLA-only prototype on `refactor/sink-lifecycle` (`4d24e3f8`, `drop_tx` + `signal_dropped`) is prior art for this shape only; nothing else on that branch is carried forward. Design rationale in [`streaming_pipeline_design.md`](streaming_pipeline_design.md) §5.1.2; the channel-context alternative (`refactor/sink-to-context`) was considered and rejected — the Sink trait shape stays.

Ownership does not change: the component keeps owning its Sink, and the per-call `Weak::upgrade()` stays the liveness gate. Inverting it (a component-held `Arc<dyn Sink>`, a registry-held `Weak`, an `alive` flag for call gating) was considered and rejected.

## bpv7-reader-editor review ledger (2026-09-28)

**Per-hop blocks under an encrypted BIB park at the next hop, keys or not (review 1.1 residual).** Under the block lifecycle model, a node that must change or remove a block is the acceptor of every security operation on it, and the security source of any protection on the block that replaces it. A previous node may BIB-sign its Previous Node to assert its identity to the next hop, one-hop integrity the next hop consumes as its acceptor; signed only, this works: the forwarder's replace in `update_extension_blocks` strips the consumed operation, which discharges the RFC 9172 §5.1.2 acceptor duty, and at a next hop without the key, which has failed to accept the operation, the strip is Hardy's policy for that failure. A Previous Node or Bundle Age block that is BCB-covered, in a bundle carrying an encrypted BIB, is marked `BibCoverage::Maybe` by the forwarder's keyless structural re-parse: `Editor::insert_block` refuses its replacement with `MaybeHasBib`, and the bundle parks until expiry. Holding the keys does not help: ingress decrypts extension blocks only into memory (the `bundle/parse.rs` §E rewrite only removes blocks), so the stored bytes keep the BCB and the encrypted BIB, and the forwarder re-parses without keys. The Hop Count does not park: its increment is a SHOULD (RFC 9171 §4.4.3), so where the editor refuses it the block travels unchanged. A partially decrypted bundle, where an acceptor decrypted the per-hop block but not the BIB over it, does not park either: the block is no longer BCB-covered, so the forwarder edits it and the key-holder's check fails closed (the bpv7 ledger's `remove_encryption` entry); for a per-hop block that state is itself invalid (below), so the edit is legitimate. A signed-then-encrypted Previous Node is non-compliant at its source: the block lives one hop, so its signer and its encryptor are the same node, and the final paragraph of RFC 9172 §3.9 forbids a source adding both a BIB and then a BCB for one target. No BCB context yields a plaintext integrity result (RFC 9172 §3.2 counts the AEAD tag as part of the confidentiality service), so neither a MAC nor an asymmetric assertion such as draft-ietf-dtn-bpsec-cose's `COSE_Sign1` combines compliantly with confidentiality. An integrity operation on a per-hop block inside an encrypted BIB is therefore invalid, whether or not the receiving node holds the keys: only the forwarder that inserted the block can source an operation on it, and either it signed and then encrypted the block, which §3.9 forbids, or the signature is an earlier node's that the changing node, as its acceptor, had to remove. The Hop Count is the partial exception, since its increment is a SHOULD: a signature on a count no node has incremented can legitimately survive. Hardy can still receive such bundles from other implementations. **Target (ruled 2026-10-05), a per-hop change of its own:** a per-hop block's security operations end at the next node that changes it, which is their acceptor, so no valid operation puts a per-hop block inside an encrypted BIB. (1) A forwarder that cannot tell whether an encrypted BIB covers a Previous Node or Bundle Age block disregards the BIB: it removes the block and its BCB operation and writes the replacement in plaintext. Not the Hop Count: a signature on a count no node has incremented can legitimately survive inside an encrypted BIB, so the block keeps travelling unchanged. (2) Where every BCB-covered block other than a BIB is a per-hop block, the encrypted BIB provably covers one, and every operation in it is on a per-hop block: the forwarder removes the whole BIB and the BCB's operation on it, then writes the replacements. Both need new `hardy_bpv7` editor operations: a per-hop replace that treats `Maybe` as uncovered, and the removal of a whole encrypted BIB. (3) A key holder that decrypts an encrypted BIB and finds an integrity operation on a per-hop block treats the block as unverifiable, deleting the bundle where it can then no longer be processed: losing a Previous Node does not stop it, an unclocked bundle's Bundle Age the node cannot read or trust does (reason "Block unintelligible"), and the Hop Count is a matter of policy; a report for the invalid combination carries reason code 16, Conflicting security operation ("Reason codes for per-hop failures" below). This needs the forwarder to act on keyed coverage: it re-parses the stored bytes without keys, so a key holder's editor refuses exactly as a keyless one's does. The park itself is the missing terminal disposition recorded under "No terminal disposition for a deterministic per-bundle forward error" above: an editor refusal cannot resolve differently on retry either.

**A scheduled §5.1.1 removal under an encrypted BIB is retained without a key.** The output doors apply the ingress-scheduled removals (RFC 9172 §5.1.1 failure-drops and honoured `delete_block_on_failure` unknowns) through bpv7's `remove_blocks`, which keeps a target it cannot remove safely: one covered by a BCB-encrypted BIB this node cannot decrypt, or cannot re-encrypt for want of an Encrypt-capable key, or whose encrypted-BIB coverage is unresolved (`Maybe`). The bundle then travels, or is delivered, still carrying a block §5.1.1 required gone, rather than with a BIB naming a block that no longer exists. Target: the per-hop change's whole-encrypted-BIB removal, which removes the BIB and the BCB's operation on it before removing the block, a conformant course for a node that cannot edit an encrypted BIB.

## Per-hop block handling (BPSec per-hop paper audit, 2026-09-29)

Items found checking the forwarding path against RFC 9171 and RFC 9172 while drafting a working-group discussion paper on per-hop blocks (in draft). The per-hop park under an encrypted BIB is the first entry above.

**A keyless forwarder sends a clocked bundle's encrypted Bundle Age on without increasing it.** Without the key, ingress cannot read a BCB-encrypted Bundle Age, so it records no age. For a bundle with a clock, `update_extension_blocks` updates the age only when ingress read one or the bundle is unclocked, so the encrypted block is forwarded unchanged, contrary to RFC 9171 §5.4 (the bundle age "MUST be increased"). The unclocked case is rejected at ingress instead (`is_liveness_critical`); an encrypted Hop Count travels unchanged, since its increment is a SHOULD. No option is fully conformant: a keyless node cannot increase the age as RFC 9171 §5.4 requires, and RFC 9172 §5.1.1 mandates discarding the block only if "cannot be decrypted" includes holding no key. Under the block lifecycle model a node that must update a Bundle Age it cannot decrypt is the acceptor of its confidentiality operation and has failed to accept it, so RFC 9172 §5.1.1 requires the block to be discarded with its BCB operation, which the ruling below does. Ruled 2026-10-01: remove the block and its BCB operation, whether or not it reads `BibCoverage::Maybe`. A clocked bundle needs no Bundle Age block, removal matches the reading of RFC 9172 §5.1.1 under which "cannot be decrypted" includes holding no key, and no valid bundle has an encrypted BIB over a Bundle Age block, so a `Maybe` mark on it can be disregarded. Where every BCB-covered block other than a BIB is a per-hop block, the encrypted BIB visibly covers a per-hop block, and the forwarder removes the whole BIB with its BCB operation, as the park entry's target (2) does. Revisit if the IETF DTN WG settles the reading of §5.1.1.


**A key-holding forwarder strips the confidentiality of a per-hop block it updates.** When this node holds the key, ingress decrypts a BCB-encrypted per-hop block into memory. The forwarder's keyless re-parse then finds the block BCB-covered but not `Maybe` (the bundle carries no encrypted BIB), so `Editor::insert_block` removes it from its BCB and writes the updated value in plaintext. In effect the node accepts the confidentiality operation, as it accepts plaintext integrity operations on the block. That fits treating per-hop blocks as unsuitable BCB targets, but it is recorded nowhere as policy. Ruled 2026-09-29: it is forwarder policy, the acceptance half of the block lifecycle model, in which a node required to replace or update a per-hop block is the acceptor of every operation targeting it, and the security source of any protection on the replacement; document it in the `update_extension_blocks` comment and the design doc. The source half, re-encrypting the updated block under a BCB this node sources where security policy requires the block to stay confidential, waits for an egress security policy, which the BPA does not yet have.

**Reason codes for per-hop failures: no path to Conflicting security operation.** `status_report_reason_for` (`bundle/parse.rs`) maps `DecryptionFailed` and `IntegrityCheckFailed` to Failed security operation (15), the BPSec context errors to Unknown security operation (13), unsupported blocks to Block unsupported (11), and everything else to Block unintelligible (8); it never returns Conflicting security operation (16). The existing split is right where it applies: a Hop Count or unclocked Bundle Age that fails authentication is a genuine failure and takes 15, which RFC 9172 §7.1 defines for failures "for reasons other than misconfiguration", while one the node holds no key for is a misconfiguration, deleted because the bundle cannot be processed without the block, and takes 8 (`reject_undecryptable_liveness`). What is missing is a path to 16 for an invalid integrity operation on a per-hop block once it is detected (park entry, fix direction (b)). The function's doc also says a Conflicting violation "is rejected by the structural parser before any reportable bundle exists", which is not true of that combination: the structural parser cannot see inside an encrypted BIB, and the keyed checks do not look. Add the 16 path with the detection, and correct the doc.

**The `update_extension_blocks` comment misstates when the editor refuses.** It describes a block the editor cannot safely update as "BCB-covered, so possibly under an encrypted BIB". The editor refuses only on `BibCoverage::Maybe`, which the keyless re-parse sets on a BCB-covered block only when the bundle also carries an encrypted BIB, and it refuses whether or not this node holds the keys. A BCB-covered block in a bundle without an encrypted BIB is removed from its BCB and rewritten in plaintext (previous entry). Correct the comment.

## BPSec egress seam: designed, not built

The BPA verifies and decrypts at ingress and decrypts the payload at Deliver, but signs or encrypts nothing on the way out and, beyond stripping BIB results over the per-hop blocks it rewrites (`forward.rs`), accepts no operation at Forward. The design places all of that at the fixed BPSec-egress seam, applied per attempt to a bundle stored as received ([`filter_subsystem_design.md`](filter_subsystem_design.md) "BPSec roles at the boundaries"; [`streaming_pipeline_design.md`](streaming_pipeline_design.md) §5.5, §6.1):

- **Source** — BIB/BCB per security policy on originated and forwarded bundles. A payload BIB is two-pass over the stored payload (§6.1.2), never computed at ingress.
- **Waypoint acceptor** — decrypt and strip the operations this node accepts, with the RFC 9172 §5.1.1 dispositions.
- **Payload BCB** (encrypt as source, decrypt as acceptor at Forward and Deliver) waits on the streaming AES-GCM wrapper (Phase D; `bpv7/docs/TODO.md`): the door withholds the stream's end until the tag verifies, and a payload whose tag fails is discarded.

## Storage encryption at rest is the backend's, and undocumented

Bundles are stored as received — plaintext where they arrived or were originated in plaintext, including those this node will secure as a BPSec source — and the metadata carries decoded per-hop values in plaintext even where the block is BCB-protected (`streaming_pipeline_design.md` §5.5). That is within BPSec's model, which leaves the nodes' own storage out of scope (RFC 9172 §1), but a backend outside the node's trust boundary (S3, a database on another host, removable media) needs encryption at rest from the backend itself. [`docs/user-docs/configuration/storage.md`](../../docs/user-docs/configuration/storage.md) does not say so; it should.

## External #712 review ledger (2026-09-30)

**No test observes the filter counters.** `bpa.filter.filtered` and `bpa.filter.modified` are incremented as documented, but the bpa tests install no metrics recorder, so nothing pins them. **The post-registration poll can re-attempt a fresh park.** `register_service` spawns `poll_service_waiting` asynchronously; landing after a bundle parks `WaitingForService`, it re-dispatches the bundle at once — one redundant attempt (failing the same way if the failure is deterministic), and a non-determinism tests must synchronise around (`bpa/tests/filter_dispositions.rs` waits on the park swap itself). The RIB's Waiting poller skips stale wakes since `Rib::request_poll`; the service poll has no equivalent.
