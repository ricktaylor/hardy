## The strategic frame

The policy subsystem serves a **centralized policy manager** that pushes policy to a group of BPAs so that traffic flows consistently across an administrative domain — the DiffServ *Bandwidth Broker* (RFC 2638) crossed with an SDN controller's push model — for DTN, a controller that plans link capacity temporospatially. The division of labour is exact: the controller plans *when and how much* capacity exists; the BPA decides *which bundles* fill each planned window.

The open-core boundary follows the filter doc's purpose statement, generalised: **the open `bpa` crate exposes mechanism traits at every policy point; closed code supplies the policy through those doors.** Concretely: the class model, the queues, the scheduling seams, the basic scheduler, and the distribution seams are open; advanced schedulers and the policy manager with its on-node agent are the closed product. And because a DTN domain *will* routinely be partitioned from its controller — that is what DTN is for — disconnected operation is a first-class mode, not a fallback (see [Distribution](#distribution--the-policy-manager)).

## The traffic class

The **class** is the unit of differentiated treatment. A bundle's membership is assigned by Classifiers into the `MetadataDelta` (`class: Option<ClassId>` — the filter doc owns that seam); everything about what membership *means* is defined here, once per class, as properties:

- **Typed, open properties**, consumed by open machinery: the basic classes provider's match rules (a `bpa-server` concern — see [Configuration](#configuration)), the dispatch weight, the routing table (`routing_table_redesign.md`), and an eviction rank if the storage-pressure work earns it.
- **An opaque controller section** (`[classes.X.controller]`): a structured value passed verbatim to the FlowController type bound to each CLA (the peer seats), validated *by that type's factory*. The open crate never defines a contract vocabulary it does not implement; closed controllers define vocabularies (floors, deadline weights, whatever the product invents) the open crate never sees.

Class definitions compile into a **`ClassPolicy` table** with snapshot semantics: readers (FlowControllers, table selection, eviction) hold an immutable `Arc` and read by array index; updates publish a new snapshot (the RIB's existing pattern). `ClassPolicy` and `MetadataDelta` are `#[non_exhaustive]`; growth is additive. The criterion for where a value lives is the filter doc's: *enumerable treatment → class property; unbounded per-bundle data → delta field.*

With no classes configured there is one default class and the node behaves as today — the `NullPolicy` binding: the zero-config baseline, which doubles as the disconnected-from-manager degraded mode.

## The scheduling discipline

One slogan covers it: **fair queuing everywhere, loss nowhere, shaping only at the link.** (In tc terms: keep the fq — and keep the codel too, with its drop verb re-aimed: a codel "drop" here sends a bundle back into storage for later, never to loss.)

**Why no loss.** IP quality-of-service drops for two reasons DTN lacks: tiny finite buffers (the DTN buffer is the bundle store — holding is the design) and congestion signalling to responsive sources (there is no receiver for that signal; the sender is minutes or hours in the past). Fairness never required drop — it comes from the scheduler. Discard authority stays entirely outside the schedulers: lifetime expiry (the reaper), storage-pressure eviction (retention policy), and explicit routing Drop are the only discards in the system. A scheduler chooses service order and rate, never loss.

**Why not strict priority.** Strict priority upstream defeats fairness downstream: the egress scheduler is only fair among bundles that reach it, and the storm that deepens Dispatch (a Waiting sweep) is typically caused by the same contact opening that makes egress fairness matter. In a deadline network (lifetimes, contact windows) starvation anywhere converts to loss — drop with extra steps. So every queue-draining point is *weighted-fair and work-conserving*; there is no strict tier even for control traffic (a weighted-fair round at CPU speed bounds delay to a sub-millisecond cycle, so a large weight suffices; a capped strict tier would need drop to enforce the cap).

**One scheduler primitive.** Weighted Round Robin (WRR) is Deficit Round Robin (DRR) with every item costing 1, so the deficit core is implemented once and instantiated twice:

- **Dispatch: bare WRR by count.** The shared resource is processing slots (a Routing Information Base lookup costs the same for any bundle size), so items are the honest quantum. Bare — no floors, ceilings, or budgets — because the CPU is not a contracted resource: a lone busy class gets everything; weights bite only under contention. Weights come from one fixed monotone function of the class, node-wide — never per-queue configuration.
- **Egress: DRR by bytes, with budgets.** At the link the quantum is bytes and bundles are indivisible (increasingly so as RFC 9171 fragmentation deprecates), so the deficit carry-over is what keeps fairness byte-exact over lumpy items. On the deficit core sit three contract layers: the **contact volume budget** (the pie is bytes-this-contact — bandwidth × duration from TVR; when spent, traffic waits, never drops), **floors** (guaranteed minimum shares — the anti-starvation contract), and **ceilings with borrowing** (caps, with unclaimed volume redistributed to classes with demand). Within a class's turn, selection is deadline-aware: a volume-limited contact is a knapsack with deadlines — a bundle expiring before the next contact has infinite claim on this one; one expiring regardless is worthless to send. The only non-work-conserving elements in the whole system are here, and both are contracts: link-rate pacing and ceilings.

Worked example: contact = 10 MB; floors critical 2 MB / normal 1 MB; bulk ceiling 4 MB; demand 1 / 5 / 20 MB. Floors first (critical 1, normal 1), borrowing on the remaining 8 (normal +4 meets demand, bulk +4 hits ceiling): pie exactly spent, bulk's other 16 MB waits — undropped — for the next contact.

## The log-jam invariant — end-to-end preemptability

**A small high-priority bundle must never wait behind a large low-priority bundle, anywhere in the system.** The discipline that guarantees it: every shared resource is served at a **bounded quantum** — never at whole-bundle granularity — so the worst-case head-of-line wait at any point is one quantum, not one bundle. The streaming pipeline is what makes this satisfiable at all (whole-bundle materialisation was whole-bundle head-of-line blocking by construction — `streaming_pipeline_design.md` §1.1); the policy layer is what makes it actually hold. Checked point by point:

- **Dispatch**: entries are metadata-only and a RIB lookup costs the same for any bundle size, so items are the honest quantum — WRR by count satisfies the invariant as-is.
- **Storage bandwidth**: concurrent spool writes and egress reads must interleave at chunk granularity across streams (the second-link section below); a whole-bundle disk write that blocks a competing read is the log-jam in internal form.
- **Egress link**: DRR by bytes with deficit carry-over is quantum-bounded by design; the budget/floor/ceiling layers sit above it and never suspend it.
- **The convergence layer is the residual hazard, with two ways out**: a CL satisfies the invariant natively when it interleaves in-flight transfers at bounded quantum — TCPCLv4 does, running several transfers concurrently over one session interleaved at XFER_SEGMENT granularity, so the segment size is its quantum. Where a CL cannot interleave (a one-transfer-at-a-time session model, a serial link), **lanes restore the invariant**: multiple lanes per peer — today's CLA `queue_count` is exactly this concept, misnamed (see the vocabulary note in FlowControllers) — with the discipline keeping expedited traffic on a lane that never waits behind bulk's in-flight transfer. A single-lane, non-interleaving CL degrades honestly to one-transfer head-of-line, which deadline-aware selection must then weigh (starting a giant bulk transfer near contact end, or when expedited arrivals are likely, is the closed scheduler's craft to avoid).
- **Delivery**: service seats drain per-ADU streams chunk-wise; a giant delivery to one service blocks neither another service's seat (per-seat isolation) nor the same service's expedited traffic beyond one quantum (per-class queues within the seat).

## Adaptive de-staging — what codel becomes

> **Called out as its own section deliberately: this is critical technology that needs implementing, not an optimisation to defer.** The architecture's memory story — "the DTN buffer is the bundle store; holding is the design" — is only true if RAM occupancy is actively managed, and today it is managed by fixed counts chosen by hand (the hybrid channel depths, `poll_channel_depth`). Adaptive de-staging is the mechanism that makes the story true. It rides the queue-mechanism tranche, and every seat inherits it.

**The mechanism is CoDel re-aimed.** The detector is kept — sojourn time above target identifies a standing queue — and only the verb changes, because a standing queue in DTN has a home: the response is to **de-stage**, "dropping" the bundle back into storage (undropped, re-drawn later by the poller), keeping the fast-path queues at the shallow depth that makes them fast. The signal is consumed locally by the queue mechanism — never sent to sources (there is no one to signal), and never exercised by a FlowController (de-staging is staging-layer mechanism, not discipline).

**Why it is critical, three ways.** *Memory*: a fixed staging depth is wrong in both directions — too deep bloats RAM on the 32-bit targets Hardy commits to, too shallow starves a fast link of drain concurrency — and the right depth is a function of the actual drain rate, which is exactly what sojourn time measures. *Policy freshness*: a bundle staged in RAM is frozen in yesterday's decisions — its queue position, class, and route were fixed at staging time — while a bundle de-staged and re-drawn passes back through today's RIB, class snapshot, and discipline; a standing queue is not just wasted memory, it is stale policy in flight, and de-staging returns standing traffic to the discipline's reach (the policy epoch's lazy re-derivation applies on the re-draw for free). *Contact dynamics*: DTN load is bursty by construction — a contact opening converts a quiet node into a storm — so any depth tuned for one regime is wrong in the other; adaptation is not a refinement here, it is the only correct answer.

**Why it is cheap and safe here as nowhere else.** The hybrid channel's delivery contract already requires the bundle durably persisted (the status column) *before* it is offered to the in-memory buffer, and its slow path already drops the in-memory copy on the floor at admission when the buffer is full. De-staging is exactly that operation, performed continuously by sojourn rather than once by occupancy — no new custody question, no new persistence path, at-least-once semantics unchanged (consumers already tombstone duplicates). Spill-on-full is the degenerate form of adaptive de-staging; the implementation is confined to the queue mechanism, invisible to producers and FlowControllers alike.

**Where it applies.** Every staging point: the dispatch seat's fast path, peer-seat sub-queues, service-seat heads, and the plain hybrid channels that predate the seats. First target is the hybrid channel itself, since every seat inherits it. CoDel's constants (5 ms target, 100 ms interval) are internet-RTT folklore and do not transfer; the staging equivalents derive from storage re-draw cost versus drain rate, and their derivation is an open question below.

## The second link — storage bandwidth

Once the streaming pipeline's storage work lands (`streaming_pipeline_design.md` §3, §10 Phases A/B), payload streams through the store in both directions and disk bandwidth becomes a shared, contended resource — an internal second link. The claimants: ingress spooling (CLA→disk), egress streaming (disk→CLA), generational rewrites, reassembly, and the reaper. Egress drain rate becomes min(link rate, storage read rate), and storage read rate is coupled to concurrent ingress writes. The slogan splits precisely here: the disk gets **fair queuing** (weighted, work-conserving, chunk-quantum — the log-jam invariant applied internally), never **shaping** — pacing and ceilings remain wire-link contracts, and an idle disk byte is pure waste.

Contention is sharpest during bidirectional contacts — receive and transmit compete for the same disk at exactly the moment both matter, and the bandwidth split decides whether the contact is spent receiving or transmitting. That is a policy decision with TVR-supplied data (both directions' planned volumes), not an accident of which task wins the disk. The candidate shape is a **storage seat**: the same FlowController vocabulary — claimant queues, a disk-bandwidth budget, weights from class policy — stamped once per node like the dispatch seat; whether it earns a full seat or a fixed weighted budget is an open question below.

Two affordances the storage discipline should own deliberately rather than inherit by accident. **The wire is an ingress buffer**: the pre-drain gate plus the pull-paced payload drain mean the BPA can decline to drain — backpressure rides the bounded channel back into TCP/LTP flow control and the link layer holds the bytes — spending link credit instead of disk bandwidth when egress reads matter more. **The hot-forward tee reclaims disk bandwidth**: a bundle forwarded within the contact streams wire-to-wire with the spool riding along, and a delivery ack before spool commit aborts the write retroactively (`streaming_pipeline_design.md` §3.2) — under contention this is not a latency optimisation but freed disk bandwidth. Finally, backends differ in preferred concurrency — S3 wants parallel streams, a single disk wants few and sequential, NOR flash reads fast and writes slow — so the backend supplies **directional lane counts** (read lanes and write lanes, each `Option<NonZeroUsize>` — S3 honestly reports `None`/`None`, a single disk `Some(1)`/`Some(1)`) at construction, exactly as a CLA hints its FlowController type and lane count.

## FlowControllers

**The thesis of this section: prioritisation behaviour is decoupled from queue implementation.** Durable queue primitives (mechanism: the queue factory, the hybrid channels, the storage backends) evolve independently of the disciplines that order service over them (policy: FlowController implementations, from `NullPolicy` FIFO to closed contact-knapsack schedulers), and both are independent of classification (rules: the filter chain). Each layer swaps without touching the other two — and unlike Linux's qdiscs, which own their own packet lists, a discipline here can never lose a bundle even in principle, because custody never leaves the mechanism.

The pattern end-to-end: a registered Ingress/Originate Classifier assigns traffic-class membership (`class` in the delta); the **FlowController** at the dispatch seat maps class → queue and drains by weighted rotation into the processing pool; a per-CLA **`FlowControllerFactory`** instantiates a FlowController per peer at connect, mapping class → queue and draining by byte-fair rotation under contracts.

**Vocabulary — queues hold waiting work; lanes carry in-flight work.** A queue is where bundles wait: durable, effectively unbounded, discipline-ordered. A **lane** is one bounded-quantum service channel of a resource — it carries one in-flight item at a time without internal preemption — and a resource's **lane count is its honest parallelism**. The whole FlowController story in one sentence: *the discipline maps classes to queues at push, and feeds lanes at dequeue.* Every seat reads the same way: the dispatch seat's N workers are its lanes; a peer seat's lane count is its CL's **maximum concurrent transfers** (a TCPCLv4 session carries several at once, interleaved at segment granularity; a datagram CL is effectively unconstrained) — how the CL maps lanes onto sessions is its own business; the storage seat's lanes are the backend's preferred concurrent streams, split by direction (read lanes / write lanes — NOR flash reads fast and writes slow); a service seat's lane count is how many concurrent deliveries its consumer drains. Two rules keep the concept honest. **Lanes are capacity, classes are priority — never structurally bound**: an expedited bundle takes any free lane, and *reserving* a lane for a class is a discipline's moment-to-moment choice, not a static mapping (a reserved-but-idle lane is the non-work-conserving smell banned everywhere but the wire). **Lane counts are resource-supplied scale, not policy**: hinted at registration/construction and cheaply updatable (session churn and per-session limits; S3 throttling), never configuration.

**The lane-count type is `Option<NonZeroUsize>`** — `None` means the resource imposes no limit, and zero is unrepresentable rather than validated (the niche optimisation makes this the same bytes as a raw count, with the compiler policing the sentinel at every use site). Unbounded never reaches a dequeue block: every seat computes **effective lanes = min(hint, seat cap)**, and the cap exists regardless of the hint because each in-flight item costs real resources (a staging channel, a storage read lane, a bandwidth share) — `None` merely drops one term from the min. On the wire the same shape is presence-tracked: `optional uint32 lane_count`, absent = no declared limit (the BPA's policy default for a lane-oblivious client is serial), zero = invalid, rejected at registration. A bare `uint32` with 0-as-unlimited is rejected deliberately: proto3 cannot distinguish "explicitly 0" from "never set", so every client that forgot the field would silently declare unlimited — the unsafe default in exactly the wrong direction, since over-declared lanes re-hide head-of-line blocking inside the CL.

Scheduling logic lives in **FlowController processing blocks**, never in queue wrappers (`queue_architecture.md`'s own layering rule). A FlowController owns its seat's whole queuing station — the qdisc contract: ***push* is a trait method producers call** (`push(bundle, class)`) — not a queue the controller consumes — with the FlowController owning the class→queue mapping and its internal organization (a custom implementation may keep per-source sub-queues or any other structure), and ***dequeue* is the symmetric functional block** that owns the rotation across those queues, executed by the mechanism's tasks. Push is called concurrently from many producers; dequeue runs in the seat's block — the instance is shared, its mapping state small and cheap to guard, with the heavy concurrency handled by the queue primitives beneath. Durable queue primitives are supplied by the mechanism (the queue factory) at instantiation; the discipline is only ever the FlowController's choice of which of its plain queues to serve next — storage-backed queues never need weighted queries.

The push/dequeue pair binds at the type level — one instance owns both ends and the interior state that keeps them consistent (Linux carries both on one `Qdisc_ops` struct for the same reason) — and what happens between them is implementation-specific, made safe by two boundary guarantees. **Custody stays with the mechanism**: bundles live in factory-owned durable queues, so an implementation can misorder traffic but never lose it, and can never drop it — discard authority sits outside all schedulers. **Interior scheduler state is legitimately ephemeral**: the class→queue mapping must be a pure function of the `ClassPolicy` snapshot and the seat parameters, re-deriving identically at restart or peer reconnect; deficit counters, cursors, and accumulated budgets reset harmlessly.

**The seam already exists in embryo** (`bpa/src/policy`): today's `EgressPolicy` (`queue_count` / `classify(flow_label)` / `new_controller`) is the `FlowControllerFactory`, and today's `EgressController::forward(queue, bundle)` is `FlowController::push(bundle, class)` — with two deliberate shifts: `classify` dissolves (classification belongs to the Classifier chain; `push` receives the class and owns the class→queue mapping), and the caller passes a *class*, never a queue index (the mapping is the controller's own). `EgressQueue` becomes the mechanism-owned durable queue handle. The verb `push` also repairs today's triple overload of `forward` (`Cla::forward`, `EgressController::forward`, `EgressQueue::forward`) and matches the house verb (`BundleParser::push`, `StreamIn::push`, `PayloadTail::push`). **`NullPolicy` — one FIFO queue, `classify` always `None` — is already the default at CLA registration and carries over as the zero-config binding at both seats.** That makes the queue tranche's first step a behaviour-preserving rename: wrap today's exact semantics as the NullPolicy FlowController behind the new trait, then the class-aware fair implementation arrives as an opt-in binding. (The dormant `htb_policy`/`tbf_policy` files are candidates to revive behind the new trait or retire toward the closed side — a product-line call.) With null, basic-fair, and the first closed controller, the trait freezes against three real implementations — exceeding the rule of two. The lane vocabulary lands here too: `queue_count` is the peer's lane count and the CLA-facing `queue` index is a lane index — and because `queue_count` and `Forwarding.queue` are **v1 wire-contract names**, the wire-side rename (`lane_count`, `lane`) must ride the same one-cheap-moment batch as the `hardy.*.v1` package scoping; the Rust-side renames can follow at leisure. *(First shift landed 2026-09-03: the mapping is controller-owned — `EgressPolicy::classify` is deleted, the per-peer `EgressController::queue_for()` assigns the queue, and queues are total (`queue_count() -> NonZeroU32`, `ForwardPending.queue: u32`); class-awareness and the push/dequeue inversion follow with this tranche.)*

**One trait, seat-agnostic.** The deficit-core unification (WRR = DRR with cost 1) extends to the API: there is a single **`FlowController` trait** with its **`FlowControllerFactory`** — no `Egress`/`Dispatch` prefix, so the same trait serves dispatch ordering, CLA peer queuing, and service delivery alike; module scoping disambiguates, exactly as it already does for Hardy's several `Sink` traits. A **seat** is where a FlowController instance is wired; seats differ by parameterization (cost function, quantum, contracts, lifecycle), never by trait shape:

- **The dispatch seat** — one instance per node. `dispatch_bundle` becomes `flow_controller.push(bundle, class)` — a trait call placing the bundle into the correct durable class queue (today's `dispatch_tx.send` call site, made class-aware); k class queues, k = class count, fixed at construction. The dequeue functional block feeds processing by **pull**: a fixed pool of N workers — the seat's lanes — each looping on `dequeue()` → `process_bundle`, which subsumes the bounded-semaphore spawn shape (`run_dispatch_queue` + `BoundedTaskPool`) — concurrency is bounded by lane count by construction, busy lanes simply stop calling `dequeue` and the class queues absorb, and fairness is applied at exactly the draw point. The in-memory structure is short — the hybrid channel's fast path made class-aware, with the durable per-class queues as its spill side. It binds the open basic implementation with degenerate parameters — cost = 1 (items), no budgets, no contracts: bare WRR *is* the deficit core at unit cost. All producers push by class — including the Waiting sweep, which today bypasses the dispatch queue and must be rerouted through it (the storm path must not skip the discipline). The binding is fixed to the basic implementation by default; because the trait is shared, opening this seat to other implementations later is a decision, not a redesign.
- **Peer seats** — an instance per CLA peer, created at peer connect and destroyed at disconnect. `Forward(peer)` resolves to a direct trait call — `peer_controller.push(bundle, class)` — placing the bundle into the correct durable sub-queue in one hop; there is no intermediate per-peer forward queue to bridge. The properties such a queue would have provided relocate cleanly: durability is the push placement itself (the queue-layer atomic commit), backpressure is the call's await/result (a closed seat hands the bundle back for return-to-Waiting, exactly as `cla_registry.forward` does today), and peer loss tears the seat down and sweeps its sub-queues to Waiting. The dequeue functional block feeds the CLA send path in discipline order. Each peer seat carries a **type per CLA**: the tc model of a queuing discipline per interface. FlowController types are factories on the construction-frozen tier (Builder-registered — the licence-clean door for proprietary schedulers); the CLA→type binding is configuration, defaulted by a hint from the CLA at registration (a scheduled-contact CLA hints the budget type; an always-on trunk hints plain pacing). Each instance is stamped from **frozen policy × peer-supplied scale** — the policy brings the shares, the peer brings the magnitude (link rate and lane count from the CLA, contact volume from TVR as runtime data) — so per-peer instantiation needs no configuration and cannot fail at connect: every config failure mode was consumed at validation time.
- **Service seats** — an instance per service/application registration, created at register and destroyed at unregister; the delivery-side twin of the peer seat. Today `Deliver(service)` awaits the service inline from the processing context, so a slow or absent consumer pins the worker serving it — under the current `BoundedTaskPool`, ~4×cores parked deliveries halt the entire dispatch plane, transit traffic included, and the coupling is real: a remote gRPC client that holds its connection but stops reading its event stream parks one processing task per inbound bundle, unboundedly. The seat bounds that cost to the service's own queue: `Deliver(service)` resolves to `service_controller.push(bundle, class)`, and the dequeue block drives the delivery door in discipline order; the seat's lane count — how many concurrent deliveries the consumer will drain — is a registration hint, one by default. The backpressure verb here is **park**, not await: a seat whose consumer is not draining returns the bundle to the waiting-for-service status (the parked state the streamed-door work introduced) rather than holding a worker, and unregister tears the seat down with its queues sweeping to the same — symmetric with peer loss at peer seats. Re-registration re-drives the parked backlog through the seat, which subsumes today's `poll_service_waiting` special case. Deadline-aware selection applies here as much as at the link (a bundle expiring before the service next drains has the same infinite-claim shape as the contact knapsack). A remote delivery bridge falls out naturally: announce the bundle to the client, serve the payload when the client claims it, park on an unclaimed deadline — the claim deadline is just this seat's dequeue discipline, not bespoke bridge machinery, and a late claim is a re-drive of a parked delivery through the same door.

**The `FlowController` trait is committed public API and the subsystem's highest risk.** An advanced controller needs more than pull-next: browse/select over the candidate set (sizes, expiries, classes) against a budget, capacity events, the hand-off path, completion feedback — and its vocabulary must stay seat-agnostic (a *budget window* is a contact at a peer seat and unbounded at the dispatch seat). Mitigations: mechanism only — nothing policy-shaped crosses into the open trait; `#[non_exhaustive]` context structs; and a rule of two — the trait is designed against two real implementations (the open basic controller and the first closed one) before it is declared stable. The open crate ships **one deliberately basic built-in type** (fair queuing and pacing, no contracts) serving both seats; the advanced machinery — contracts, floors, volume knapsack, deadline selection — is the closed product, and the design's only obligation is that the line be drawable.

**Validation case — latest-only delivery (ESA UQEB).** ESA's QoS proposal (`draft-algarra-dtn-qos`; worked example in [`filter_subsystem_design.md`](filter_subsystem_design.md)) includes a latest-only mode: a queued bundle is discarded when a newer bundle from the same source to the same destination arrives, and the newer bundle inherits the discarded one's place in line. This is queue-discipline material by construction — a cross-bundle decision at push time, which no per-bundle Classifier can express — so it lands here as a per-flow-replacement FlowController behaviour enabled by an enumerable class property, with flow identity `(source node, destination)` computed at push. The trait shape must therefore not preclude: (a) push-time visibility of the controller's own queued candidates per flow key; (b) dropping a queued bundle from within the discipline as a **deletion in custody**, routed through the mechanism so reporting fires per the bundle's flags and custody never silently evaporates inside a scheduler; (c) the replacement inheriting the dropped bundle's queue position. None of this forces the capabilities into the basic built-in type — it constrains the trait, and it is a third real implementation shape to design against alongside the rule-of-two pair.

## Configuration

Two rules keep the surface contained:

1. **Zero config is a working node** (above). The apparatus is invisible until opted into.
2. **One `[classes]` section owns everything about a class.** Match rules, weight, table, eviction, and the opaque per-controller section, in one stanza — "mission-critical behaves like X everywhere" is one place, structurally, not a promise kept across sections.

**The basic classes provider lives in `bpa-server`, exactly as `static_routes` does.** It parses `[classes]`, hands the class definitions to the `bpa` Builder as structs, and registers its match-rule Classifier **through the public filter trait at build time** — the same door a closed embedder uses. `bpa` itself carries only the class *mechanism* (the `ClassPolicy` table, the per-class queues, the delta field, the default class) and ships **zero classifiers**: the chain is genuinely empty until an embedder, open or closed, supplies policy. The placement follows the litmus test — a deployment can legitimately omit or replace class assignment, so it is a filter, not pipeline (the opposite verdict from validity/rfc9171, which were spec and dissolved inward) — and it dogfoods the public trait: the seam is validated by its first consumer, since if the open provider cannot be built on it, neither can a closed one. The provider's match rules are fixed at build (change = restart), consistent with the local file as bootstrap/baseline; runtime rule updates are the policy manager's side of the fence (its agent's classifiers may snapshot-swap internally — interior data, not chain mutation — with the policy epoch driving re-derivation).

Egress contracts default to **percentages of contact volume**: scale-free, so one class definition is portable from a 9.6 kbit/s UHF link to a 100 Mbit/s trunk without per-peer configuration; absolute per-peer overrides exist only if earned. Scheduler mechanics (quanta, cycles, weight functions) are never configuration. The `bpa` crate's Builder takes structs; TOML parsing is `bpa-server`'s — a closed embedder configures in code and never meets the format. All validation happens where policy enters: at `build()` for local config, at push time for distributed policy (below) — a class with floors bound to a controller type whose factory rejects them, floors summing past 100%, or a dangling table reference is a loud, immediate error, never a quiet runtime surprise.

## Distribution — the policy manager

The frozen/runtime boundary refines to **policy *code* versus policy *data***. Code — filter chains, classifier implementations, controller types — is link-time and rides the restart boundary. Class definitions are data, and data flows at runtime exactly as routes already do: through a registered component.

- **PolicyAgent** is a new registry+sink row, sibling of RoutingAgent — runtime tier, gRPC-remotable, which is precisely what a centralized manager needs to reach a fleet. The open crate ships the trait, registry, and proto (mechanism); the manager and its on-node agent are closed (policy). Pushed updates are validated and answered with a `Result` (as `rib.add` does), then published as a new `ClassPolicy` snapshot.
- **Precedence**: the local `[classes]` file and pushed policy coexist as source-attributed policy with precedence — the same model as the static-routes file beside RoutingAgent routes. Local file = bootstrap and disconnected baseline; pushed policy overrides by source.
- **The policy epoch**: a push makes persisted `class` fields stale, which is the restart re-admission problem without a restart. The re-admission stamp is therefore a **policy epoch**, not a boot id — a restart bumps it and so does a push — and stale bundles re-derive their classification lazily at the Dispatch block. One mechanism serves both cases (this is what settled the re-admission seat as lazy).
- **Validity windows**: a temporospatial controller plans the future, so pushed artifacts carry activation windows — tomorrow's policy pushed today, activating on schedule. Class policy becomes time-variant exactly as contact plans already are; epochs are time-activatable.
- **Domain consistency** has both DiffServ shapes available: push identical match rules to every node (re-derive per hop), or mark at the edge — an egress Rewriter writes a class-mark extension block, interior nodes run a trivial Classifier that honors it (the mark block joins the mutable per-hop conventions; whether the domain signs it at the edge is product security policy). Percentage contracts are what make one domain policy meaningful across heterogeneous links; the manager computes absolute overrides only where it knows better.

## Open questions

1. **`[classes]` format details.** The match-rule language for the basic provider's Classifier (eid-pattern predicates plus what else?), the class-name/id scheme, and the default-table fallback (shared with the routing doc).
2. **`ClassId` representation.** Stable name vs table index, and its interaction with the policy-epoch stamp (shared with the filter doc; a Phase-2 detail there, an on-the-wire detail for pushes here).
3. **The `FlowController` trait shape.** The push/dequeue (qdisc) contract, the browse/select surface, capacity/contact-event delivery, completion feedback, and the seat-agnostic vocabulary — designed under the rule of two before freezing, and checked against the latest-only-delivery validation case above (per-flow replacement, in-discipline deletion in custody, position inheritance) and the service seat's park shape (a dequeue that can decline into park rather than pull, and a claim-deadline discipline for remote consumers); the lane model (dequeue concurrency = the seat's lane count; lane reservation as a discipline choice, never a structural binding) is part of the same seat-agnostic vocabulary.
4. **PolicyAgent protocol.** The proto, precedence semantics between sources, epoch/validity-window encoding, and partial-update vs full-snapshot pushes.
5. **Eviction rank.** Lands only if the storage-pressure tranche shows retention value diverging from urgency (the inversion test: high-urgency telemetry, worthless once stale — evict first).
6. **Per-source fairness within a class** (stochastic-fair-queuing style, per source EID) if chatty-source monopolisation of contacts proves real — same deficit machinery, more queues.
7. **Adaptive de-staging parameters.** CoDel's target/interval constants derive from internet RTTs and do not transfer; the staging equivalents derive from storage re-draw cost versus drain rate. To settle: one node-wide pair or per-seat targets; head-sojourn (codel proper) versus tail eviction as the de-staging victim; and the metric surface needed to observe staging health in the field.
8. **The storage seat.** Full FlowController seat over disk bandwidth, or a fixed weighted budget? The claimant set (ingress spool, egress stream, rewrites, reassembly, reaper), how the bidirectional-contact receive-vs-transmit split is decided (TVR volumes, class demand, or both), the shape of the backend lane hint (directional read/write lane counts, and its update path), and where the decline-to-drain (wire-as-ingress-buffer) decision sits.
