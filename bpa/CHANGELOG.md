# Changelog

All notable changes to `hardy-bpa` are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this crate adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- Annotation slots — embedder-private, typed, size-bounded per-bundle metadata in the classification group (see [Annotation slots](docs/filter_subsystem_design.md#annotation-slots--embedder-private-metadata)): a `FilterPack` registers a slot by stable name and receives the typed `SlotHandle` capability — possession gates every read and write, so a filter pair shares state by sharing the handle. Classifiers write through `MetadataDelta::set`; holders read via `BundleMetadata::slot`, or borrow without copying via `slot_str`/`slot_bytes` (`filter::slots::Blob` is the owned byte-string value type, since bare byte containers deliberately encode with CBOR array semantics). Values are canonically-encoded CBOR at rest, persisted with the bundle; over-sized writes are dropped with a warning, and duplicate names within a pack fail `build()`. Records without slots serialize byte-identically to records from before this change.
- `BundleStatus::same_queue` — queue-identity comparison (peer/service/queue, ignoring per-bundle payload fields), used by the storage channels to recover queue membership without matching the whole assignment record.
- Local delivery now mirrors forwarding (see the rationalised state machine in [refactor_plan.md](docs/refactor_plan.md)): each registered service gets a per-service delivery queue in the new `BundleStatus::DeliverPending` state (the local analogue of `ForwardPending`), whose consumer claims each bundle to the new `BundleStatus::DeliveryAckPending` before `on_deliver` (the analogue of `ForwardAckPending` — no storage poller, every delivery exit resolves the claim). Deliveries are serialized per service in queue order, no longer consuming dispatch processing-pool slots. Unregistering sweeps the service's queued bundles to `WaitingForService` via the new `MetadataStorage::reset_service_queue`; restart re-parks `DeliverPending`/`DeliveryAckPending` the same way, and (re-)registration recovers them. A bundle addressed to a local service that is not registered now parks as `WaitingForService` at dispatch, never `Waiting`. Storage backends gain the new statuses (SQLite codes 8/9; PostgreSQL migrations `0004_dispatch_delivery_statuses`, `0005_deliver_pending_index`).
- Hand-offs resolve truthfully across expiry: once a bundle is in an external party's hands — mid-`on_deliver` (`DeliveryAckPending`) or owned by a CLA transfer (`ForwardAckPending`) — the reaper defers it instead of racing it, since neither can be recalled and expiring it would report a deletion that did not happen. A bundle that expires mid-`on_deliver` but is consumed by the service reports *delivered*, and a transfer the CLA completes reports its completion — not the previous contradictory "deleted: lifetime expired". Deferral does not launder expiry: a deferred delivery re-parks and then expires honestly, a failed transfer re-enters dispatch, and dispatch now carries an expiry checkpoint that drops any expired bundle as `LifetimeExpired` before routing it onward. Expiry before a hand-off commences is unchanged.
- `BpaBuilder::max_bundle_size` — bounds in-memory bundle accumulation on every ingress door (private 64 MiB default). A transfer over the cap or truncated mid-stream is `Refused` at `dispatch`, so the CLA withholds its acknowledgement; the negotiated-cap entry under Changed describes the final `NonZeroU64` shape and CLA propagation.
- Deferred CLA transfer outcomes (see [Deferred CLA Transfer Outcomes](docs/design.md#deferred-cla-transfer-outcomes)): `ForwardBundleResult::Accepted` lets a CLA take ownership of a transfer and report `Completed`/`Failed` later via the new `Sink::transfer_outcome`, keyed by bundle ID. Accepted bundles are retained in the new `BundleStatus::ForwardAckPending` state until the outcome arrives or the peer is removed (outcome-unknown, back to `Waiting`); a lifetime that expires mid-transfer is enforced when the outcome arrives, not by recalling the transfer. A deferred `Failed` re-enters dispatch per-bundle rather than resetting the whole peer queue. Outcome resolution is arbitrated by the new status-conditioned `MetadataStorage::swap_status` and its terminal form `tombstone_if` (a completed transfer resolves straight to its tombstone, never transiting a status the dispatch poller could recover), so an outcome racing the peer-loss sweep or a duplicate of itself is ignored; the in-memory metadata backend additionally never replaces a tombstone with a live entry.
- `MetadataStorage::reset_peer_ack_pending` — the outcome-unknown sweep, mirroring `reset_peer_queue`.
- `Bytes` implements `stream::Receiver<Segment>` — a whole in-memory buffer is a one-`Final`-segment stream, zero-copy — and `stream::buffer_stream` assembles a segment stream into a contiguous buffer, enforcing `total_len` exactness and 32-bit addressability via the new `stream::BufferError` (which converts into `cla::Error`/`services::Error` through the new `PayloadUnaddressable` variants).

### Changed
- Routing is decided at the ingress gate and is the decision of record for fresh arrivals: the RIB lookup runs on the resident headers before the payload is drained, a destination resolving to an explicit `Drop` route rejects the bundle having spooled nothing (reported like any gated drop when the route carries a reason; silent when it does not), and the commit executes the carried decision directly — fresh arrivals no longer transit `DispatchPending`, which now belongs to the originate and re-dispatch paths (parks, polls, sweeps, restart, transfer outcomes). A decision that proves stale during the drain lands in a failure arm whose park re-checks the gate-time table snapshot and re-enters dispatch, and a crash between the metadata insert and execution recovers through restart's `Dispatching` arm — both machinery that already existed. Fresh-arrival execution is bounded by CLA session concurrency rather than the dispatch pool, in line with the plan for backpressure to live at the CLAs, services, and stores.
- **BREAKING:** the egress queue model is totalised, and the policy traits take the redesign's names: `EgressPolicy` is `FlowControllerFactory` and `EgressController` is `FlowController` (`EgressQueue` keeps its name — in the general case it is a queue, feeding one lane directive). `FlowControllerFactory::queue_count` returns `NonZeroU32` — every policy has a queue for every bundle to classify into, and queue indices are the policy's own naming (index 0 is only guaranteed to exist; relative priority is a policy-internal decision) — and `FlowControllerFactory::classify` is deleted: the per-peer `FlowController` owns the queue assignment (`queue_for()`, an index in `0..queue_count()`; an out-of-range index is clamped to queue 0 and logged), so the hot forwarding path touches no shared policy state — the first recorded shift of `docs/policy_subsystem_redesign.md`'s FlowController model. `FlowController::forward` and `BundleStatus::ForwardPending` carry the plain index, through the storage codecs (SQLite/PostgreSQL store the queue parameter unconditionally). The `Option` remains where it is meaningful — the lane directive keying `new_controller`'s queue set: `Some(n)` transmits pinned to declared lane `n`, `None` (always present) on the next free lane.
- **BREAKING:** `storage::MetadataStorage::replace` is removed, and with it the last non-status rewrite of a stored record: a record's non-status metadata is fixed at insert, and thereafter only its status moves (`update_status`/`swap_status`/`tombstone_*`). Backends drop their `replace` implementations.
- Bundle reception is one pipeline with one metadata write. The Ingress filter chain runs at the pre-drain gate on the resident header prefix — before the payload is drained and before anything is stored — so a chain Drop skips drain and store entirely and reports like the sibling gate rejections (a combined reception + deletion status report per the bundle's flags). An admitted bundle is written to the metadata store exactly once, directly at `Dispatching`, carrying the chain's classifier deltas; `New` is an in-memory marker that is never persisted, and restart treats a recovered `Dispatching` record as chain-complete.
- Received bundles are stored exactly as received — no editing on input. RFC 9172 §5.1.1 failure-drops and unrecognised `delete_block_on_failure` removals are *scheduled* in the bundle's metadata and applied per attempt at the output doors: the fixed head of the egress rewrite stage, and a strip before raw-service delivery (`ReasonCode::BlockUnintelligible` drop if the strip fails). A shared BCB whose failed co-target is dropped survives with its remaining coverage intact, per the §5.1.1 cascade.
- The streamed payload tail is validated as it drains: the payload CRC, bundle framing, and each deferred payload-BIB digest are fed per segment, so an oversized signed bundle needs no whole-buffer verification pass after the drain. The deferred verifiers are begun inside the keyed header pass — key material is resolved once per bundle and never crosses an `await`; only the `Send` digest states ride the drain. A complete-but-invalid drain failure (payload CRC/framing, deferred-BIB integrity) or keyed header-verification failure with a recoverable bundle id is dropped with the conforming RFC 9171 §5.6/§5.10 reports, coalesced into a **single** status report bundle: one §6.1.1 admin record asserts both reception and deletion (each gated on its own request flag), with the record's reason citing the deletion. Every ingress reject — the gates included — now emits one report bundle where two were sent before; a truncated stream is refused and never reported.
- RFC 9171 §5.6 Step 4 conformance: an unprocessable extension block flagged `report_on_failure` triggers its "Block unsupported" reception status report on the block flag alone — previously the report was also gated on the bundle-level receipt-report flag, so a block's demand on a non-reporting bundle was silently dropped. A status report addressed to a null report-to endpoint is suppressed (reachable only via the block-flag trigger; the §4.2.4 admin-record/anonymous flag combinations are rejected at parse). Report construction is gated up front: with reporting disabled or a null report-to, no report is encoded and the `bpa.status_report.sent` counters no longer tick for reports that were never sent.
- **BREAKING:** filter registration is construction-frozen packs of three new filter kinds, replacing the runtime filter registry (the full design is [docs/filter_subsystem_design.md](docs/filter_subsystem_design.md)). Embedders implement `filter::{Verifier, Classifier, Rewriter}` — synchronous, payload-free, reading the bundle through the new `filter::BundleReader` (primary block, block headers, metadata, and plaintext or BCB-decrypted block bodies) and returning a `filter::Verdict` — collect them into a `filter::pack::FilterPack` (per-hook registration methods; a Classifier may declare a payload-peek prefix via the `_with_peek` variants), and hand the pack to the new `BpaBuilder::add_filters` before `build()`. Chain order is call order, within a pack and across `add_filters` calls; `build()` freezes the chains, which the dispatcher runs inline at the four hooks (Ingress, Originate, Egress, Deliver). Removed: `Bpa::register_filter`/`unregister_filter`, `BpaBuilder::filter`, the `Filter` and `Hook` enums, `ReadFilter`/`WriteFilter`, `ReadResult`/`WriteResult`, `Mutation`, `ExecResult`, and the name/`after` dependency graph with its `filter::Error` variants — filters no longer have names (a pack-prefixed diagnostic label replaces them) or a runtime lifecycle.
- **BREAKING:** bundle mutation by filters is scoped to extension blocks: a `Rewriter` (Egress and Deliver hooks) edits through the `filter::editor::ScopedEditor` handle (`insert`/`replace`/`remove`), which refuses the primary block, the payload, BIB/BCB, and any block under (possibly unprovable) BPSec coverage. Edits are in-memory and per transmission/delivery attempt — the stored bundle is never rewritten, so the `WriteResult` byte-return path and the post-rewrite re-validation re-parse are gone with it.
- **BREAKING:** the RFC 9171 validity checks are config-gated pipeline checks at the pre-drain ingress gate, controlled by the new `BpaBuilder::primary_block_integrity` and `bundle_age_required` setters (both strict by default): a policy rejection now happens before the payload is drained or anything is stored, reported like every gated drop (the combined reception + deletion status report, per the bundle's flags). `Rfc9171ValidityFilter`, `BundleValidityFilter`, the `filter::rfc9171` and `filter::validity` modules, and the `no-rfc9171-autoregister` cargo feature are removed; raw-bytes origination performs the equivalent inline lifetime/hop check.
- **BREAKING:** the IPN legacy 2-element re-encode is a built-in of the per-hop rewrite stage, configured with the new `BpaBuilder::ipn_legacy_peers(Vec<EidPattern>)`; the `hardy-ipn-legacy-filter` crate is retired.
- **BREAKING:** `BundleStatus::ForwardPending` carries the resolved adjacency in a new `next_hop: Eid` field — the routing decision rides the queue-assignment record, so the egress channels' at-least-once storage recovery re-delivers it intact — and the transient `BundleMetadata::next_hop` field is removed. Storage backends must persist the new field (SQLite reuses `status_param3`; PostgreSQL migration `0006_forward_pending_next_hop`) and their queue polls must match on queue identity rather than the whole status (see `same_queue` above); ownership swaps keep full-equality semantics.
- **BREAKING:** `WritableMetadata` and its `flow_label` field are removed with nothing left writing them: the classification group (annotation slots now; `class` and `route_key` arrive with the policy and routing tranches) is the new write path. The flow label as the egress policy's *input* remains: `FlowControllerFactory::classify` keeps its label parameter (ECMP and HTB-style policies stay in scope) and is invoked with `None` until the policy tranche derives the label from classification; in the interim, ECMP peer selection hashes (source, destination).
- **BREAKING:** `cla::Sink::dispatch` returns the new `#[must_use]` `cla::Acceptance` verdict, and `Err` no longer carries one. `Accepted` means the CLA may acknowledge the transfer — internal disposal of an invalid-but-complete or duplicate bundle is still acceptance, because refusing invalid content would invite the previous node's custody/retransmission machinery to resend identical bytes forever, so the first BPA to detect a content problem accepts and terminates the bundle. `Refused` means the CLA must not acknowledge (a truncated stream, or a bundle over `max_bundle_size`) and its peer retains responsibility. `Err` is reserved for sink faults (`Disconnected`, internal failures) — a CLA's own unregistration mid-stream now surfaces as `Err(Disconnected)` rather than a per-bundle outcome — and `StreamCancelled`/`PayloadTooLarge` are no longer returned by `dispatch` (both remain in use on the egress-door buffering paths). The bundle stream itself carries no verdict: the BPA may stop reading at any point (it may already have accepted — e.g. a duplicate identified from the headers), so a producer that sees `stream::SendError` stops pushing and takes the verdict from `dispatch`'s return value alone.
- **BREAKING:** registration negotiates the bundle size cap. `BpaBuilder::cla` and `BpaRegistration::register_cla` take the CLA's declared transport limit (`Option<NonZeroU64>`; `None` = no CLA-side limit — `Tcpclv4` exposes its configured transfer MRU via the new `max_bundle_size()` accessor for this), and `cla::Cla::on_register` receives the *effective* `max_bundle_size: NonZeroU64` — the BPA's configured cap (which `dispatch` enforces) folded with the declaration — for the CLA to propagate into its own transfer advertising, so an over-cap transfer is never offered: refusal is deterministic, and a peer that kept offering the same bundle would loop forever. The effective cap and the CLA's address type are snapshotted on the BPA-resident registration. The value is definite (the BPA always enforces a cap); a remote proxy that cannot learn the far BPA's cap passes `NonZeroU64::MAX`. `BpaBuilder::max_bundle_size` takes `NonZeroU64` (was `NonZeroUsize`); on a 32-bit target a cap beyond the address space saturates to the addressable bound for in-memory accumulation.
- **BREAKING:** `Bpa::start` is `async` and, when `recover_storage` is set, runs storage crash recovery to completion before resolving: recovery's checkpoint resets assume a quiescent store, so CLAs and services must only be registered after `start` returns.
- **BREAKING:** `cla::Sink::dispatch` takes the bundle as a segment stream (`&mut dyn stream::Receiver<Segment>`), bounded by `max_bundle_size`; a CLA holding a whole bundle in memory passes it directly, since `Bytes` implements `stream::Receiver<Segment>`.
- **BREAKING:** `ServiceSink::send` takes the bundle as a segment stream, bounded by `max_bundle_size` like CLA ingress. `services::Error` gains `StreamCancelled` for a stream that ends before its final segment.
- **BREAKING:** the service delivery callbacks are renamed to `on_deliver`, one streamed door per trait: `Service::on_deliver` and `Application::on_deliver` receive the bundle ID, the exact `total_len`, and the payload as a segment stream (buffer it with `stream::buffer_stream` when the whole payload is needed in memory). The `source` parameter is gone — it is the bundle ID's source component.
- **BREAKING:** `stream::Receiver` is `Send`-only (the `Sync` bound is dropped) and `recv` takes `&mut self`, making exclusive consumption a type-system property and implementors plain state machines.
- **BREAKING:** `Cla::queue_count` is replaced by `lane_count(&self) -> Option<NonZeroU32>` with no default — lanes are the CLA-side parallel transport channels (queues remain the BPA-side priority queues feeding them), and `None` declares unbounded parallelism. Eager per-lane queue instantiation is clamped to 256 so a CLA's declaration cannot size an unbounded allocation.
- **BREAKING:** `BpaBuilder` is obtained only from `Bpa::builder()`: `BpaBuilder::new` is no longer public and the `Default` impl is removed. The cache setters (`lru_capacity`, `max_cached_bundle_size`) have no effect when no bundle storage is configured, as the default memory store is never cached.
- **BREAKING:** `Cla::forward` takes an optional lane, the bundle ID (so a deferring CLA can echo it back without parsing the bundle), the exact `total_len`, and the bundle as a segment stream. `ForwardBundleResult` and `BundleStatus` have new variants; `Sink` has a new required method.
- The dispatcher records `ForwardAckPending` before offering a bundle to the CLA, so an in-flight transfer is distinguishable from a queued one and a deferred outcome cannot race the offer.
- **BREAKING:** the library no longer exposes config-file structs; config schemas belong to the server crates. `MetadataMemStorage::new` and `BundleMemStorage::new` take `Option<NonZeroUsize>` knobs with dimension-named parameters (the zero floor is unrepresentable instead of silently clamped), and defaults are owned privately at the point of use; the `MetadataMemStorageConfig`/`BundleMemStorageConfig` re-exports are removed.
- **BREAKING:** the bundle-cache defaults are owned by `CachedBundleStorage`: its `new` takes `Option` knobs and applies its own defaults, and the `DEFAULT_LRU_CAPACITY`/`DEFAULT_MAX_CACHED_BUNDLE_SIZE` constants are no longer public. `BpaBuilder` carries unset knobs as `None` instead of materialising defaults, and `build` caches any configured bundle storage unless `no_cache()` was called; the default in-memory storage is never cached.
- **BREAKING:** `BundleMetadata` is partitioned by write discipline. Arrival facts are a write-once provenance group read via `received_at()` / `origin()`, with the new `Origin` enum (`Ingress { peer_node, peer_addr, cla }` / `Originated` / `Recovered`); the decoded extension-field cache moves to the public `extensions: ExtensionFields` group (was `read_only: ReadOnlyMetadata`); `ReadOnlyMetadata` is removed. `ExtensionFields` is also what the parse pipelines return, so parser output moves into the record as one assignment. `Default` is removed — construct records via `ingress()` / `originated()` / `new(received_at, origin)`.
- **BREAKING:** the persisted metadata serde shape changes: `origin` is a new (tagged) required key replacing the flattened `ingress_peer_node` / `ingress_peer_addr` keys, and the ingress CLA name is now persisted inside it — fixing restart recovery, which previously mis-read every recovered bundle as locally originated because the CLA name was transient. The wrapper `Bundle`'s wire-bundle key is also renamed (`bundle` → `bpv7`). Metadata stores written by earlier versions do not deserialize: there is no compatibility shim, and on restart recovery treats old-shape records as corrupt and tombstones them — wipe the metadata database when upgrading a node with a populated SQLite/PostgreSQL store.
- **BREAKING:** `bundle::Bundle`'s wire-bundle field is renamed `bundle` → `bpv7`, ending the `bundle.bundle.…` stutter; the common reads are now accessors (`Bundle::id()`, `Bundle::primary()`) and `Bundle::new(bpv7, metadata)` constructs a record in the initial `New` status.
- **BREAKING:** `MetadataStorage::confirm_exists` returns `Option<(BundleMetadata, BundleStatus)>` — the record halves recovery actually consumes — instead of a full `Bundle` whose re-materialized wire half every caller discarded.
- A reassembled ADU now carries the provenance of its earliest-arriving fragment (previously it had no ingress context at all).

### Fixed
- A peer removed while `add_peer` was still constructing it (a multi-await window) no longer strands RIB forward entries that nothing would ever clean up: peers are constructed complete and published once (no half-built peer is ever reachable), and the addition re-checks its address claim after construction, withdrawing the peer if a concurrent removal won.
- The default (null) egress policy no longer panics when a CLA declares explicit egress lanes: the declaration is CLA-side shape — remote, once the v1 wire carries `lane_count` — and applying no policy imposes no lane constraint, so every bundle transmits with the next-free-lane directive and a multi-lane CLA still fans across its idle lanes.
- Service registration no longer awaits its post-registration `WaitingForService` poll inline; the poll runs on the registry task pool, so a sink whose event buffer drains only after registration returns (the gRPC-bridge shape) can no longer deadlock registration against its own announcements.
- A bundle recovered from storage — after a restart, or spilled by egress-channel backpressure — no longer forgets its resolved next hop. The adjacency previously lived in a never-persisted metadata field, so the recovered copy saw `None` and the IPN legacy re-encode silently skipped a peer that required 2-element encoding; the next hop now rides the persisted `ForwardPending` record.
- The legacy re-encode applies only to the transmitted wire form and never replaces the record's primary block. The old egress `WriteFilter` path re-parsed the rewritten bytes into the in-memory record, so an id-keyed resolution after transmission (tombstone, dedup) could compare a rewritten `LegacyIpn` id against the stored `Ipn` id and miss — latent, but wrong by construction.
- The dispatch queue's storage poller could re-queue a bundle that was already being processed, delivering the same bundle to a service concurrently more than once (a delivery held open long enough — any slow service — was re-dispatched on every poller pass). Bundles queued for dispatch now hold the new `BundleStatus::DispatchPending` state and are claimed to `Dispatching` by the queue consumer, so the poller only ever recovers genuinely queued bundles; duplicate copies lose the claim and are dropped. Storage backends gain the new status (SQLite status code 7; PostgreSQL migration `0004_dispatch_delivery_statuses`).
- A routing or registration event that landed while a bundle was in flight (claimed `*AckPending`, invisible to that event's poll snapshot) was missed when the subsequent failure parked the bundle, stranding it until the next unrelated event or expiry. Every park now re-checks the routing table against a snapshot captured when the flight began and re-enters dispatch once if it changed — bounded, so a deterministic failure cannot spin. This fixes the delivery-side redelivery race outright (a service re-registering mid-delivery-failure now redelivers deterministically) and its forwarding-side twin. A re-dispatch re-enters from the persisted representation, discarding the failed attempt's in-memory copy: filter and hop-count rewrites are attempt-scoped, so no failure exit restores or persists them.
- Two startup-ordering races stranded recovered bundles on a cold start with a non-empty store: the dispatch-queue consumer started before the CLA registry was wired, so processing a recovered `DispatchPending` bundle panicked the task and left the bundle claimed in `Dispatching`; and storage recovery ran concurrently with live registrations, so its checkpoint resets could mistake a bundle freshly forwarded via a just-registered peer for a stale pre-restart `ForwardPending` checkpoint and silently reset it to `Waiting`. The consumer now starts only once the registry is wired, `Bpa::start` awaits recovery to completion before returning (see Changed), and recovery's resets are conditional swaps that leave a moved-on bundle alone.
- `forward_bundle`'s `NoNeighbour` and synchronous-failure arms parked with an unconditional status write from a stale `ForwardAckPending` snapshot, which could overwrite a live re-dispatched copy's status or resurrect a bundle another resolver (a peer sweep, or previously the reaper) had already tombstoned mid-transmit; both are conditional swaps again (as is the administrative path's `WaitingForService` park).
- Two delivery exits (a Deliver-filter execution error, and a BPSec payload with no usable key) stranded the bundle with no recovery path; both now park as `WaitingForService`.
- Overlapping service-registration polls (a re-registering service, or a poll racing an application cancel) can no longer dispatch — and potentially deliver — the same bundle twice: the poll claims each bundle out of `WaitingForService` with a status-conditioned swap.
- A duplicate bundle copy delivered by the hybrid channels' at-least-once storage recovery can no longer re-enter circulation or produce a second CLA offer: a queue move (`storage::channel::Sender::send`) is now a status-conditioned swap from the sender's snapshot, and forwarding claims the bundle out of its peer queue the same way before offering it — a duplicate dispatch copy could previously stomp an in-flight `ForwardAckPending` back to `ForwardPending`, re-arming the peer queue mid-transfer, and a duplicate egress copy could offer the same bundle twice.

### Removed
- **BREAKING:** `ServiceSink::cancel` and `ApplicationSink::cancel` — the implementation was status-blind, reporting success for a bundle already mid-transfer at a CLA. A future cancellation must be conditional on a still-cancellable status; the contract is recorded in [docs/TODO.md](docs/TODO.md).

## [0.2.0]

### Added
- `BpaBuilder::key_provider()` and `service_priority()`; BPSec `KeyProvider` key-resolution wiring.
- New `stream` module exposing the push-side `Sender<T>` trait and `SendError<T>`, with a blanket impl for `hardy_async::channel::Sender`.
- New public `filter` types: `Mutation`, `ExecResult`, and the `filter::validity` submodule.
- `BundleStorage::replace` for atomic in-place overwrite; `storage` re-exports `BundleMemStorage`, `MetadataMemStorage`, `CachedBundleStorage` and their `*Config` types.
- `critical-section` cargo feature (forwarded to `hardy-bpv7`) for targets without native 64-bit atomics.
- `cla::Error::PayloadTooLarge { size, max }` and `services::Error::PayloadTooLarge { size, max }` for pre-flight rejection of over-sized bundles/payloads before they can break a transport stream.

### Changed
- **BREAKING:** renamed module `routes` → `routing` and its `Action` enum → `RouteAction`; `RoutingSink::add_route`/`remove_route` take `RouteAction`. Added `Error::NullNextHop` and `Error::ViaOwnNode`.
- **BREAKING:** renamed module `filters` → `filter`; renamed `FilterResult` → `ReadResult` and `RewriteResult` → `WriteResult` (its `Continue` payload is now `Option<Vec<u8>>`, was `Option<Box<[u8]>>`). `Bpa::register_filter`/`unregister_filter` return `filter::Error`.
- **BREAKING:** `MetadataStorage`/`BundleStorage` streaming methods (`recover`, `remove_unconfirmed`, `poll_*`) take `&dyn stream::Sender<T>` instead of a `flume::Sender<T>` by value — every storage backend must be updated.
- Switched the node-id RNG from `ThreadRng` to a `SysRng`-seeded `SmallRng`; moved internal channels off `flume` to `hardy-async`/`arc-swap`.
- Raised the minimum supported Rust version (MSRV) to 1.95.

### Fixed
- Preserve bundles when a service delivery returns an error: the failure is propagated so the bundle is re-queued for retry instead of being dropped.
- Treat unexpired tombstones as dedup state and drop already-expired bundles at ingress, before the metadata write.
- `MetadataMemStorage` evicts tombstones before live bundles; `BundleMemStorage` uses an edge-triggered capacity watermark with corrected eviction.
- Exit the storage `poll_queue` drain promptly on cancellation instead of running one extra poll cycle.

### Removed
- `cla::Error::InvalidBundle(hardy_bpv7::Error)` variant.
- Public `storage::Sender<T> = flume::Sender<T>` alias and the public `storage::bundle_mem`/`storage::metadata_mem` modules (reach them via the re-exports above).
- `NodeIds::resolve_eid` is now crate-private.

Releases before this version predate this changelog; see the git history for details.
