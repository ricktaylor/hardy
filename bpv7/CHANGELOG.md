# Changelog

All notable changes to `hardy-bpv7` are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this crate adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- `bundle::Bundle::primary_has_integrity` and `editor::Editor::primary_has_integrity`: whether the primary block carries a CRC or a BIB that targets it or may (RFC 9171 §4.3.1), the editor's judged on the primary and coverage as its staged edits leave them.
- `editor::Error::StagedPayload`: `Editor::rebuild_streamed` refuses a payload whose data was staged, rather than streaming the caller's bytes in its place and dropping the staged data.
- `editor::Editor::generation()`: the number of edits staged so far, so a caller asks the editor whether anything changed rather than keeping a flag beside it; `extension_editor::ExtensionEditor::is_modified` reads it.
- `editor::Editor` implements `reader::Reader`: an editor reads as the bundle its staged edits leave, a staged block's data or a kept block's wire bytes, a read borrowing it only for its own duration.
- `editor::Editor::current_bundle()`: the bundle as the staged edits leave it — the current primary block and the block headers with their current BIB and BCB coverage — a header-sized copy for reading while the editor goes on editing; a staged block's extents index nothing, a staged primary block's included, and its body reads through the editor.
- `bpsec::DecryptingReader::over_editor`: a decrypting reader over an editor's staged bundle, reading each block's body as the editor holds it, under the editor's current headers and the BCB operation sets its BCB blocks carry as staged.
- `editor::Editor::restore_block`: an update of a block's data that keeps the security operations over it, for a caller restoring the data they were computed over, as reassembly restores the payload a fragmenter split (RFC 9171 §5.8); `update_block` removes the block from every target list, since an edit invalidates them.
- The `bpsec` feature is public: BPSec processing, both sides, the keyed check, the decrypting reader, the editor's security edits, the signer and the encryptor, enabled by every security-context feature (`rfc9173`, and the future `cose`). A build without it still parses security blocks, classifies them by their flags and removes them; nothing in it decrypts or verifies.
- `bpsec::Role`, `bpsec::Roles` and `bpsec::SecurityServices`: this node's role in a security operation, verifier or acceptor (RFC 9172 §1.4), its roles on one block's BCB and BIB operations, and the services a caller names on a block, as `Parsed::check` takes them by block number; bpa's `filter::slots` types, moved down.
- `bpsec::SecurityService`: a security service, confidentiality or integrity (RFC 9172 §1.1), as `bpsec::checks::Outcome` names the one an operation applies.
- `editor::Chunk::flatten_head`: the chunks flattened after the outer array's head, without its break, for a caller that continues the bytes itself, as a streamed rebuild's header region is continued by the payload and its trailer; `Chunk::flatten` is it with the break.
- `block::BibCoverage` is `Copy`.
- `bpsec::bib::Operation::is_unsupported` and `bpsec::bcb::Operation::is_unsupported`: whether this node cannot process the operation, for a caller deciding what an operation it could not check means.
- `editor::Editor::with_streamed_payload(plaintext_len)` and `Editor::rebuild_streamed()`, for a payload whose data streams past the editor rather than being resident, as at a payload's security acceptor holding only the headers (RFC 9172 §5.1.1). Told the payload streams, `BPSecEditor::remove_encryption` writes the payload block for a plaintext of that length rather than decrypting resident data, with the encrypted BIB over the payload and that BIB's other targets all or none as before, and the payload regains the CRC its context removed (RFC 9173 §4.8.2); `remove_integrity(1)` then removes an accepted BIB over it. `rebuild_streamed` returns the rebuilt headers and the payload block's header for the declared length, with the payload's index entry spanning its full wire form, and a `builder::PayloadTrailer` that the caller feeds the plaintext as it streams and that ends the wire form; `Builder::build_stream` and the editor share that framing, so the two frame a streamed payload byte for byte alike. A payload received in plaintext streams as it stands, a removed BIB over it restoring its CRC. A streamed rebuild without the payload declared as streamed, or of an encrypted payload whose encryption was not removed for the stream, is `NoBlockData`.
- **BREAKING:** `Parsed::check` reports an integrity operation on a Previous Node or Bundle Age block among the blocks it accepts inside an encrypted BIB: a combination no valid bundle carries, since only the forwarder that inserted a per-hop block can source an operation on it, and RFC 9172 §3.9 forbids it both signing and encrypting the block. A BIB it decrypted proves it, recording the BIB's operation on the block `Checked::Conflicting`; without the key, the structure shows an encrypted BIB may cover such a block when every BCB-covered block other than a BIB is one of those two, recorded `Checked::PossiblyConflicting`, one outcome per unread BIB and block it may cover. The caller, the block's acceptor, applies its policy; that a bundle without a creation time cannot lose the block is its caller's to decide. The `bundle` tool refuses either. The Hop Count is exempt, its increment being a SHOULD.
- `bpsec::DecryptingReader`: a `reader::Reader` that decrypts BCB-covered blocks on demand and memoises each block's outcome — plaintext, no-key, or decrypt-failure — for the reader's lifetime, so a chain of consumers sharing one reader through the trait costs one decrypt attempt per covered block (the give doors re-run a cached failure to report its exact cause). The trait impl lends (cache borrows, zeroized when the reader drops); the inherent `block_data()` gives (owned plaintext, typed errors carrying the diagnostic cause, and `Ok(None)` for non-resident extents), preserving the free `bpsec::block_data` contract; `into_block_data()` is its consuming form, which moves a covered block's plaintext out instead of cloning it, for callers that read one block and drop the reader.
- `extension_editor::ExtensionEditor`: a scoped extension-block editing handle on an owner's `editor::Editor` — insert/replace/remove of extension blocks only. Some owner privileges are absent from the type (the primary-field setters, BIB/BCB creation and management, coverage stripping); target gates refuse the rest at runtime with a typed error — the primary and payload blocks, the reserved block types, security blocks as targets, and covered targets (unprovable coverage refuses conservatively). Blocks inserted through the handle are valid targets for its own replace/remove; the edits go into the owner's editor, which the owner rebuilds once the handle is gone, and `is_modified` reports whether the handle applied any. An edit that would make a malformed bundle is refused at call time instead of failing at the owner's rebuild or at a receiver's decoders: what the structural parser rejects, as `Error::Invalid` with the parser's own error (`InvalidFlags` for a `report_on_failure` flag the bundle forbids, `InvalidCrc` for an unrecognised CRC type), and Previous Node, Bundle Age, or Hop Count data that does not decode as its type (on `insert` and `replace`), as `Error::UndecodableBody` carrying the type and its decode error — data the parser rejects in a received block. Removing the Bundle Age block of a bundle without a creation time is refused as `Error::Invalid(MissingBundleAge)`, the parser's own error (RFC 9171 §4.4.2). Receiver policy over a well-formed bundle — hop limits, a receiver's handling of unsupported blocks — is the caller's decision and is not refused.
- `PrimaryBlock::forbids_report_on_failure()`: the one statement of RFC 9171 §4.2.3-4/-5's block-flag rule — an administrative-record or null-source bundle forbids the `report_on_failure` flag on every block. The parser rejects the combination through it, `Builder::build` clears the flag, `ExtensionEditor` refuses it at call time, and the owner `Editor` refuses it when it rebuilds, once the primary is final.
- `reader::ReaderExt`, blanket-implemented for every `Reader` (trait objects included): `extract<T>()` CBOR-decodes a block's payload, with `Ok(None)` for absent-or-unavailable and `Err` only for decode failures.
- `block::Flags` and `bundle::Flags` implement `Hash`, as `rfc9173::ScopeFlags` does; hashing goes by the encoding (see Changed).
- `canonicalize()` on `block::Flags`, `bundle::Flags`, and `rfc9173::ScopeFlags`: it folds each bit of `unrecognised` that names a flag into that flag's field, mirroring `block::Type::canonicalize()`. `rfc9173::ScopeFlags` gains `From<u64>` and `From<&ScopeFlags> for u64`, the conversions its CBOR codec delegates to.
- `is_canonical()` on `block::Flags`, `bundle::Flags`, `rfc9173::ScopeFlags`, and `block::Type`: whether a value is the form `canonicalize()` returns — the one test that tells an alias from its canonical form, which equality no longer does.
- `bpsec::Decrypted`, the decrypt outcomes of one parse's BCB-covered blocks (each plaintext, and the blocks that failed), carried from one pass over a bundle to the next: `DecryptingReader::with_decrypted` seeds a reader's memo with them, so it decrypts none of those blocks again, and `DecryptingReader::into_decrypted` hands back the reader's outcomes, seeded or its own. Its `Debug` shows block numbers, never plaintext.
- **BREAKING:** `bpsec::edit::remove_encryption` is `BPSecEditor::remove_encryption`, a method of the trait taking only the block number: a block's plaintext comes from the editor's cache (`Editor::with_decrypted`), as a security acceptor's earlier pass over the bundle leaves it, written from it, borrowed into the edit rather than copied, so that no block is decrypted twice, and any other block the removal needs is decrypted with the editor's key source (`Editor::with_key_source`); a decrypt neither serves fails with `NoKey`. `BPSecEditor::remove_blocks` takes the blocks by reference and no key source, reading the same two, and `rewrite::apply_rewrites` takes the `Editor` to apply the rewrites through, in place of the data, the bundle and a key source.
- `bib::Operation::require_key` and `bcb::Operation::require_key`: whether a key source holds a key the operation can verify or decrypt with, looked up exactly as processing looks it up, without processing — so an acceptor can learn it holds no key before it takes a bundle. Each RFC 9173 context keeps one key lookup that the probe and the operation share.
- `bpsec::bcb::Operation::begin_decrypt` begins a `bpsec::bcb::Decryptor` for a target whose data streams past, against headers that need not hold it: the decrypt stage of a security acceptor's drain (RFC 9172 §5.1.1). The key is resolved, the content-encryption key unwrapped and the additional authenticated data built before the first byte, so a missing key (`NoKey`), an unsupported context or variant, a key that cannot serve, or a target carrying a CRC its context removes fails there, before anything is stored. The caller feeds the target's data as received (`update`) and settles with `finish`, which returns the plaintext, authenticated and zeroized on drop, `plaintext_len()` long (the received length, less a tag carried with the ciphertext, RFC 9173 §4.4); data short of or past the target's length, or a tag that does not authenticate, fails as `DecryptionFailed`. Under BCB-AES-GCM the decryptor holds the content-encryption key, zeroized on drop, and collects the ciphertext to decrypt it whole, so it is `Send`; its `Debug` shows lengths only. `bcb::Operation::decrypt` is its all-in-one counterpart, feeding it a resident target's whole data, as `bib::Operation::verify` feeds `begin_verify`'s verifier, so the two paths cannot diverge.
- Incremental BIB verification for a streamed target: `bpsec::bib::Operation::begin_verify` begins a `bpsec::bib::Verifier` from header material alone, every header-resident IPPT part absorbed, for `target_len` bytes of the target's data: as received, for the payload BIB operations `Parsed::check` records `Deferred`, or the plaintext of an encrypted target its security acceptor decrypted, which RFC 9172 §3.9 forbids checking against ciphertext. The caller feeds the data as it streams (`update`) and settles with `finish` (constant-time tag compare). A primary-block target is refused (`InvalidBIBTarget`): its integrity input is its canonical form, verified resident. The verifier owns everything it needs — the MAC state keyed with the resolved key; the CEK copy is zeroized once the MAC is keyed, but the `hmac` crate's pad state is not zeroized on drop — so it is `Send` and may cross `await` points and task boundaries.
- `builder::Builder::build_stream(payload_len, timestamp)` — the emit-side twin of the parser's `Partial` route, for building a bundle whose payload is supplied as a stream. Returns a `builder::StreamBuild`: the parsed `Bundle` view (block extents span the full future wire form, so `encoded_len`/`payload_range` are exact from the prefix alone), the resident wire prefix ending at the payload block's byte-string head, and a `builder::PayloadTrailer` continuation that holds the declared length (`update` absorbs payload runs into the payload block's CRC digest, refusing a run past the declaration with `builder::PayloadOverrun`; `finish` yields the CRC field and the outer break, refusing a payload short of the declaration with `builder::PayloadUnderrun`; `received` reports the bytes absorbed so far). `prefix ++ payload ++ trailer` is byte-for-byte the `build()` output for the same inputs — an administrative-record or null-source bundle included, where both clear `report_on_failure` on every block. A `payload_len` whose wire form would end past `u64::MAX` is refused with `builder::Error::PayloadLengthOverflow`.
- `status_report::ReasonCode` implements `From<&Error>`: the reason a bundle deleted for an error is reported with. A block this node cannot process, an unsupported block type or a security operation it holds no key for, is `BlockUnsupported` (RFC 9171 §5.6 Step 4); an unknown security context or parameter is `UnknownSecurityOperation`, a failed decryption or integrity check `FailedSecurityOperation`, and an encrypted BIB over a Previous Node or Bundle Age block `ConflictingSecurityOperation` (RFC 9172 §7.1); any other error is a malformed block, `BlockUnintelligible` (Step 3).
- **BREAKING:** `parse::Parsed::per_hop`, a new `parse::PerHopFields`: the decoded values of the Previous Node, Bundle Age and Hop Count blocks no BCB covers, which `BundleParser::finish` and `parse()` now decode. A BCB-covered block's field is `None` until its acceptor decrypts it, decoding the plaintext with `PerHopFields::decode`; `PerHopFields::from_blocks` decodes a built bundle's. With the `serde` feature it serializes, each absent field omitted. A destructuring of `Parsed` that names every field needs the new one or `..`.
- **BREAKING:** `rewrite::apply_rewrites` returns `editor::Error`, the removal cascade's, instead of panicking on it: the cascade checks each BCB-encrypted BIB it decrypts itself (its targets, and RFC 9172 §3.8's shared-target rule), so the caller no longer has to have decrypted and validated those BIBs first, and a BIB it cannot parse, check or read where it must strip a target is an error. Naming a block the bundle lacks in `to_update` is a usage error, and still panics.
- **BREAKING (behaviour):** `BPSecEditor::remove_encryption` removes the encryption of the encrypted BIB over its target, and of that BIB's other BCB-covered targets, with it, all or none (RFC 9172 §3.9): every decryption must succeed, or nothing is removed and the call returns the error (`NoKey`, `DecryptionFailed`). A target that is itself an encrypted BIB takes its targets likewise. A target whose coverage reads `BibCoverage::Maybe` is resolved by decrypting the bundle's encrypted BIBs, and an encrypted BIB that may cover it and cannot be decrypted fails the call. The BIB is checked once decrypted and written in plaintext with its integrity operations intact, for `BPSecEditor::remove_integrity` to strip those the caller accepts; a BIB sharing the target's BCB no longer has its operation on the target stripped. `editor::Error::CannotDecryptRelatedBib` is removed. A BCB that does not list the block it covers fails the call as `Error::Altered`, where the editor came back unchanged.
- `editor::Editor::with_key_source` sets the key source an editor decrypts with, and `Editor::with_decrypted` the plaintext cache it reads before decrypting: the `BPSecEditor` methods read both, and `update_block`, `insert_block`'s replace, `remove_block` and `BPSecEditor::remove_integrity` resolve a block's `BibCoverage::Maybe` by decrypting the bundle's encrypted BIBs until one lists the block, and checking that one, where they refused with `MaybeHasBib`; without a key source, or where a BIB that may list the block cannot be decrypted, they still refuse.
- **BREAKING (behaviour):** `BPSecEditor::remove_integrity` reads the block's current coverage, including what the editor's earlier operations resolved, and refuses a block an encrypted BIB may cover with `MaybeHasBib` rather than `NotSigned`.
- **BREAKING (behaviour):** no security operation changes a target's CRC, on any block, under any security context. The `Signer` and the `Encryptor` leave a target's CRC type as it stands, the `Encryptor`'s rebuild computing the CRC over the ciphertext as any block edit does; verification and decryption take a target with a CRC or without one; and `BPSecEditor::remove_integrity`, `remove_blocks` and `remove_encryption` add none, so a target whose source removed its CRC, as RFC 9173 §3.8.1 and §4.8.1 have a source do, travels on without one, the primary block included, which RFC 9171 §4.3.1 holds immutable. RFC 9173 §3.8.1, §3.8.2, §4.8.1 and §4.8.2 are not implemented, under which the `Signer` and `Encryptor` removed a target's CRC, verification, encryption and decryption refused a target that carried one, and the removals included a CRC-32C again, the primary's whatever the context: the CRC is in neither the IPPT (RFC 9173 §3.7) nor the AAD (§4.7), so an operation's result is the same either way; a CRC the source removes is the one check every node between it and the acceptor can make (RFC 9171 §5.6); and each change to the primary broke every operation whose scope included it. RFC 9172 §9.3 leaves a target's CRC to the context's own statement, and the draft COSE context leaves it alone. `bpsec::Error::CrcPresent` goes with the refusal, and `editor::Error::PrimaryInSecurityScope` comes only from an edit to the primary block itself: `Signer::sign_block` signs a primary that carries a CRC while another operation scopes the primary, `remove_integrity(0)` removes the primary's BIB, and `remove_blocks` no longer retains it, since removing it changes nothing in the primary; a primary created without a CRC under a BIB stays without one once the BIB goes.

### Removed
- **BREAKING:** `checks::verify`, `checks::accept`, `checks::verify_payload`, `checks::verify_all_bibs` and `checks::classify_unsupported`, with `checks::VerifyFacts`, `checks::AcceptFacts`, `checks::DeferredBibs` and `checks::Services`: the parser classifies the blocks this node cannot process (`Parsed::classification`), one keyed check on the parse reports every security operation (`Parsed::check`, `bpsec::checks::Facts`), a deferred payload BIB is settled as the payload streams (`bib::Operation::begin_verify`, `bib::Verifier`), and `bpsec::SecurityServices` names the services (see Changed).
- **BREAKING:** `bib::OperationSet::is_unsupported` and `bcb::OperationSet::is_unsupported`, and `can_share` on `bcb::Operation` and `bcb::OperationSet`, are private to the crate: what a security context supports, and whether it lets operations share a block, is bpv7's own machinery, asked by the classification, the Signer and the keyed check. So are the methods of the RFC 9173 context types, which a caller could reach through `bib::Operation::HMAC_SHA2`, `bcb::Operation::AES_GCM` and `bib::Verifier::HMAC_SHA2`: the wrappers on `bib::Operation`, `bcb::Operation` and `bib::Verifier` are the API, and the context types' fields stay public.
- **BREAKING:** the free `bpsec::block_data()` function — `bpsec::DecryptingReader::block_data` is the same contract (typed errors carrying the cause; owned decrypted plaintext) plus outcome memoisation and an explicit `Ok(None)` for non-resident extents. A one-shot caller migrates to `DecryptingReader::new(..).into_block_data(n)`, which, like the removed function, returns the decrypted plaintext without an extra copy.
- `bpsec::no_keys`: a caller that holds no keys passes `key::KeySet::EMPTY` to the checks, or wraps it as its key provider.

### Changed
- `editor::Editor::set_fragment_info` sets the primary's fragment flag with the fragment info, and `set_bundle_flags` keeps the flag with the fragment info whatever flags it is given, so the staged primary agrees with what the rebuild emits; the rebuild no longer corrects the flag itself.
- `parse::Classification::delete_bundle` names the lowest-numbered block of its kind, so the verdict does not depend on the parse's map order.
- An editor resolving a block's `Maybe` coverage with its key source returns the error of a BCB-encrypted BIB it decrypts that does not parse or fails its checks, rather than refusing with `MaybeHasBib`; the coverage stays `Maybe` only while such a BIB cannot be read.
- **BREAKING:** the editor edits in place. Every edit on `editor::Editor` takes `&mut self` and returns `Result<(), Error>`: the primary setters are `set_bundle_flags`, `set_bundle_crc_type`, `set_timestamp`, `set_source`, `set_destination`, `set_report_to`, `set_lifetime` and `set_fragment_info`; `push_block`, `insert_block`, `update_block` and `restore_block` return a `BlockBuilder` that borrows the editor and stages its block on `rebuild()`, which returns nothing, a builder dropped unrebuilt staging nothing; `remove_block` and `bpsec::edit::BPSecEditor::{remove_integrity, remove_encryption}` return `Result<(), Error>`, and `remove_blocks` the set it removed. A refusal leaves the editor as it was, so nothing hands it back beside the error, and `(Self, Error)` is gone from every signature. The construction-time `with_streamed_payload`, `with_key_source` and `with_decrypted`, and the terminal `rebuild`, `rebuild_bundle` and `rebuild_streamed`, keep their consuming form.
- **BREAKING:** `bpsec::signer::Signer::sign_block` and `bpsec::encryptor::Encryptor::encrypt_block` take `&mut self` and return `Result<(), Error>`; `rebuild` and `rebuild_bundle` consume the signer or encryptor as before.
- **BREAKING (behaviour):** `Parsed::check` checks only the per-hop blocks' operations on a fragment, a Previous Node, Bundle Age or Hop Count block being the forwarder's write to the fragment (RFC 9171 §5.4): every other operation in this node's roles is recorded `Deferred`, nothing of it decrypted and no key looked up for it, since it covers the primary block as it was before fragmentation, or a part of the payload, and is checkable only once the bundle is reassembled (RFC 9172 §5.2).
- **BREAKING:** the keyed checks are one call on the parse: `Parsed::check(keys, roles, others)`, in `bpsec::checks`, replaces `checks::verify` and `checks::accept`. It takes this node's `bpsec::Roles` by block number and, in `others`, its roles on every block the map does not name, and runs in one pass, in the one order that works: the acceptors' confidentiality processing, short of removing the operations, which decrypts each accepted block's BCB operation into the parse's plaintext cache (`Parsed::decrypted`, a `bpsec::Decrypted`, empty from the parse) with the BCB operations on an encrypted BIB that covers the block and on that BIB's other targets, all or none (RFC 9172 §3.9), each a block this node must accept too, and an encrypted BIB by necessity where an accepted block other than a Previous Node or Bundle Age block is BCB-covered beside one under a BCB from the same security source, the only BIB that covers it in a valid bundle (RFC 9172 §3.9), its coverage stamped on the parse's blocks; the verifiers' decryption of their own block into the cache, the block travelling as received; and the integrity checks of every block named for integrity, either role, over the plaintext just cached, a target under a BCB the cache does not hold passed over, since RFC 9172 §3.9 forbids checking a BIB against ciphertext and its BCB's acceptor is the one to check it. It returns one `bpsec::checks::Facts`: an `Outcome` per security operation met, naming its security block, its target, its `bpsec::SecurityService` and what the check made of it (`Checked`: verified, failed, no key, unsupported, deferred, conflicting, possibly conflicting), and `incomplete`, the blocks whose acceptance could not be completed, coupled through an encrypted BIB to a block this node does not accept or whose BCB operation it could not process, that operation carrying its own outcome, or under an encrypted BIB it cannot read that may cover the block; `Facts::any`, `Facts::targets` and `Facts::targets_of` read them. A failed integrity check or ciphertext that does not authenticate is an outcome, `Checked::Failed`, not an error, and an operation this node holds no key for `Checked::NoKey`, each naming its security block and target, so the caller applies its failure policy to each; an operation in a security context this node does not support is recorded `Checked::Unsupported` and never processed, a BIB decrypted by necessity included, its flags being its acceptor's. The payload's own operations are not processed, since the payload need not be resident: with its confidentiality accepted, the key its decryption needs is required now and the operation recorded `Deferred` or `NoKey`, and a BIB operation on it the same unless the payload is resident in plaintext, for its acceptor to check as it streams (`bcb::Operation::begin_decrypt`, `bib::Operation::begin_verify`); a verifier of the payload's confidentiality is passed over. A Hop Count whose acceptance cannot be completed is read all the same, as a verifier reads it, its increment being a SHOULD. No keyed check fails a bundle for a target it cannot lose: that the primary block, the payload (RFC 9171 §4.1) and the Bundle Age of a bundle without a creation time (§4.4.2) delete the bundle when an operation on them fails or finds no key is the caller's fate to decide, which bpa decides from the same outcomes. `verify`'s implicit per-hop acceptor set, its `acceptors` argument and its `to_update` overlay, which no caller filled, are gone with it.
- **BREAKING:** the parser classifies the blocks this node cannot process: `parse::Classification`, filled by `BundleParser::finish` into `Parsed::classification` at a complete and at a headers-only parse alike, replaces `checks::classify_unsupported` and its `supported_types`, which no caller passed. It classifies `Type::Unrecognised` blocks (A1), BCBs (A2) and plaintext BIBs (A3) with an unsupported security operation by their flags, with the deletion one of them may demand in `Classification::delete_bundle`, an A1 block's before an A2 block's before an A3 block's, beside the facts, so a caller reporting that deletion still sees which blocks request a status report (RFC 9171 §5.6 Step 4: report, then delete). What remains of `checks` is BPSec's and lives beside the signer, the encryptor and the editor as `bpsec::checks`.
- **BREAKING:** BPSec processing needs the `bpsec` feature, on by default through `rfc9173`: `bpsec::checks` and `Parsed::check`; `bpsec::DecryptingReader`; `bib::Verifier` with `bib::Operation::{begin_verify, verify, require_key}`; `bcb::Decryptor` with `bcb::Operation::{decrypt, begin_decrypt, require_key, encrypt}`; `Editor::with_key_source` and `Editor::with_decrypted`; and `BPSecEditor::remove_encryption`. Each keyed half is a module of its own behind the feature, `bpsec::checks` and the private `bpsec::reader`, `bib::keyed`, `bcb::keyed` and `edit::keyed`, whose public items keep their paths. Without it `BPSecEditor::remove_blocks` reads no encrypted BIB, refusing a removal one may cover unless the BIB goes too, and `remove_integrity` resolves no `Maybe` coverage. `bpsec::key`, `bpsec::Decrypted` and `Parsed::decrypted`, the operation arguments, the operation-set parse, the parser's coverage stamps and classification, `Role`, `Roles`, `SecurityServices` and `rewrite` need no feature.
- **BREAKING:** `bpsec::bib::OperationArgs` and `bpsec::bcb::OperationArgs` name the operation's security source `source` and its BIB or BCB `security_block`, as `bpsec::checks::Outcome` does. `bpsec::UnknownOperation`, an operation in a security context this node does not implement, is public, as `bib::Operation::Unrecognised` and `bcb::Operation::Unrecognised` carry it.
- **BREAKING:** the editor's refusals have one home. `editor::Error` gains a transparent `Bpsec(bpsec::Error)` variant, so a security operation that fails inside an edit, a decryption, the checks of a decoded BIB, a key the source does not hold, arrives as `editor::Error::Bpsec(e)` rather than `Builder(InternalError(InvalidBPSec(e)))`; and `NotEncrypted`, `NotSigned`, `MaybeHasBib`, `StrandsCiphertext` and `ShrinksEncryptedBib` move from `bpsec::Error` to `editor::Error`, beside `BibIsEncrypted` and `PrimaryBlockHasBib`, as refusals of an edit rather than failures of a security operation. `Signer::sign_block` and `Encryptor::encrypt_block` refuse a target whose coverage reads `Maybe` with `editor::Error::MaybeHasBib`, through their `Editor` variant, and a BPSec error reaches them the same way.
- **BREAKING (behaviour):** `BPSecEditor::remove_blocks` never encrypts anything again, and removes every requested block or none. Where removing a block would shrink a BCB-encrypted BIB that also covers a block that stays, it refuses with the new `bpsec::Error::ShrinksEncryptedBib { block, bib }`, where it re-encrypted the shrunk BIB given an encryption key: new ciphertext under that BCB is its security source's to write, and RFC 9173's BCB carries one IV for all its targets, so a BIB sharing a BCB lost its IV or another target's. It refuses with `bpsec::Error::MaybeHasBib(block)` a block an encrypted BIB it cannot decrypt may cover, and with `editor::Error::PrimaryInSecurityScope` the primary block's BIB while another operation's scope includes the primary, where it kept those blocks and left them out of the returned set. Naming the encrypted BIB too removes it whole. `rewrite::apply_rewrites` returns those refusals. New variant `bpsec::Error::ShrinksEncryptedBib` on the non-`#[non_exhaustive]` `bpsec::Error` enum can break exhaustive `match` arms.
- **BREAKING:** `bpsec::key::KeySource` requires `Send + Sync`, so one key source can serve every stage that processes a bundle, across `await` points and threads. An implementation holding interior mutability moves to its thread-safe form (an atomic for a `Cell` counter, a lock for a `RefCell`).
- **BREAKING:** the `unrecognised` field of `block::Flags`, `bundle::Flags`, and `rfc9173::ScopeFlags` is a plain `u64`, zero when no unrecognised bits are set (was `Option<u64>`, where `None` and `Some(0)` meant the same). Migration: `None` becomes `0` and `Some(bits)` becomes `bits`, so `if let Some(bits) = flags.unrecognised` becomes `if flags.unrecognised != 0`. The serde shape of `block::Flags` and `bundle::Flags` is unchanged for every value a parse or builder produces — the field is omitted when zero — except that an explicit `null` no longer deserializes.
- **BREAKING (behaviour):** equality, hashing, and ordering compare what a value encodes. `block::Flags`, `bundle::Flags`, and `rfc9173::ScopeFlags` compare and hash their wire `u64`, and `block::Type` compares, orders, and hashes its type code, so an alias equals its canonical form (`Type::Unrecognised(1) == Type::Payload`) where it previously compared unequal, and `block::Type`'s order is the code order (it was declaration order, with every `Unrecognised` code last). Pattern matching and the derived `Debug` stay structural, so code that matches on named variants or reads named fields canonicalizes first, and two equal values can print differently; `is_canonical()` tells an alias from its canonical form. Serde canonicalizes `block::Flags`, `bundle::Flags`, and `block::Type` in both directions, with the stored shape unchanged. A security scope written as an alias is the same context as its canonical form, so a context whose targets share a security block shares it across both: the `Signer` puts such targets in one BIB where their scope lets them share, while BCB-AES-GCM gives every target its own BCB.
- **BREAKING:** the owner `Editor`'s `rebuild()` and `rebuild_bundle()` refuse a block carrying `report_on_failure` on a bundle whose final primary forbids it (RFC 9171 §4.2.3-4/-5) — whether an edit set the flag or a kept block carried it under the primary the edits replaced — with the new `editor::Error::ReportOnFailureForbidden(block_number)` variant, which can break exhaustive `match` arms. They previously emitted bytes the parser rejects.
- **BREAKING (behaviour):** the owner `Editor` no longer lets a primary-block edit break a BPSec operation. Its primary setters also refuse, with the new `editor::Error::PrimaryInSecurityScope(block)` naming the lowest such security block, while any remaining BIB or BCB operation's scope includes the primary block, as RFC 9173's default scope does, or a BIB survives whose body cannot be read, as an encrypted BIB's cannot. `with_fragment_info` is exempt and no longer fails: no BIB or BCB is ever added to a fragment (RFC 9172 §5.2), so every operation covers the unfragmented primary. The new variant can break exhaustive `match` arms.
- **BREAKING (behaviour):** `Signer::sign_block` refuses a target already queued in the session with `AlreadySigned`, where it silently replaced the earlier request. Targets share a BIB only when queued with the same source, context and key reference (the same `&Key`), the key standing for the security acceptors that can process them, and only when the context lets operations share a block: BIB-HMAC-SHA2 shares only under a scope that leaves the security header out, since a result bound to its BIB's block number breaks when an RFC 9172 §3.9 split moves it (RFC 9172 erratum 8723), so under the default scope every target gets its own BIB. The `Encryptor`'s shared BCBs group by key the same way.
- **BREAKING:** `Encryptor::encrypt_block` refuses a target whose BIB also covers the primary block, before queueing anything, with the new `encryptor::Error::BibCoversPrimary(bib)` naming that BIB: encrypting the target encrypts the BIB and every block it covers (RFC 9172 §3.9), and a BCB cannot target the primary. Its rustdoc now states that widening. It previously failed at rebuild with an opaque `Editor(PrimaryBlock)`. The new variant can break exhaustive `match` arms.
- **BREAKING:** new variant `builder::Error::PayloadLengthOverflow(u64)` on the non-`#[non_exhaustive]` `builder::Error` enum can break exhaustive `match` arms. `Builder::build_stream` returns it for a declared payload length whose wire form would end past `u64::MAX`.
- **BREAKING:** the block read abstraction is renamed and lifted to the crate root, joining the `Builder`/`Editor`/`Signer`/`Encryptor` role-noun family: trait `bpsec::BlockSet` is now `reader::Reader`, and `bpsec::PlainBlockSet` is now `reader::PlainReader`. No behavioural change — signatures and semantics are otherwise identical, and plain block reading no longer requires the `bpsec` module path. `PlainReader`, two shared references, also derives `Clone`, `Copy` and `Debug`.
- **BREAKING:** `reader::Reader::block` reports the payload slot as a four-state `reader::Availability` instead of `Option<Payload>`: `Available(Payload)`, `NotResident` (extents beyond the resident bytes), `NoKey` (BCB-covered, no usable key), and `NotDecryptable` (BCB-covered, and this node cannot produce the plaintext despite trying — the ciphertext failed to authenticate, or the security context or parameters are unsupported; the give doors report which). A present block's unavailable payload no longer conflates "not held in memory" with "not decryptable by this node", so a caller can respond to each state differently; callers to whom every unavailable state is equivalent use `Availability::available()`.
- **BREAKING (behaviour):** the structural parse marks `BibCoverage::Maybe` only on BCB-covered blocks. As built under RFC 9172 §3.9 ("when adding a BCB"), an encrypted BIB targets only blocks a BCB also covers, so on a bundle carrying an encrypted BIB, a block no BCB covers — typically the per-hop PreviousNode, HopCount and BundleAge blocks, and always the primary block — now reads `None` where it previously read `Maybe`. Editing, signing or encrypting such a block (`Editor`, `ExtensionEditor`, `Signer`, `Encryptor`) no longer refuses with `MaybeHasBib`, so a keyless relay performs its RFC 9171 per-hop rewrites on a signed-then-encrypted bundle instead of refusing them. Residual: a non-conformant sender can leave an encrypted BIB over a block no BCB covers; an edit to that block breaks the hidden signature, which fails closed at the downstream key-holder. A BCB-covered Previous Node or Bundle Age block is not marked either: no valid bundle has an encrypted BIB over one, since only the forwarder that inserted the block can source an operation on it and RFC 9172 §3.9 forbids it a BIB and then a BCB on one target, so an editor without the BIB's key replaces or removes either, where it refused with `MaybeHasBib`. A keyed pass that decrypts such a BIB still stamps the coverage, and `Parsed::check` records the operation conflicting (see Added). The Hop Count keeps the mark, since a signature on a count no node has incremented can stand.
- `creation_timestamp::CreationTimestamp::now` issues strictly monotonic `(time, sequence)` pairs per process, from one atomic: with a well-behaved clock the time component is truly the current UTC time, bundles created in the same millisecond take ascending sequence numbers, and a wall clock that steps backwards never re-issues an earlier pair — so ids built from `now()` are unique by construction within a process and callers need no collision checks. Previously the sequence number was derived from the clock's nanoseconds alone, so two reads landing on the same instant (coarse clocks, concurrent issuers) could collide. Uniqueness across process restarts rests on the wall clock moving forward (RFC 9171 §4.2.7); each fresh millisecond's sequence numbers are seeded from the sub-millisecond nanoseconds, so even a restart across a backward clock step is overwhelmingly unlikely to re-issue a pre-restart pair. Every production minting site benefits without per-site collision handling.
- **BREAKING (behaviour):** non-canonical bundle framing is now a hard parse error (`Error::NotCanonical`). The parser no longer records non-shortest framing for later repair: `bundle validate` loses its "non-canonical but semantically valid" diagnostic, and `bundle rewrite` no longer repairs framing (its repair now covers PreviousNode/HopCount bodies only).
- **BREAKING:** new variants `Error::PossibleBpv6` and `Error::NotABundle(u8)` on the non-`#[non_exhaustive]` `Error` enum can break exhaustive `match` arms. The classification of data that cannot start a BPv7 bundle also changed: the first-byte gate now returns `PossibleBpv6` (CBOR unsigned integer 6, the opening byte of an RFC 5050 primary block), `NotCanonical` (definite-length outer array), or `NotABundle` carrying the offending first byte, where previous releases returned `InvalidCBOR(IncorrectType(..))`.
- CBOR tags at grammar positions that permit none — every scalar and structured field, and the block-array head — are now rejected from the first byte of the tag run, without reading it (decoded via the new `hardy-cbor` `Untagged` wrapper; its cbor-level `UnexpectedTag` is translated to each error domain's `NotCanonical`, so the observable classification is unchanged from previous releases, which read the entire run before rejecting). The one position permitting a tag (`#6.24` on block data) enforces the same fixed-byte bound by hand. This keeps ingress rejection of adversarial tag runs free of per-tag work and per-tag allocation (a scalar-field reject still boxes its one constant field-label error).
- **BREAKING:** the parser bounds every pre-payload offset to 256 MiB (new `Error::PrePayloadTooLarge`): the primary block, every extension block, and the payload block's header must end within the bound — an implementation limit; the whole pre-payload region must be resident for verification, and real header chains are kilobytes. Rejected from the declared lengths alone, before any body byte arrives, identically on every node regardless of pointer width. Only the payload body may exceed the bound (`Block::extent`/`payload_range` stay `u64`), so a parsed header extent always converts to `usize`, and a hostile header-chain declaration can no longer invite spooling bytes the parser must reject anyway.

### Fixed
- A Previous Node block must name a node (RFC 9171 §4.4.1: "That node ID SHALL conform to" §4.2.5.2): `parse::PerHopFields::decode`, and so the parse, refuses one whose endpoint names a service, an ipn endpoint with a non-zero service number or a dtn endpoint with a service name, with `Error::InvalidEid(eid::Error::InvalidNodeId)` inside the "extension block data" field error, where it was accepted.
- BCB-AES-GCM decryption of a target whose authentication tag follows the ciphertext, as Hardy's own encryptor writes it (RFC 9173 §4.4), decrypts in place into one wiped buffer of the plaintext's exact length. It went through `aead`'s allocating `decrypt`, whose spare capacity for the tag made the conversion to a boxed slice reallocate and free the first copy of the plaintext unwiped.
- `Builder::build` no longer makes bundles the parser rejects through the `report_on_failure` block flag when the bundle is an administrative record or has a null source: the flag is cleared on every block (RFC 9171 §4.2.3-4/-5), normalised like the fragment flag. Previously `with_hop_count`, which sets the flag, made any such bundle with a hop limit unparseable.
- A named flag bit carried in the `unrecognised` field of `block::Flags`, `bundle::Flags`, or `rfc9173::ScopeFlags` is now the flag it encodes. A hand-built `unrecognised` encodes bit for bit, so a named bit carried there set the flag on the wire while its field read false: it slipped past `ExtensionEditor`'s `report_on_failure` refusal and `Builder::build`'s normalisation into bytes the parser rejects, and in a BPSec scope it left the primary block out of the IPPT/AAD the security source computed while the emitted parameter told the receiver to include it. Every method that takes flags now canonicalizes them (the new `canonicalize()`, above) — `Builder::with_flags`, both `BlockBuilder::with_flags`s, `Editor::set_bundle_flags`, `ExtensionEditor::insert`, and the BIB-HMAC-SHA2 and BCB-AES-GCM operations' scope, with the builder's block template as the backstop — so an alias is refused, normalised, or covered as the flag it encodes, and the `Bundle` a builder returns matches its bytes. Parsed values are already canonical, so parsed round-trips are unchanged. Serde canonicalizes in both directions (see Changed); direct field writes are not canonicalized.
- `Editor::push_block`, `Editor::insert_block`, and `Builder::add_extension_block` canonicalize their block-type argument through the new `block::Type::canonicalize()`, which folds an `Unrecognised` alias of a known type code back to its named variant. A hand-built `Type::Unrecognised(v)` encodes as the raw code `v`, so `Unrecognised(11)` or `Unrecognised(12)` previously bypassed `push_block`'s security-block refusal and emitted a block the next node parses as a real BIB/BCB without going through the Signer/Encryptor; `Unrecognised(0)` bypassed both primary-block refusals, and `Unrecognised(1 | 6 | 7 | 10)` bypassed the singleton-duplicate rules (producing bundles the receiving parser rejects). All three caller-supplied-type doors canonicalize, and `BlockTemplate::new` canonicalizes as the constructor invariant, so a stored template never holds an alias and replace-by-type matches are sound. Scope of the refusals is per door: the editor doors refuse the reserved codes and enforce the singleton rules whatever variant carries them; the builder door refuses only wire code 0 — its contract deliberately permits security blocks and duplicates, as the test-crafting surface. Any other policy that matches on named variants can canonicalize first.
- `Editor::insert_block`'s replace-by-type path handles BPSec coverage exactly like `update_block`: the replaced block is stripped from its covering BIB/BCB target lists, and the replace refuses (`BibIsEncrypted`, `MaybeHasBib`) where coverage cannot be safely updated. Previously it built a fresh template with no BIB handling, so replacing a BIB-covered block (e.g. the forwarding path's hop-count update on a bundle whose HopCount a peer had signed) emitted a wire bundle whose BIB still targeted the changed body — failing verification downstream — while the in-memory rebuilt `Bundle` reported the block uncovered.
- The owner `Editor`'s primary-block setters (`with_source`, `with_destination` and the rest), used for wire re-encoding, fragment reassembly and tooling, refuse with `PrimaryBlockHasBib` whenever a BIB still targets the primary block. Previously they refused only while that BIB was untouched, so stripping another target from the same BIB in the same session — as replacing a signed Hop Count does — let a setter through and left a primary signature that no longer verified. `remove_integrity(0)`, or removing the BIB with `BPSecEditor::remove_blocks`, releases the primary for editing once no other operation's scope includes it.
- The `Signer` computes every group's IPPT over the primary block as it stands, so no result depends on the order the groups are built. In a session where one source signed a primary carrying a CRC and another signed a block under a scope including the primary, the group built first computed its IPPT over the primary with its CRC and the one built second over the primary without it, so by `HashMap` order about half the outputs failed verification.
- Under key wrap, a multi-target BIB's targets share one CEK, wrapped once into the BIB's one parameter set (RFC 9173 §3.8.2). Each target minted its own, and only the first target's wrapped key reached the wire, so every other target's HMAC could never verify.
- `Editor::remove_block`, `Editor::update_block` and the BPSec cascades under them read a block's current BIB and BCB coverage. After `update_block` stripped an encrypted block from its BCB, the BCB went and a pushed block could reuse its number; removing or updating the first block again then parsed the pushed block as a BCB and failed, a removal with the first block already gone from the returned editor. A failed strip now also leaves the block in place.
- `BPSecEditor::remove_blocks`, given a key, no longer emits a BIB in plaintext under the BCB that encrypted it. Removing a block that was signed and then encrypted decrypted the covering BIB but never stripped the block from it, so an emptied BIB stayed in the clear under a BCB still listing it, and a shrunk one was re-encrypted still naming the removed block. The decrypt now resolves the removed targets' coverage: an emptied BIB goes with the BCB's operation on it.
- A CBOR tag on the status flag of a status-report assertion was silently accepted — the bare `bool` decode folds tag presence into a canonical flag the caller discarded. It is now rejected (`InvalidField("status")` wrapping `NotCanonical`).
- A payload block whose declared byte string carries the bundle's wire form to `u64::MAX`, leaving no room for the outer break, is rejected as `InvalidCBOR(TooBig)` by `parse` and the streaming parser alike. `parse` reported it as truncation (`InvalidCBOR(NeedMoreData(_))`), and the streaming parser handed it back as `Partial`, whose `encoded_len()` overflowed: a panic in a debug build, and a length of 0 in release.
- The keyed check leaves a plaintext BIB with an unsupported security operation to the parser's classification (`Parsed::classification`), whose flags decide what becomes of it (RFC 9171 §5.6 Step 4). It checked it and failed with `UnrecognisedContext`, so a BIB that asked for nothing rejected the bundle, and callers had to take a `bib_deletable` BIB out of the BIB operation sets before verifying; they no longer do. A BIB under a BCB with an unsupported security operation is left encrypted, as one without a key is.
- `parse()` and `BundleParser::finish` reject a bundle whose plaintext Previous Node, Bundle Age or Hop Count data does not decode as RFC 9171 §4.4 defines it (`InvalidField("extension block data")` over the decode error), as §5.6 Step 3 makes it malformed. They accepted it, leaving the decode, and the rejection, to each consumer.
- **BREAKING:** `parse()` and `BundleParser::finish` reject a bundle whose creation time is zero and that carries no Bundle Age block, with the new `Error::MissingBundleAge`: RFC 9171 §4.4.2 requires one of a bundle whose source has no accurate clock. A BCB-covered Bundle Age counts, its presence being what the rule asks. The RFC 9173 Appendix A.1, A.2 and A.4 examples carry none, so they no longer parse as published; the tests use them with one inserted, which changes none of their security results.

## [0.6.0]

### Added
- `bundle_age` and `lifetime` modules with `BundleAge`/`Lifetime` newtypes that enforce canonical CBOR on the wire.
- `cmp` module with `compare_bundles()` for structural bundle diffing.
- `crc::Digest` push-mode digest (`new`/`cbor_head`/`push`/`push_zeros`/`verify`/`finalize`) avoiding heap allocation on the CRC path.
- `editor::Chunk` zero-copy output type and `Editor::rebuild_bundle()` returning the parsed `Bundle` alongside its chunks.
- `builder::BlockTemplate::build_to_vec()`, `eid::Eid::to_node_id()`, `block::Payload::{len, is_empty}`.
- `IpnNodeId: Copy`; `block::Type: PartialOrd + Ord`.

### Changed
- **BREAKING:** `FromCbor::Error` for `block::Flags`/`Type`, `bundle::Flags`, `crc::CrcType`, `bpsec::Context`, `dtn_time::DtnTime`, `status_report::ReasonCode` changed from `hardy_cbor::decode::Error` to the crate/`bpsec` error type (carrying `NotCanonical`).
- **BREAKING:** `Editor::rebuild()` now returns `Vec<editor::Chunk>` instead of `Box<[u8]>`; `RewrittenBundle::Rewritten.new_data` and `CheckedBundle.new_data` now hold `Vec<editor::Chunk>` instead of `Box<[u8]>`.
- **BREAKING:** new variants on public (non-`#[non_exhaustive]`) error enums — `Error::{InvalidHopLimit, NotCanonical}`, `editor::Error::SecurityBlock`, `eid::Error::NotCanonical`, `status_report::Error::NotCanonical` — can break exhaustive `match` arms.
- **BREAKING (behaviour):** scalar decoders now strictly enforce RFC 9171 canonical form, rejecting non-shortest encodings and hop limits outside `1..=255`; some bundles that previously parsed are now rejected.
- Bumped `aes-gcm` 0.10 → 0.11 (internal; BPSec AES-GCM adapted to the `AeadInOut`/`decrypt_inout_detached` API; behaviour unchanged).
- Raised the minimum supported Rust version (MSRV) to 1.95.

### Fixed
- Accept fragment bundles with `offset == 0` and `total == 0`.
- Accept multi-target BCBs from other implementations; handle non-payload BCB decrypt failures per RFC 9172; narrow handling to the `DecryptionFailed` case.
- Use `core::cmp::Reverse` so `no_std` builds compile.
- `Builder::build` keys the returned `Bundle.blocks` map by wire block number (primary 0, payload 1, extensions 2+) instead of the extension enumeration index, which previously collided with the primary and payload entries.
- `Editor::flatten_inplace` handles mixed-direction edits (a block shrinking before an unchanged block while another grows after it) by assembling into a fresh buffer instead of an unsound single-direction in-place copy.
- **BREAKING (behaviour):** signing the primary block with a BIB now removes the primary's CRC before generating the IPPT (RFC 9173 §3.8.1), matching what conformant verifiers compute; a prior release signed the primary with its CRC still present, producing a non-interoperable signature. The CRC is retained when the primary is only IPPT scope context, not the BIB target.
- `Editor::remove_integrity` clears the target block's BIB coverage when its covering BIB is removed, so `rebuild_bundle()` no longer reports a dangling reference to a BIB that no longer exists.
