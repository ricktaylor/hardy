# Changelog

All notable changes to `hardy-tcpclv4` are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this crate adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- `Tcpclv4Builder::max_outstanding_transfers` (default: 16; a `NonZeroUsize`, so zero is unrepresentable) bounds the transfers accepted but not yet resolved with an outcome, per peer; when reached, further forwards to that peer are held unanswered, which is the flow control back to the BPA. Per-peer scoping keeps one unreachable peer's stalled dials from starving admission for healthy peers.
- Mutual TLS: `tls.client-auth` (`off` | `optional` | `required`) has the listener request dialers' certificates and verify them against `tls.ca-certs`; `optional` verifies a certificate when one is presented but accepts dialers without one, easing fleet migration towards `required` (the RFC 9174 Section 4.4.3 baseline). The `tls.cert-file`/`tls.key-file` pair is the node's single identity: it is now also presented as the client certificate when a dialed peer requests one, so dialing into a mutual-TLS peer needs no additional configuration.

### Changed
- Forwards resolve out-of-band per the `hardy-bpa` deferred transfer-outcome contract: `forward` answers `Accepted` once the transfer passes admission, the transfer runs to its terminal state on pooled sessions, and the outcome — `Completed` on full acknowledgment, `Failed` otherwise — is reported via `Sink::transfer_outcome`. Transfers overlap across pooled connections instead of serialising behind a held forward call; completion order across connections is not guaranteed.
- **BREAKING**: the crate no longer parses configuration. The `config` module and the `serde` cargo feature are removed; the config-file schema (unchanged on disk) is owned by the consuming applications, and the example configuration files live with `hardy-tcpclv4-server`. The CLA is the renamed `Tcpclv4` type, constructed by `Tcpclv4::builder()`, with every default private to the builder and documented on its method.
- **BREAKING**: builder inputs carry their invariants as types instead of build-time checks: `ContactTimeout` bounds the contact-header wait to RFC 9174 Section 4.2's 1 to 60 seconds, `KeepaliveInterval` wraps a non-zero interval (disabled is `None`, matching the wire's zero encoding), and the MRUs and connection rate limit are `NonZero` integers. A listener is a passive listening element added per `listen(address)` call (RFC 9174 Section 2.1 allows zero or more), so the library binds nothing unless asked; `listen_default()` is the IANA-registered `[::]:4556`. Listener sockets are bound eagerly during `build()` (accepting starts at BPA registration), so bind failures surface as construction errors, and listeners under a required-TLS policy with no identity are a build error instead of a silently idle listener.
- **BREAKING**: TLS material is built from the now-public `tls::Tls::builder()` (loaded and validated by `TlsBuilder::build()`) and attaches with `tls(..)`, with `required(..)` chained on the TLS builder to refuse sessions that do not negotiate TLS. "TLS required but not configured" and a lone certificate half are unrepresentable; a missing trust anchor is a build-time error; and the crate-root `Error` type is replaced by the focused `builder::Error` (socket binding and TLS loading, the only ways `build()` can fail).
- **BREAKING**: the TLS debug flag `tls.debug.accept-self-signed` is replaced by the deliberately loud `insecure-skip-verify` (`tls::Tls::builder().dangerous().insecure_skip_verify()`), and the `tls.debug` section is removed. `private-key-file` is renamed to `key-file` (the old name remains accepted as an alias by the config surfaces). A trust anchor is mandatory: configuring neither `ca-certs` nor `insecure-skip-verify` is a startup error, and `insecure-skip-verify` overrides `ca-certs` with a startup warning naming both (the ignored certificates are never loaded), so a debug session is one line to flip.
- `session::Error` is the session's outcome taxonomy: transport I/O failures split from codec (dialect) failures at conversion, and writer-closed / ingest-stopped are first-class outcomes with truthful `tcpclv4.session.terminated` labels (`writer_closed`, `ingest_stopped`; an `UnexpectedEof` counts as `hangup`). `WriterHandle::send` returns a two-variant `SendError` instead of a tri-state bool result, so a closed writer cannot be mistaken for success by construction.
- The UT-TCP-03/04 unit tests exercise the production negotiation and segmentation code (`KeepaliveInterval::negotiate` and `negotiate_segment_mtu`; `send_once` driven end-to-end against a preloaded acknowledgment stream) instead of asserting on re-implementations of the same arithmetic.
- Bundle dispatch to the BPA moved off the session reader loop into a per-session ordered ingest task: segments, acknowledgments of outbound transfers, and keepalives keep flowing while a received bundle is being stored. The final `XFER_ACK` of a transfer is still only sent after dispatch completes, and acknowledgments are emitted in segment-arrival order.
- Outbound segments are queued to the writer task without a per-segment completion round-trip, and the writer flushes when its command queue runs dry. The session never awaits a blocked write without concurrently processing inbound messages, removing a mutual-stall risk when both peers send large transfers simultaneously.

### Fixed
- The contact header's `CAN_TLS` flag is honest per role: the accepting side advertises TLS only when an identity is configured to serve it, while the dialing side still offers TLS with trust-only material (the client role needs no identity). Previously a listener with trust-only TLS material advertised `CAN_TLS`, and a peer accepting the offer drove the accept path into an identity-less TLS accept and aborted the process.
- A mid-transfer `XFER_REFUSE` now clears all outstanding acknowledgment expectations for the refused transfer (RFC 9174 Section 5.2.2 sends no further `XFER_ACK` messages for it), where previously stale expectations desynchronised the acknowledgment matcher and tore down the session.
- A dial timeout no longer stalls a forward behind repeated connection attempts when a session to the peer already exists: the forward falls back to queueing on the busy session after one attempt. The TCP connect itself is now bounded by `contact-timeout` (previously unbounded — around two minutes at Linux defaults for a silently dropped SYN). Concurrent forwards coalesce on a per-peer dial lock instead of racing parallel dials past the pool's capacity bound.
- A rejection whose write never reached the peer (writer already closed) now terminates the session instead of being reported as success; unknown message types are rejected-and-tolerated in every session state rather than being fatal only when idle; and desync rejections use the `Unexpected` reason (the message type is known), with a dispatch-dead session terminating as `ResourceExhaustion` rather than `Unknown`.
- An out-of-order `XFER_SEGMENT` with the START flag now also drops the in-progress reassembly buffer, which could otherwise splice two transfers into one dispatched bundle; the offending transfer's remaining segments are swallowed after a single rejection.
- An actively dialed session registers in the pool before the dial returns, so the dialing forward can no longer miss its own fresh session and dial twice.
- A session torn down by ingest failure still sends its courtesy `SESS_TERM (Resource Exhaustion)`: the graceful-teardown skip now triggers only on CLA-wide shutdown, and the outcome is labelled `ingest_stopped` in the termination metric.
- A failed or panicked ingest task (BPA dispatch failure) now cancels its session promptly instead of stalling until the next inbound segment; dispatch failures log at `warn!` and an ingest panic at `error!`.
- The writer closes on any transport write failure (previously only `Feed` failures closed it) and remains cancellable under sustained feeds: every socket write and flush is raced against the cancellation token, so shutdown cannot hang behind a peer that stops reading.
- The connection pool is bounded at its documented `max-idle-connections` capacity (previously effectively one over), and `max-idle-connections = 0` no longer retains an idle connection.
- Oversized inbound transfers are refused with `XFER_REFUSE (Not Acceptable)` and their remaining segments swallowed, instead of `MSG_REJECT` followed by a rejection per segment.
- Session termination follows RFC 9174 Section 6.1: no new outgoing transfers start once the session is Ending (queued forwards return to the pool for retry on another session), and a crossing `SESS_TERM` is not acknowledged with a second one.
- Peer-supplied `segment_mru` and configured `transfer_mru` are clamped rather than truncated on 32-bit targets, where truncation to a zero segment MTU turned the segmentation loop into an infinite empty-segment spin.
- The connection pool now dials a new connection when every pooled session is busy and the pool is under capacity, matching the documented pooling strategy — previously a forward queued behind a busy session and parallel connections were only established when none existed at all. If the peer cannot accept a new connection, the forward falls back to queueing on a busy session, preserving delivery to peers with asymmetric reachability.

## [0.4.0]

### Changed
- **BREAKING:** raised the `hardy-bpa`/`hardy-bpv7`/`hardy-async` requirements to their incompatible 0.2/0.6/0.2 releases. `Cla` implements `hardy_bpa::cla::Cla`, so consumers must move to `hardy-bpa` 0.2 in lockstep.
- Raised the minimum supported Rust version (MSRV) to 1.95.

### Fixed
- Bound the connection-pool forward retry loop so a flapping peer (sessions that accept then fail while the pool stays above `max_idle`) can no longer wedge a forward indefinitely.
- Use pointer identity (`Arc::ptr_eq`) when removing an emptied pool, so a concurrently re-created pool for the same peer is not erroneously dropped.

Releases before this version predate this changelog; see the git history for details.
